telephony-triage 구조 안내서

Jira 이슈와 logcat을 받아 원인과 해결책을 찾고, 그 결과를 팀 공용 이슈 DB 레포에 카테고리 > 이슈 유형(증상) > 원인으로 쌓는 도구입니다. 1부는 처음 쓰는 사람을 위한 설명과 상황별 사용 예, 2부는 구조와 동작 원리, 3부는 장단점과 앞으로의 계획입니다.

01이 도구가 하는 일

기술 용어 없이 먼저 설명합니다. 자세한 구조는 2부에 있습니다.

폰에서 "데이터가 안 붙어요", "통화가 끊겨요" 같은 이슈가 Jira로 들어오면, 담당자는 수만 줄짜리 로그를 열어 원인을 찾습니다. 그런데 같은 원인은 몇 달 뒤 다른 사람에게 또 들어옵니다. 그때마다 처음부터 다시 찾는 일을 줄이려고 만든 도구입니다.

병원에 비유하면 이렇습니다.

검사 결과logcat 로그. 폰이 남긴 기록입니다.
진단 기준시그니처. "이 로그 줄이 보이면 이 원인"이라는 규칙입니다.
병명 사전이슈 DB. 팀이 지금까지 찾은 증상·원인·해결책을 모아 둔 GitHub 레포입니다.
소견서분석 리포트. 어떤 원인과 맞았고 근거 로그가 무엇인지 보여줍니다.

도구는 로그를 사전의 진단 기준과 자동으로 대조해서 "이 이슈는 예전 그 원인과 같다"를 알려 줍니다. 처음 보는 원인이면 담당자가 확인한 내용을 사전에 새로 등록합니다. 등록은 PR로 올라가고 카테고리 담당자가 리뷰한 뒤 반영됩니다. 이렇게 사전이 쌓일수록 다음 사람이 빨라집니다.

그림 0 · 사용자가 보는 네 단계

사람이 하는 일

  • Jira 키와 로그 파일 경로를 넣는다
  • 리포트를 읽고 "이 원인이 맞다 / 아니다"를 고른다
  • 올리기 전 확인 화면을 보고 승인한다

도구가 하는 일

  • 로그에서 전화번호·IMSI 같은 개인정보를 가린다
  • 사전과 대조해 후보 원인과 근거 로그를 고른다
  • 사전 수정 파일을 만들고, 기존 분류를 깨지 않는지 검사하고, PR을 올린다
Claude는 어디에 쓰이나요? "이 원인이다"라는 판정은 Python 스크립트가 규칙대로 합니다. 같은 로그면 누가 돌려도 같은 결과가 나오게 하려는 것입니다. Claude는 스크립트를 실행하고, 결과를 사람 말로 설명하고, 새 원인 초안을 쓰고, 사용자에게 질문하는 역할을 맡습니다. 사전에 처음 보는 패턴을 Claude가 더 깊이 분석하는 단계는 새 패턴을 Claude로 분석하기에 정리했습니다.

플러그인 telephony-triage

Claude Code에 설치하는 도구. 스킬 1개, 커맨드 13개, hooks, Python 스크립트(파서·매처·검증기·PR 오케스트레이터)로 구성됩니다.

이슈 DB telephony-issue-db

사내 GitHub 레포. 유형·원인·시그니처·파서 규칙·마스킹된 fixture 로그·Jira 기록이 YAML/Markdown으로 쌓입니다. README와 STATS는 생성 파일입니다.

설계의 중심 원칙. 분류·회귀·검증 판단은 결정적인 스크립트 출력(파서 이벤트, 시그니처 매칭)이 합니다. LLM(Claude)은 스크립트를 부르고, 결과를 설명하고, 초안을 쓰고, 사람에게 확인받는 역할만 합니다. 이슈 DB 파일을 Claude가 직접 쓰지 않습니다.

A

처음 써 보는 연습 (dry-run)

누구나 · 5분
상황
설치는 했는데 실제로 PR이 올라갈까 봐 겁난다.
입력
/telephony-triage:analyze ABC-12345 ~/logs/radio.txt --dry-run
진행
  1. 평소 분석과 똑같이 로그를 읽고 리포트와 분류 질문까지 보여줍니다.
  2. 마지막 "올리기 전 확인 화면"까지 보여주고 거기서 끝냅니다.
결과
아무것도 올라가지 않습니다. 임시 작업 폴더도 정리됩니다. GitHub 로그인(gh auth) 전에도 됩니다.
팁
Jira 연결이 아직 안 됐으면 --jira-file <yaml>로 Jira 내용을 파일로 줄 수 있습니다. 이 옵션은 dry-run에서만 받습니다.
B

예전과 같은 원인 (가장 흔한 경우)

기여자 · 10분
상황
"로밍 중 데이터 안 됨" Jira가 들어왔다. radio·main 로그가 있다.
입력
/telephony-triage:analyze ABC-12345 ~/logs/radio.txt ~/logs/main.txt
진행
  1. 도구가 이슈 DB를 최신으로 맞추고 Jira를 읽습니다. Jira에 발생 시각이 없으면 로그에서 후보 시각을 보여주고 고르게 합니다.
  2. Android 버전에 맞는 소스 트리(16/17)를 추천하고 확인받습니다.
  3. 로그를 대조해 리포트를 보여줍니다.
  4. "이렇게 분류할까요?"에 예를 고릅니다.
  5. 올리기 전 확인 화면을 보고 승인하면 PR이 올라갑니다.
화면 예시
## ABC-12345 분석 - 분류 후보: data > DATA-001 > DATA-001-02 Roaming disabled (규칙 일치 점수 1.0, 신뢰도 높음) - 근거 로그 (마스킹, 슬롯 phone 1): - 08:00:00 SST-1 onRoamingOn: roaming=true - 08:00:02 DSMGR-1 DataRoamingEnabled changed to false - 08:00:03 DNC-1 Data evaluation: … Data disallowed reasons: ROAMING_DISABLED - 로그 범위: 07:58 ~ 08:09 (발생 시각 포함), 시계 이상 없음 - 해결책: 데이터 로밍 설정을 켠다 수정 상태: not-a-bug - 기존 사례: Jira 1건 (ABC-333) 이 이슈를 Data > SETUP_DATA_CALL이 발생하지 않음 > Roaming disabled 로 분류할까요? > 예
결과
이슈 DB에 jira/ABC-12345.yaml 한 파일이 추가되는 PR. README의 "Jira 2건"이 자동으로 갱신됩니다. data 카테고리 오너가 리뷰합니다.
팁
"규칙 일치 점수"는 원인 확정이 아니라 규칙과 얼마나 맞는지입니다. 근거 로그 줄을 직접 확인하고 고르세요.
C

증상은 맞는데 원인이 확인되지 않음

기여자
상황
리포트에 "유형 일치, 원인 미확인"이 나온다. 증상 규칙은 맞았지만 그 아래 원인 규칙은 하나도 맞지 않은 경우입니다.
선택지
  • 먼저 탐색 분석을 실행하면 Claude가 타임라인과 소스를 보고 원인 가설을 정리해 줍니다(Step 5-2, 토큰 추가 사용).
  • 로그를 보고 기존 원인 중 하나가 맞다고 판단되면 그 원인을 고릅니다 (chose-other). 그 원인에 규칙이 없던 경우("시그니처 없는 기존 원인")라면 규칙 추가도 함께 제안됩니다.
  • 원인이 새것이면 D. 새 원인으로 갑니다.
  • 아직 모르겠으면 원인 미확정으로 기록합니다. Jira는 그 증상 아래 cause: unresolved로 쌓이고, 같은 것이 모이면 월간 리뷰에서 다룹니다.
팁
추정만으로 새 원인을 만들지 마세요. 확신이 없으면 "원인 미확정"이 정답입니다.
D

아는 증상, 처음 보는 원인

기여자 · 20~30분
상황
"SETUP_DATA_CALL 안 나감" 증상인데, 로그를 보니 APN 설정이 비어 있어서였다. 사전에 이 원인이 없다.
진행
  1. 분류 질문에서 새 원인을 고릅니다.
  2. Claude가 원인 제목, 설명, 해결책, 판별 규칙(시그니처), 필요하면 파서 규칙, 그리고 근거 로그만 잘라 마스킹한 fixture 초안을 보여줍니다. 하나씩 고치거나 승인합니다.
  3. 도구가 초안 검증 R1~R5를 돌려 표로 보여줍니다: 새 규칙이 이 로그를 잡는지, 정상 로그나 다른 원인 로그는 안 잡는지, 기존 분류가 그대로인지.
  4. 확인 화면에서 승인하면 PR.
화면 예시
### 검증 결과 R1 파서 ✅ / R2 양성 ✅ (C=1, 다른 원인 C=0) / R3 음성 ✅ (C=0 12/12) R4 교차 회귀 ✅ / R5 이벤트 diff ✅ (추가 1, 변경 0) / R6 추가 표본: 없음 ### ID 할당 NEW-CAUSE-1 → DATA-001-03
결과
원인 정의(type.md), fixture 로그, Jira 기록이 한 PR로 올라갑니다. 임시 이름 NEW-CAUSE-1은 올리는 순간 비어 있는 다음 번호로 바뀝니다.
팁
규칙을 아직 못 만들겠으면 record에서 "시그니처 나중에"(signatures_pending)로 원인만 먼저 등록할 수 있습니다. 해결책은 근거(다른 Jira, 적용 후 로그)가 있어야 "검증됨"이 됩니다.
E

"후보 없음": 처음 보는 증상

기여자
상황
리포트에 후보 없음이 나온다. 사전의 어떤 증상 규칙에도 맞지 않는 경우입니다. 초기에 사전이 비어 있을 때 자주 나옵니다.
지금 보여주는 것
  • Jira 요약 키워드로 찾은 비슷한 유형 상위 3개 ("설명 기반 유사 후보")
  • 발생 시각 앞뒤 5분의 오류·거부·타임아웃 이벤트 목록
  • 로그가 발생 시각을 포함하는지, 시계 이상이 있는지
화면 예시
- 분류 후보: 후보 없음 (S=1인 유형 없음) - 설명 기반 유사 후보: SMS-001 SMS가 전송되지 않음, IMS-001 IMS 등록이 되지 않음 - 오류·거부·타임아웃 이벤트: 7건 - 로그 범위: 13:20 ~ 13:31 (발생 시각 포함) 선택: 새 유형 / 원인 미확정(가장 가까운 유형) / 기록하지 않음
선택지
  • 새 유형: 비슷한 유형 3개를 먼저 보여주고, 정말 새것이면 증상 규칙(필수)과 첫 원인 초안을 만듭니다. 이후는 D와 같습니다.
  • 원인 미확정: 가장 가까운 유형에 태그와 함께 넣어 둡니다. 같은 성격이 3건 이상 쌓이면 메인테이너가 새 유형이나 새 카테고리를 만듭니다.
  • 기록하지 않음: 아무것도 올리지 않고 끝냅니다.
실패 스텝

13파싱과 매칭

로그 수만 줄을 사건 목록으로 바꾸고, 알려진 패턴과 대조하는 부분입니다.

그림 8 · logcat에서 후보까지

점수 공식

S = 증상 시그니처 충족 시 1, 아니면 0
C = 원인 시그니처 충족 시 1, 아니면 0
base  = symptom_weight × S + cause_weight × C            # 기본 0.4·S + 0.6·C
bonus = proximity_bonus_max × (1 − |근거 시각 − 발생 시각| / 분석 범위 절반)
      + keyword_bonus_max  × (Jira 텍스트와 원인 title/tags 키워드 일치 비율)
score = min(1, base + bonus)
# 피드백 가중치가 켜져 있고 표본 ≥ min_samples이면: score × (0.5 + 0.5 × 수락률)

후보 순위

순위 키 = (−(score + focus), −(근접 + 키워드 + focus), 유형 ID, 원인 ID)
# focus: 실패 스텝 기준 우선 유형이면 최대 0.05, 아니면 0

S=C=1이면 score가 1.0에서 포화되므로, 점수가 같은 후보는 발생 시각 근접·키워드(Jira 요약·설명·실패 스텝) 근거로 정렬합니다(R8, 10/04). score, 일치 수준, S/C는 바뀌지 않고 회귀·검증 모드에는 보너스와 focus가 없어 결과가 그대로입니다. 리포트의 "일치 수준"은 규칙이 얼마나 맞는지이지 진단 확신도가 아닙니다.

분석 모드 (analyze)

  • 범위: 발생 시각 ±5분
  • S=1인 유형 안에서만 원인 평가
  • bonus, 피드백 가중치 사용
  • S=1, C=0 → "유형 일치, 원인 미확인"

회귀·검증 모드 (--regress)

  • 범위: fixture 파일 전체
  • 모든 active 원인의 C를 S와 무관하게 평가
  • bonus 0, 피드백 가중치 끔
  • 판정은 S/C 값만 사용 (점수 무관)

매처와 extractor는 항상 마스킹된 텍스트에서 돕니다. 마스킹은 같은 값을 같은 번호(<CELL#1>)로 바꾸고 멱등이라, 분석과 회귀가 같은 텍스트를 봅니다. 그래서 시그니처도 마스킹된 로그 기준으로 씁니다. same_phone: true(기본)는 듀얼 SIM에서 모든 조건이 같은 슬롯의 이벤트로 충족돼야 한다는 뜻입니다.

구성내용

19장점

재현되는 판정

분류 기준이 결정적 스크립트 출력이라 누가 돌려도 같은 결과가 나옵니다. LLM 답변의 편차가 분류에 섞이지 않습니다.

지식이 데이터에 있음

태그·문구·시그니처·fixture가 이슈 DB에 있어서, Android 버전이 바뀌어도 플러그인 재배포 없이 이슈 DB PR로 대응합니다.

팀이 함께 키우는 사전

새 유형은 코드가 아니라 규칙 파일로 추가됩니다. 팀원이 PR만으로 파서와 시그니처를 발전시킬 수 있습니다.

규칙 변경의 회귀 안전망

모든 원인에 양성·음성 fixture가 있고, R1~R6이 "새 규칙이 기존 분류를 깨는지"를 PR 전에 잡습니다.

충돌 없는 협업

계획 재적용 + 적용 시점 ID 할당 + drift 확인으로, 여러 명이 동시에 기여해도 텍스트 충돌이나 ID 중복이 거의 없습니다.

개인정보 보호

로그·Jira 텍스트를 즉시 마스킹하고, Jira 원문은 모델 컨텍스트에도 들어가지 않습니다(RF-1 브리지).

토큰 절약

드라이버가 결정적 단계를 묶어 Claude는 4KB 결과 하나만 읽습니다. 확실한 단일 후보는 LLM 없이도 리포트가 거의 완성됩니다.

사외 개발, 사내 끼워 맞추기

모의 Jira·gh·소스 트리·합성 로그로 사외에서 전부 테스트하고, 사내 값은 SITE_PATHS 경로에만 둬서 재반입이 안전합니다.
