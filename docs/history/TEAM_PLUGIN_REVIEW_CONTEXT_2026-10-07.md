# 팀 운영 관점 플러그인 검토 컨텍스트

작성일: 2026-10-07. 목적: 사용자·관리자·승인권자의 사용성, 운영성, 보안, 분석 신뢰성 및 확장 방향을 현재 구현 근거로 평가한다. 구현 변경이나 배포 승인을 의미하지 않는다.

## 요청과 검토 범위

팀은 Jira와 Android Telephony 로그를 분석하고 원인·해결책을 이슈 DB에 축적하며 리포트를 공유하려 한다. 메인 오케스트레이터가 역할별 에이전트의 독립 검토를 종합한다. 승인권자는 분류 확인자, PR 리뷰어/카테고리 오너, 운영 도입·접근 권한 승인자를 구분한다.

- 사용자: 설치, 첫 분석, 검색, 수동 기록, 불확실한 결과 해석, 중단·재개, 리포트 공유.
- 관리자: 설정·배포·업데이트, DB 품질, 운영 지표, 장애 복구, 백업·보존, 확장 비용.
- 승인권자: 승인 대상과 근거, 권한 분리, 변경 추적, 예외 승인, 재승인, 서버 측 강제.
- 공통: 개인정보·사내 코드, 외부 입력의 지시문, 로컬 산출물, 외부 파서, 분석 재현성, 다중 사용자 협업.

## 확인된 구조와 전제

- commands Markdown → Claude skill → Python CLI 구조다. Claude는 설명과 사람 확인을 담당하며, 파서·시그니처의 S/C 판정은 Python이 수행한다.
- triage.py/triagelib은 lock, DB 스냅샷, Jira 정규화, 분석 구간, 파싱·마스킹, 매칭, 코드 참조, analysis.json/report.md를 조율한다. 하위 CLI main()을 같은 프로세스에서 호출한다.
- DB는 별도 Git 저장소다. 카테고리 > 유형 > 원인, Jira별 YAML, parser-rules, 마스킹 fixture, feedback으로 구성한다.
- 쓰기는 plan.json → 최신 main 기준 별도 worktree → 검증·생성 파일 → 변경 승인 → commit/push/PR이다. sync-pr는 계획을 재적용하며 drift를 감지한다.
- guard와 Jira bridge가 도구 호출을 통제한다. 로컬 hook은 완전한 보안 경계가 아니며 서버 권한·브랜치 보호와 구분해야 한다.
- 분석 캐시는 있지만 시그니처 컴파일 파일 캐시는 제거되어 있다. confidence는 규칙 점수 구간이며 확률로 단정하지 않는다.
- 현재 .local-draft 존재, plugin/site-defaults.yaml 부재. example은 테스트 헬퍼용이다. 사내 실제 데이터 정확도·호환성은 확인 필요다.
- 기존 스테이징 변경(DRAFT_NOTES, site 관련 문서, s0_suggest 및 테스트, CHANGES 등)이 있다. 이번 검토는 이를 변경·커밋하지 않는다.

## 협업 방식

1. 사용자 경험 에이전트: 실제 명령·스킬·리포트 흐름을 따라 마찰과 오해 위험을 평가한다.
2. 운영·확장 에이전트: 설정, 배포, DB 거버넌스, 복구, 성능·아키텍처 확장을 평가한다.
3. 승인·보안 에이전트: 권한 경계, 승인 무결성, 정보 흐름, 감사·보존과 위협을 평가한다.
4. 메인 오케스트레이터: 분석 신뢰성과 검증을 추가 검토하고, 중복 제거·상충 조정·근거 확인·우선순위·로드맵·수용 기준을 종합한다.

각 에이전트는 파일 수정 없이 검토 결과를 전달한다. docs/history/는 읽지 않는다. CLAUDE.md, docs/design/12-principles.md, DRAFT_NOTES와 관련 설계/계약을 따른다. Claude 전용 기능을 실행하지 않는다. 외부 Jira·Git 쓰기, 실제 민감 로그 열람, 네트워크 변경, 구현 수정은 범위 밖이다.

## 근거와 출력 규칙

- 기존 보호 장치를 먼저 확인하고 이미 구현된 기능을 신규 제안처럼 제시하지 않는다.
- 사실(코드 경로), 설계 의도, 미검증 사항, 제안을 분리한다. 결함은 재현 근거가 없으면 잠재 위험으로 표기한다.
- 항목마다 역할/사용 시나리오, 현재 근거(path:line), 영향, 제안, 우선순위, 비용(S/M/L), 수용 기준을 낸다.
- P0: 확인된 중대한 차단 문제. P1: 팀 도입 전 해결 또는 검증 필요. P2: 파일럿 후 개선. P3: 중장기 확장. 잠재 위험만으로 P0를 부여하지 않는다.
- 기능 확대보다 작은 팀 파일럿에서 확인할 가설과 측정 지표를 우선한다. 수치는 제안 목표이며 측정 결과로 쓰지 않는다.
- 보안 편의를 위해 승인이나 마스킹을 제거하지 않는다. 중복 질문 축소와 위험별 승인 묶음은 검토할 수 있다.
- 확장은 현 플러그인의 안정화와 별도 범용 코어 분리를 구분한다. 자동 게시, Jira 쓰기, 서버화, 웹 UI는 별도 권한·품질 조건을 제시한다.

## 최종 산출물

별도 종합 검토 문서에 역할별 평가, 근거 기반 개선 목록, 우선순위와 의존성, 단계별 확장 로드맵, 파일럿 측정 계획, 미확인 질문을 정리한다. 이번 컨텍스트 자체도 향후 재검토 시 재사용 가능하게 유지한다.

## 종합 후 재생성한 검토 초점 (v2)

사용자의 후속 지시에 따라 메인이 추가 승인 질문 없이 조사·우선순위·종합을 결정했다. 이 위임은 이번 분석 작업에 적용하며, 제품 사용자의 승인 절차를 없애는 요구로 해석하지 않는다.

- 독립 검토 완료: 사용자 경험, 운영·확장, 승인·보안. 메인이 실제 코드의 공통 근거와 분석 지표 정의를 교차 검토했다.
- 이미 있는 doctor, 검색, 상태 저장, 재분석, confidence 오해 방지, 정리, 배포 SHA, 품질 리뷰, 프롬프트 주입 주의문을 신규 기능처럼 다시 제안하지 않는다.
- 도입 전 초점: Jira 원문 격리 실제 동작, 서버 보호, PR 메타데이터까지 승인 결속, PR 없는 작업의 보존, 작업 경로 권한, 마스킹 예외, 복구·배포 명세.
- 제품 경험 초점: 능력별 준비 상태, 사용자용 상태/재개, 공유본 완성 검사, 검색 기준 시점, 후보 비교·다음 행동.
- 품질 초점: 정상 무후보와 증상 일치/원인 미확정을 분리한 평가, 오류를 포함한 완료율, 출처 manifest, 실제 로그에서의 슬롯 미식별 비율.
- 확장 순서: 도입 관문 → 제한된 파일럿 → 팀 운영 → 별도 범용 코어 → 필요한 경우 서버·UI·자동화. 기존 Runner의 전역 환경/stdout 변경을 동시 서버 실행에 그대로 가져가지 않는다.
- 전체 결과: [TEAM_PLUGIN_REVIEW_2026-10-07.md](TEAM_PLUGIN_REVIEW_2026-10-07.md). 정적 검토이며 사내 실행 및 공격 재현 결과로 인용하지 않는다.

## 토큰 비용 관점 추가 (v3)

후속 요청에 따라 기존 사용자·관리자·승인권자 검토를 토큰 효율과 함께 평가한다. 목표는 단일 응답 길이 최소화가 아니라 **안전하고 올바르게 완료한 작업당 비용·시간 절감**이다.

- 기존 최적화: 선택적 reference, 4KB 분석 요약, 검색 brief/Markdown, 검증 성공 상세 접기, 단계 통합 호출, 입력 재사용, 조건부 심층/탐색, 모델별 토큰·캐시·비용 평가를 먼저 인정한다.
- 토큰, UTF-8 바이트, CPU 실행시간, 모델 호출 수, 캐시 읽기/생성, 실제 비용을 구별한다. 캐시 적중이나 병렬 에이전트가 토큰 감소를 자동 보장하지 않는다.
- 절약 후보: 같은 결과의 JSON/Markdown 중복 읽기, 재분석 전체 재설명, 넓은 소스 열람, 문서의 반복 로딩, 전체 대화의 에이전트별 복제, 불필요한 심층 호출.
- 승인 근거·마스킹·실패/건너뜀·불확실성·중요 경고는 절약 대상에서 제외한다. 출력 축소에는 생략 메타정보와 상세 조회 경로를 요구한다.
- 기존 eval로 동일 모델·환경·입력의 변경 전후를 비교하고, 정상뿐 아니라 실패·재시도·중단 비용을 포함한다. 최신 가격이나 절감률을 추측하지 않는다.
- 상세 결과: [TEAM_PLUGIN_TOKEN_REVIEW_2026-10-07.md](TEAM_PLUGIN_TOKEN_REVIEW_2026-10-07.md).
