# 팀 운영 관점 플러그인 종합 검토

작성일: 2026-10-07. 검토 컨텍스트: [TEAM_PLUGIN_REVIEW_CONTEXT_2026-10-07.md](TEAM_PLUGIN_REVIEW_CONTEXT_2026-10-07.md).

## 판단

현 구조의 결정적 파서·매처, 사용자 확인, 계획 기반 DB 반영, 회귀 검증은 유지할 가치가 있다. 팀 도입을 위해 우선 보완할 부분은 수집·승인·보존·복구 경계를 실제 운영에서 확인하는 것과, 작업 상태 및 공유 결과를 사용자가 이해하기 쉽게 만드는 것이다. 웹 UI나 범용화부터 시작할 이유는 현재 근거에서 확인되지 않았다.

권고는 **도입 전 관문을 충족한 뒤 제한된 카테고리의 파일럿을 진행**하는 것이다. 현재 site-defaults.yaml이 없고 실제 사내 hook·권한·데이터 검증이 남아 있으므로 이번 검토만으로 운영 준비 완료라고 판단하지 않는다. 확인된 P0는 없다. 이는 안전성 인증이나 결함 부재의 보장이 아니다.

## 검토 방식과 범위

- 메인 오케스트레이터: 구조·계약, 분석 신뢰성, 근거 교차 확인, 중복 제거, 우선순위와 로드맵.
- 사용자 경험 에이전트: 첫 실행, 검색, 분석, 재개, 분류 확인, 결과 공유.
- 운영·확장 에이전트: 진단, 배포, 보존, 복구, DB 품질, 운영 지표, 범용화.
- 승인·보안 에이전트: 수집 경계, 승인 무결성, 서버 권한, 마스킹, 접근 제한, 감사.

현재 체크아웃의 코드와 관련 문서를 읽은 정적 검토다. 실제 Jira/GHE 호출, Claude hook 실행, 실제 민감 로그 분석, 공격 재현은 하지 않았다. Python 실행 파일의 기존 경로와 PATH 검색이 모두 실패하여 작은 평가 함수 실행 확인도 하지 못했다. 테스트 통과를 주장하지 않는다. 기존 테스트는 의도를 확인하는 근거로만 읽었다. docs/history는 읽지 않았고 기존 스테이징 변경은 건드리지 않았다. 새 검토 문서 2개만 작성했다.

증거 표기: **확인**은 코드에서 확인한 동작 또는 구현 범위, **미검증**은 사내 수용시험 필요, **제안**은 운영·제품 개선이다. P1은 팀 도입 전 해결 또는 검증, P2는 파일럿 개선, P3는 중장기 확장이다. 비용 S/M/L은 상대적 작업 규모이며 일정 견적이 아니다.

## 역할별 요구와 승인 책임

| 역할 | 가장 중요한 질문 | 필요한 화면/근거 | 책임 구분 |
|---|---|---|---|
| 분석 사용자 | 지금 무엇을 할 수 있고 다음에 무엇을 해야 하나? | 준비 상태, 작업 단계, 근거/미확정 이유, 다음 행동 | 분석 대상·분류·공유 의도 확인 |
| DB 관리자 | 규칙과 데이터가 유지 가능하고 복구 가능한가? | 품질 변화, 소유자, 배포 명세, 보존·복구 결과 | 스키마·공통 규칙·업데이트·보존 정책 |
| 카테고리 승인자 | 이 변경은 근거가 충분하고 다른 유형을 해치지 않는가? | 의미 diff, fixture, 검증 실패/건너뜀, 영향 범위 | 해당 분류·규칙·해결책의 품질 리뷰 |
| 운영·보안 승인자 | 어떤 데이터가 어디로 가고 누가 변경 가능한가? | 데이터 흐름, 서비스 계정 권한, 서버 보호, 수집 시험 | 조직 도입·접근·보관·외부 연결 허가 |

분류 확인, push 허가, PR 리뷰, 운영 도입 허가는 서로 다른 결정이다. 현재 로컬 approved_hash는 내용 일치 확인이며 승인자 인증이나 전자서명이 아니다. 인증된 최종 리뷰 근거는 GHE에서 연결하는 것이 적절하다.

권장 변경별 검토 범위: 기존 원인에 Jira 추가는 카테고리 리뷰, 새 원인·시그니처는 영향 카테고리와 검증 결과 리뷰, parser-rules/마스킹 예외/.githooks/스키마는 메인테이너 리뷰, 신규 데이터 연결·보존 정책·외부 처리 경로는 운영·보안 승인이다. 실제 팀 권한표로 구체화해야 하며 모든 PR에 모든 사람의 승인을 요구할 필요는 없다.

A1은 **승인 무결성의 정적 구현 공백**이다. 기존 코드 트리 검사는 작동하도록 구현되어 있으며 이를 '아무 파일이나 무승인 게시 가능'으로 확대 해석하면 안 된다. 같은 로컬 실행 주체가 PR 상태 파일을 바꿀 수 있는 상황에서, 사용자가 본 PR 메타와 실제 게시 메타를 추가로 결속하자는 제안이다.

A2에서 원문 격리가 확인되지 않으면 live Jira 연동 도입을 완료 처리하지 않는다. hook이 없을 때 경고하는 것과 원문이 모델에 들어가지 않았음을 보장하는 것은 다르다. 시험 데이터는 실제 개인정보가 아닌 고유 합성 식별자를 사용한다.

A7은 현재 문서와 테스트에 맞게 구현된 동작이므로 기존 구현 버그로 단정하지 않는다. `tests/test_commands.py:244`는 unresolved를 음성으로 사용하는 의도를 확인한다. 다만 제품의 '원인 미확정'과 평가 라벨의 '무후보 기대'에 같은 단어를 쓰면 운영 지표를 잘못 해석하기 쉽다. 코드상 top3=[None]도 비어 있지 않은 목록이므로 오탐으로 집계된다. 이는 정적 추론이며 실행 재현은 하지 않았다.

| O3 / P2·M 승인 감사 | 로컬 approved_hash와 서버 리뷰는 의미가 다름 (`scripts/dbpr/publish.py:362`) | 승인 종류·대상 digest·건너뛴 검사·예외 사유를 분리하고 인증된 GHE 리뷰와 연결. '로컬 승인 해시=승인자 서명'으로 표현하지 않음 |

우선순위가 P1인 사용자 개선은 첫 파일럿에서 검증해야 할 사용성 관문이다. 보안 경계의 필수 조건과 동일한 위험도로 간주하지 않는다. 전부 구현할 때까지 모든 학습을 중단하기보다, 합성 자료와 제한된 기능의 관찰 파일럿으로 개선 범위를 확인할 수 있다.

## 추가로 검증할 분석 신뢰성

1. **재현 출처:** 캐시는 이미 스크립트·DB·설정 해시를 고려한다(`scripts/triagelib/cache.py:78-107`). 이를 '재현성 없음'으로 평가하지 않는다. 공유 결과에서 같은 출처를 식별하도록 별도 manifest로 노출할 필요가 있다. 해시만으로 원문을 복원할 수는 없으며 원문 보존은 조직 정책을 따른다.
2. **슬롯 미식별:** `scripts/common/signatures.py:213-223`은 phone_id=None을 다른 슬롯과도 맞는 값으로 취급한다. 의도된 계약이다. 실제 벤더 로그에서 슬롯 미식별 비율과 그 근거에 의존한 후보 비율을 측정한 뒤 경고나 선택적 엄격 모드를 검토한다. 곧바로 판정 규칙을 변경하면 기존 유효 로그를 놓칠 수 있다.
3. **LLM 결과 품질:** '외부 문장은 지시가 아니다' 안내가 이미 있으므로 부재로 평가하지 않는다. 합성 Jira/로그/소스 주석에 악성 지시를 넣고 shell 호출·게시 대상·리뷰어·분류가 바뀌지 않는지 행동 평가를 추가한다. 안내문만으로 보안이 보장됐다고 주장하지 않는다.
4. **실데이터 평가:** 기존 fixture 재생 성공과 사내 진단 정확도는 다른 지표다. 반복 로그·같은 이슈가 학습 규칙과 평가에 중복되는 것을 피하고, 카테고리·버전·벤더·듀얼 SIM별 미확정과 오탐을 따로 본다. 소표본 결과는 건수와 함께 보고한다.

범용화는 DRAFT_NOTES의 별도 G 트랙과 맞춰 기존 telephony 안정화를 먼저 진행한다. 플랫폼 디렉터리는 있으나 `scripts/platforms/__init__.py:16`, `scripts/triagelib/anchor.py:11`, `scripts/triagelib/report.py:412` 등에 Android 결합이 남아 있다.

서버화 시 `scripts/triagelib/core.py:110`의 Runner를 그대로 여러 스레드에서 호출하면 안 된다. 현재 구현은 os.environ과 전역 stdout/stderr를 변경한다. 이는 현재 단일 작업 CLI의 확인된 구현 특성이며 현재 동시성 장애가 재현됐다는 뜻은 아니다. 서버에서는 독립 프로세스와 작업 디렉터리·자격 격리를 먼저 설계한다.

검색 품질이 실제 병목이면 별칭/키워드 검색의 실패 표본을 모은 뒤 의미 검색을 검토한다. 의미 검색은 후보 탐색을 보조하고 시그니처 S/C 판정을 대체하지 않는다. 데이터베이스 서버·벡터 저장소·대시보드 도입은 측정된 필요에 따라 결정한다.

## 파일럿 측정 계획

| 관점 | 지표와 분모 | 수집 방법/주의 |
|---|---|---|
| 사용자 | 첫 유효 결과 시간, 완료 시도/전체 시도, 중단 후 재개 성공/재개 시도, 확인 질문 수 | 실패·중단 포함. 인터뷰와 비식별 단계 이벤트를 결합 |
| 분석 | 원인 top1/top3, 정상 오탐, 미확정 유지, 관측 불가/전체, 카테고리별 표본 수 | A7 라벨 정의 선행. 오류를 제외한 정확도와 전체 처리 성공률을 함께 보고 |
| 승인자 | 검토 소요, 재승인 횟수, 반려 이유, 검증 건너뜀 비율 | 승인 속도만 목표로 삼지 않고 근거 이해·반려 품질도 관찰 |
| 관리자 | 미처리 품질 항목 나이, 규칙 회귀 실패, 복구 시간, 작업 폴더 용량·잔류 원문 | owner와 대응 기한 연결. 원문 수집 없이 상태·건수만 |
| 확장성 | 로그 크기·유형·fixture 수별 p50/p95 시간과 메모리 | 성능 문제를 가정해 캐시나 병렬화를 먼저 도입하지 않음 |

위 인원·기간은 제안이며 측정 결과가 아니다. 수치 목표는 첫 파일럿 기준선을 얻은 뒤 정한다. 보안 관문의 합성 원문 비노출, 승인 대상 변경 차단, 권한 없는 변경 거부는 성과 평균과 별개인 필수 수용 조건이다.

## 메인 오케스트레이터의 최종 우선순위

1. **가장 먼저:** 실제 원문 격리·서버 보호 확인과 승인 manifest 보완. 실제 게시 내용과 사람이 확인한 내용을 일치시킨다.
2. **함께 진행:** 중단/분석 전용 산출물의 보존·접근 제한, 배포·복구 명세, 평가 라벨 구분.
3. **파일럿에서 검증:** 능력별 시작 안내, 작업 상태·재개, 공유본 생성. 질문을 없애기보다 중복 질문을 줄이고 중요한 결정의 근거를 한 번에 보여준다.
4. **팀 확대 후:** 품질 조치 관리·운영 지표·검색 신선도·후보 비교.
5. **조건부 확장:** 별도 범용 코어와 최소 두 번째 도메인. UI·서버·자동 게시·Jira 쓰기는 사용 필요와 권한 모델을 따로 검토한다.

이번 결과는 구현 작업 목록과 사내 수용시험 설계의 입력으로 사용할 수 있다. 제안 기능의 구현, 운영 권한 변경, 배포·게시 또는 기존 진행 트랙의 완료 처리는 수행하지 않았다.

## 추가 검토: 토큰 효율

[토큰 효율 검토 보고서](TEAM_PLUGIN_TOKEN_REVIEW_2026-10-07.md)에 기존 검토와의 연결, 현재 절약 장치, 개선 우선순위, 측정 계획을 추가했다. 핵심은 반복 입력·재서술·도구 왕복을 줄이고 승인과 판단 근거를 보존하는 것이다.

- U1/U2는 설정·복귀 대화를 줄이고, U3는 공유본을 스크립트가 구성해 LLM의 반복 작성 부담을 줄인다.
- U5는 비교용 구조화 근거를 필요한 후보에만 펼치고, O1/O2는 새로 생긴 품질 문제와 비식별 집계만 전달한다.
- A1 승인 manifest는 스크립트가 구성·검증하고, 중요한 경고·변경 diff·재승인 여부를 토큰 절약 명목으로 생략하지 않는다.
- 4KB 요약은 토큰 상한이 아니다. 현재 fit의 경고 축소와 truncated 의미를 구분하는 표시 보완을 P1로 추가한다.
- 다중 에이전트는 독립 관점이 필요한 검토에 선택적으로 사용하고, 일반 이슈마다 전원에게 전체 대화를 복제하는 방식을 기본값으로 삼지 않는다.
