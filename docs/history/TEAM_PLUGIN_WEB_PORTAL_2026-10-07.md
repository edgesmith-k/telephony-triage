# 웹 기반 팀 이슈 분석 포털 제안

작성일: 2026-10-07. 사용자 제안: 웹에서 Jira 번호, 실패 단계 또는 증상을 입력하고 로그를 첨부하면 원인과 근거를 분석한다.

관련 문서: [팀 운영 검토](TEAM_PLUGIN_REVIEW_2026-10-07.md), [토큰 효율 검토](TEAM_PLUGIN_TOKEN_REVIEW_2026-10-07.md), [확장 아이디어](TEAM_PLUGIN_EXPANSION_IDEAS_2026-10-07.md).

이 문서는 제품·구조 제안이다. 웹 서버 구현, 서비스 연결, 배포 또는 운영 승인을 완료했다는 의미는 아니다.

## 목적과 사용자 흐름

현재 플러그인의 분석 엔진을 브라우저에서 사용할 수 있게 한다. 사용자가 각자 Claude·Python·Git을 설치하고 명령을 익히는 부담을 줄인다.

```text
사내 로그인
    ↓
Jira 번호 + 실패 단계/증상 + 로그 첨부
    ↓
접근 권한·입력 검사 → Jira 읽기 조회
    ↓
로그 마스킹·파싱 → 기존 이슈 DB 시그니처 매칭
    ↓
필요한 경우 AI 심층 분석·코드 근거 조사
    ↓
원인 후보 + 근거 + 해결책 + 다음 확인 사항
    ↓
사용자 분류 확인 → DB 등록 요청 → 담당자 리뷰 → PR 반영
```

원인을 항상 확정할 수 있는 서비스로 표현하지 않는다. 결과는 규칙 일치, 로그로 확인한 사실, 코드 기반 추정, 원인 미확정, 관측 불가를 구분한다. 근거가 부족하면 필요한 추가 로그와 재현 조건을 안내한다.

## 입력과 결과 화면

입력:

- Jira 번호: 서버에서 사용자의 조회 권한을 확인하고 필요한 필드만 읽는다.
- 실패 단계 또는 증상: Jira에서 얻은 정보와 사용자의 추가 설명을 함께 표시한다.
- 로그 첨부: 지원 형식, 크기, 개수, 보존 정책을 안내한다.
- 선택 정보: 발생 시각, 타임존, 빌드, SIM 슬롯, 시험 장비와 단말의 시계 차.

결과:

- 분석 상태와 실제 분석 범위, 입력 부족·파서 경고.
- 상위 원인 후보와 규칙 일치 수준. 점수를 원인 확률로 표현하지 않는다.
- 후보별 마스킹 근거 로그, 코드 참조, 반대 근거, 적용 조건.
- 해결책과 검증 상태, 관련 이슈. 조회 권한이 없는 정보는 노출하지 않는다.
- 다음 확인 사항과 추가 로그 재분석 기능.
- 분석 출처: DB SHA, 엔진·파서 식별값, 입력 digest, 생성 시각.
- 분석 결과와 DB 등록 상태를 분리해 표시한다.

## 재사용과 신규 개발 범위

| 현재 기능 | 웹에서 추가·변경할 부분 |
|---|---|
| parse_logcat, 마스킹, match_signatures | 업로드 검사·저장·작업별 파일 격리 |
| Jira 필드 추출 | 서버용 읽기 전용 Jira 연동과 사용자 접근 검사 |
| triagelib의 분석 순서·상태·리포트 | 웹 작업 상태, 질문/답변 API, 취소·재시도 |
| DB 검색·규칙·fixture 검증 | 분석 작업별 DB 스냅샷 버전 고정 |
| plan.json, db_add, db_pr | 등록 요청과 승인 화면, 서버 작업 주체·자격 설계 |
| 품질 리뷰·통계 | 관리자용 작업·용량·실패·품질 현황 |

Python 엔진만 웹 서버에 올린다고 Claude 스킬이 담당하는 코드 조사·사용자 질문·자연어 설명까지 자동 제공되는 것은 아니다. Markdown 스킬의 절차를 웹 상태 전이와 모델 호출로 연결하는 오케스트레이터가 필요하다. 결정적 판정과 LLM 설명의 분리는 유지한다.

## 권장 구성

```text
브라우저
   ↓
웹/API 서버 ── 인증·권한 검사
   ├─ 작업 상태 저장소
   ├─ 업로드/결과 저장소
   └─ 작업 큐
          ↓
      분석 워커 (작업별 독립 프로세스)
          ├─ Jira 읽기 연동
          ├─ 버전이 고정된 이슈 DB 스냅샷
          ├─ 파싱·마스킹·매칭·검증
          └─ 선택적 모델 호출

DB 등록 요청 → 승인 처리 → 별도 쓰기 작업 → PR
```

첫 배포는 한 서버에서 웹/API·큐·워커를 운영해도 된다. 장시간 분석을 HTTP 요청 처리 안에서 끝내려 하지 않고 비동기 작업으로 분리한다. 초기부터 복잡한 분산 서비스나 별도 벡터 DB가 필요한 것은 아니다.

현재 `plugin/scripts/triagelib/core.py`의 Runner는 같은 프로세스에서 CLI를 호출하면서 환경변수와 stdout/stderr를 변경한다. 여러 사용자 작업을 스레드로 동시에 실행하는 데 그대로 사용하지 않는다. 작업별 프로세스·환경·디렉터리를 분리하고, 기존 사용자별 단일 작업 lock을 서버의 작업/DB 쓰기 동시성 정책에 맞게 검토한다.

작업 상태 예시: queued → preparing → parsing → matching → awaiting_input 또는 explaining → completed. failed/cancelled도 별도 상태다. DB 등록은 draft → awaiting_approval → publishing → published로 분리한다. 이 명칭은 제안이며 기존 CLI 출력과 매핑 계약을 정의해야 한다.

## 첫 버전 범위

1. 사내 로그인과 사용자별 작업 목록.
2. Jira 번호·실패 단계·증상·로그 입력.
3. 비동기 분석, 진행 상태와 입력 보완 질문.
4. 원인 후보·근거·해결책·미확정 이유 표시.
5. 추가 로그를 첨부한 재분석.
6. 결과 저장과 권한을 확인하는 링크 공유.
7. 분석 결과에서 별도 DB 등록 요청 생성, 담당자 리뷰와 PR 연결.

개발 순서는 읽기 전용 분석 포털을 먼저 검증한 뒤 등록 요청·PR 경로를 연결하는 것이 적절하다. 자동 원인 확정, 자동 main 반영, Jira 쓰기, 장비 제어는 첫 버전에 포함하지 않는다.

## 서버화에서 먼저 정할 경계

| 영역 | 필요한 정책·검증 |
|---|---|
| Jira 권한 | 서버 계정의 조회 범위를 모든 사용자에게 그대로 노출하지 않는다. 사용자 위임 또는 서버 측 접근 검증 방식을 정한다 |
| 결과 권한 | 작업·첨부·결과·공유 링크마다 접근 검사. DB의 관련 사례도 원래 공유 가능 범위 확인 |
| 원문 처리 | 원문은 제한된 저장소에서만 처리하고 모델에는 마스킹된 필요 구간만 전달. 정상·오류·취소 경로의 삭제/보존 정책 |
| 업로드 | 파일 크기·개수·압축 해제량·형식 제한, 경로 탈출 검사, 사용자 파일명 대신 서버 생성 저장 경로 |
| 실행 격리 | 작업별 프로세스·디렉터리, 시간·메모리·CPU 제한. 외부 파서 명령은 사용자 입력으로 임의 지정하지 않음 |
| 쓰기 권한 | 분석 워커와 게시 주체를 구분. 승인 manifest와 실제 게시 내용 일치 검사. 서버 측 브랜치 보호 유지 |
| 감사·복구 | 요청자·분석 버전·승인 종류·게시 결과 기록. 민감 원문을 감사 로그에 복제하지 않음 |

로컬 Claude hook은 웹 요청을 보호하지 않는다. 기존 guard의 안전 의도는 API 권한 검사·업로드 검사·게시 서비스·서버 Git 보호로 옮겨야 한다. 모든 통제를 프롬프트에만 맡기지 않는다.

## 토큰 비용 설계

- 파싱·마스킹·시그니처 매칭·집계는 Python으로 수행한다.
- 알려진 원인은 구조화 결과와 템플릿으로 리포트를 만들고, LLM 설명은 선택적으로 사용한다.
- 미확정·근거 충돌 등 필요한 작업에만 심층 분석을 실행한다. 추가 비용이 드는 단계는 사용자에게 상태와 범위를 표시한다.
- 모델 입력은 전체 로그나 전체 DB 대신 마스킹된 근거·상위 후보·관련 코드 발췌로 제한한다.
- 재분석 시 전체 결과는 저장하되 모델에는 변경 근거와 필요한 이전 요약을 전달한다.
- 결과 재사용은 입력·설정·엔진·DB 버전을 포함해 판단한다. 사용자 간 캐시는 권한 격리가 입증되기 전 공유하지 않는다.
- 사용자/작업별 비용과 심층 호출 수를 측정한다. 예산 초과 시 미완료를 명시하고 필수 검증을 생략하지 않는다.

웹 포털이 그 자체로 토큰을 절약하는 것은 아니다. 구조화된 입력과 결과, 재사용, 조건부 모델 호출을 구현했을 때 절약 가능성이 생긴다. 실제 효과는 완료율·정확도와 작업당 비용을 함께 측정한다.

## 파일럿과 우선순위 판단

제안 파일럿: 제한된 사용자와 1~2개 카테고리에서 합성 자료로 격리·권한·실패 처리를 먼저 확인하고, 승인된 사내 데이터로 분석 품질을 평가한다.

필수 수용 사례: 다른 사용자의 첨부/결과 접근 거부, 권한 없는 Jira 조회 거부, 원문 모델 비노출, 두 작업 동시 실행 시 파일/상태 혼입 없음, 취소·재시도 시 중복 게시 없음, 불충분 로그의 판단 유보, 보존 기간 경과 작업 정리.

성과 지표: 첫 분석 완료까지 시간, 설치/지원 요청 감소, 분석 완료·재개 성공률, 원인 정확도·미확정률, 사람의 검토 시간, 올바른 완료 1건당 비용, 작업 대기시간.

팀원들이 로컬 설치와 명령 사용을 부담스러워한다면 **별도 범용 코어 분리보다 이 포털을 먼저 추진할 가치가 있다.** 현재 엔진을 활용해 실제 팀 사용성을 검증할 수 있기 때문이다. 반대로 사용자 수가 적고 CLI 작업이 원활하다면 서버 운영·접근 통제 비용과 비교해야 한다. 초기 포털은 telephony 범위를 유지하고, 여러 도메인 지원은 별도 검증 후 확장한다.
