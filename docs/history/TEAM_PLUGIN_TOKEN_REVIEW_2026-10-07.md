# 토큰 효율 관점 추가 검토

작성일: 2026-10-07. [팀 운영 종합 검토](TEAM_PLUGIN_REVIEW_2026-10-07.md)와 [검토 컨텍스트](TEAM_PLUGIN_REVIEW_CONTEXT_2026-10-07.md)의 후속이다. 메인 오케스트레이터가 출력·캐시·평가 코드를 검토하고, 별도 에이전트가 스킬·명령·문서 흐름을 독립 검토했다. 런타임 코드 변경이나 유료 행동 평가는 실행하지 않았다.

## 결론

이미 토큰 절약이 상당 부분 설계되어 있다. 추가 개선은 무조건 더 짧은 스킬이나 더 작은 JSON보다 **같은 내용을 반복 읽고 다시 쓰는 과정, 반복 질문, 넓은 근거 탐색, 전체 맥락 복제**에 집중하는 것이 적절하다. 실제 절감률은 측정 전 확정할 수 없다.

최적화 목표는 다음 두 지표를 함께 개선하는 것이다.

- 시도당 토큰·비용·시간: 실패와 중단도 포함한다.
- 올바른 완료 1건당 비용: 전체 시도 비용 / 안전·정확성 기준을 통과한 완료 건수. 완료가 0이면 값을 산출하지 않는다.

문서를 너무 줄여 재시도나 잘못된 계획이 늘면 전체 비용은 악화할 수 있다. 인간의 검토 시간도 함께 본다.

## 기존 팀 운영 제안과 연결

| 기존 항목 | 토큰을 줄이는 방식 | 유지해야 할 것 |
|---|---|---|
| U1 능력별 시작 안내 | 기본값 표 한 번, 누락만 질문 | Jira 읽기 도구 매핑·접근 허용 확인 |
| U2 작업 상태·재개 | 전체 대화 복원 대신 상태 요약·다음 행동 | owner 인계, 승인 당시 내용 변경 확인 |
| U3 공유 리포트 | 템플릿·manifest는 스크립트 생성, LLM은 설명 슬롯만 | 초안 표시·사실/추정·출처·마스킹 검사 |
| U5 후보 비교 | 전체 type 문서 대신 필요한 후보 필드/근거만 | 반대 근거·미확정과 다른 후보를 감추지 않음 |
| O1 품질 조치 | 전체 월간 보고서 재독 대신 신규·악화·해결 변화 | 유예 만료·장기 미처리·담당자 부재 |
| O2 운영 지표 | 원문 trace 대신 허용 필드의 집계표 | 실패·중단도 분모에 포함 |
| A1 승인 manifest | manifest/hash는 Python이 생성·검사, 화면 반복 작성 제거 | 승인 전 확인 화면·중요 diff·실패/건너뜀·변경 시 재승인 |

승인 화면은 이미 주요 diff가 길면 요약과 전체 diff 선택지를 제공한다(`reference/write-flow.md:78` 부근). 이를 다시 'diff 요약 신설'로 제안하지 않는다. 절약은 같은 승인 화면을 LLM이 여러 번 새로 만드는 일을 줄이는 데 적용한다.

## 계측과 비교 방법

기존 평가기를 확장해 사용한다. 별도 토큰 측정 시스템을 처음부터 만들 필요는 없다.

1. 대표 경로를 분리한다: 검색, 알려진 원인 분석, 원인 미확정, 새 원인/규칙, 수동 기록, 수정 검증, 재분석, 재개, drift, 검사 실패, setup.
2. 동일 모델 식별자·플러그인 코드·site 설정·DB/fixture·사용자 답변·캐시 조건을 고정하고 변경 전후를 비교한다. cold와 warm, 분석 캐시 hit와 miss를 구분한다.
3. 모델별 input/output/cache_creation/cache_read, 실제 기록 비용, 턴, 도구 호출, 중복 읽기, wall time, 완료/안전 평가를 함께 기록한다. UTF-8 바이트 수는 별도 보조 지표다.
4. 자식 에이전트 사용량을 포함하는 현재 modelUsage 합산을 유지하고 상위 usage만으로 절감했다고 판단하지 않는다. 값이 없으면 미기록으로 둔다.
5. 비용·토큰 비교는 성공 경로만 골라내지 않는다. 중단·형식 오류·재시도와 그 비용을 포함하고 올바른 완료율이 떨어지지 않는지 확인한다.
6. 관련 시나리오부터 최소 반복으로 측정하되 대표 정상/실패 경로는 반복 편차를 확인한다. 기존 기준선 상한은 회귀 감지용으로 유지하고, 최적화 효과는 반복 결과의 중앙값·범위 및 품질로 판단한다.

`tests/skill_evals/token_baseline.json`은 2026-10-06의 과거 저장 기록이고 dirty:true이며 현재 체크아웃 측정값이 아니다. 이 파일의 eval 1 기록에는 712,767 total에 약 $0.444, 743,146 total에 약 $0.408이 함께 있다. 총토큰이 더 많아도 기록 비용이 더 낮은 사례가 있으므로 총토큰 하나만 비용 대리값으로 삼지 않는다. 이 차이의 원인을 캐시만으로 단정하지 않으며 최신 요금·현재 예상 비용으로 사용하지 않는다. total은 누적 처리량이며 한 번의 컨텍스트 크기가 아니다.

저장된 기본 상한 여유율 1.3은 기존 실험의 회귀 감지 정책이다. 이를 절감 목표나 모든 경로에 보장되는 변동 폭으로 취급하지 않는다. 먼저 현재 버전의 기준선을 갱신해야 한다.

## 추천 실행 순서

1. **출력 축소 계약(T0)과 현재 기준선 확인:** 안전 정보·생략 표시를 먼저 고정한다.
2. **작은 연결 변경(T1)과 중복 Read 감지:** 기존 렌더러·통합 호출을 더 잘 사용한다.
3. **입력 단일화(T2), 변경분 전달(T3):** 같은 정보를 매 턴 재입력·재설명하지 않는다.
4. **근거 패킷(T4), 상태·공유본(U2/U3):** 읽기와 최종 작성의 범위를 좁힌다.
5. **조건부 심층/에이전트(T5/T6):** 비용 대비 도움이 입증된 상황에서만 확장한다.

스킬의 필수 규칙을 난해한 약어로 압축하거나 마스킹·회귀·승인·실패 근거를 빼는 방식은 권하지 않는다. 실제 모델별 프롬프트 캐시 적중은 런타임 기록으로 확인하며, 문서 배치를 바꿨다는 이유만으로 적중을 보장하지 않는다.

상태를 먼저 확인한 뒤 판정하는 `reference/verify.md`의 호출 분리처럼, 의미상 의존성이 있는 단계는 왕복 수만 줄이려고 합치지 않는다. 검색 Markdown 연결도 terms 등 스킬 분기에 필요한 정보가 남는지 확인한 뒤 적용한다.
