# 현재 기능을 기반으로 한 확장 아이디어

작성일: 2026-10-07. [운영 검토](TEAM_PLUGIN_REVIEW_2026-10-07.md), [토큰 검토](TEAM_PLUGIN_TOKEN_REVIEW_2026-10-07.md)를 함께 적용한다. 아래는 현재 저장소에서 도출한 제품 가설이며 시장 수요 조사나 구현 완료 기능이 아니다. 상대 규모 S/M/L과 LLM 부담 낮음/중간/높음은 비교용 추정으로 실측 비용이 아니다.

## 추천 방향

팀의 이슈 지식을 단순히 저장하는 데서 **새 문제에 재사용하고, 수정 효과를 확인하고, 검토할 일을 줄이는 도구**로 확장하는 것이 자연스럽다. 현재의 결정적 분석과 검증을 그대로 활용하는 기능부터 시작하면 구현 위험과 토큰 부담을 함께 줄일 수 있다.

## 1. 팀 주간 브리핑과 변화 알림

- 대상/가치: 팀장·카테고리 오너가 이번 주 새 원인, 재발, 검증 대기, 품질 부채를 한 장으로 파악한다.
- 기존 기반: db_review, db_build의 통계와 품질 판정. 신규 부분은 직전 보고와의 차이, 담당자·기한·조치 연결이다.
- 최소 구현: 두 기준일/DB SHA 간 변화와 상위 조치 5개를 Markdown으로 생성. 검증됨/미검증을 분리한다.
- 규모/토큰: S~M / 낮음. 집계·순위·본문 템플릿은 Python, LLM은 선택적 짧은 설명만.
- 조건/지표: 급증을 단말 장애율로 오해하지 않도록 DB 등록 건수임을 표시. 이메일·Slack 자동 전송은 별도 연결과 권한 조건. 보고 작성 시간과 기한 내 조치율 측정.

## 2. 수정 전후 비교 리포트

- 대상/가치: 개발자·QA가 같은 시나리오의 수정 전/후 로그에서 무엇이 달라졌는지 확인한다.
- 기존 기반: parse_logcat, match_signatures, db_verify fix/resolution, 근거 line_ref. 신규 부분은 두 실행을 하나의 비교 화면으로 연결하는 것이다.
- 최소 구현: 전/후 이벤트·S/C·시나리오 흔적·빌드·슬롯·관측 구간 비교와 기존 verify-fix 판정을 함께 표시.
- 규모/토큰: M / 낮음~중간. 이벤트 diff와 판정은 Python, 의미 설명은 필요할 때만.
- 조건/지표: 다른 시나리오나 불충분한 구간이면 '비교 불충분'. 단순 로그 감소를 수정 성공으로 처리하지 않음. 검토 시간과 비교 불충분 감지율 측정.

## 3. 승인자용 검토 패킷

- 대상/가치: 승인자가 긴 PR 전체에서 중요한 변경과 위험을 찾아내는 시간을 줄인다.
- 기존 기반: db_summary, rules 검증, semantic rule diff, 승인 해시. 기존 승인 화면을 대체하기보다 리뷰어 관점의 영향·누락·예외를 모은다.
- 최소 구현: 변경 목적, 영향 유형, 기존 이벤트 변화, 실패/건너뜀, 새 예외, 필요한 리뷰어를 정적 생성하고 전체 diff 링크를 연결.
- 규모/토큰: S~M / 낮음. 대부분 기존 결과의 재조합이며 LLM 검토는 상충·고위험 변경에 한정.
- 조건/지표: 승인 manifest 보완(A1) 선행. 자동 승인하지 않음. 리뷰 소요·누락 지적·재검토 횟수 측정.

## 4. 증상 기반 진단 안내

- 대상/가치: 비전문가가 '데이터가 안 붙는다'고 입력하면 필요한 로그와 다음 확인 순서를 안내받는다.
- 기존 기반: search, failed_step, 분석 구간, 관측 경고, 미확정 후보. 신규 부분은 상태 기반 질문·수집 체크리스트다.
- 최소 구현: 한 카테고리에서 로그 없음/시각 불명/범위 밖/원인 미확정을 구별하고 다음 확인 1~3개를 제공.
- 규모/토큰: M / 낮음~중간. 상태 전이는 규칙으로, 자유문 해석에만 LLM 사용.
- 조건/지표: 확인 전 단말 설정 변경이나 장비 제어 금지. 필요한 정보만 요청. 첫 유효 분석까지 시간·반복 질문 수·잘못된 수집 요청 비율 측정.

## 5. 알려진 이슈 재사용 카드

- 대상/가치: 팀원이 유사 이슈를 발견했을 때 적용 조건과 검증된 해결 방법을 빠르게 가져간다.
- 기존 기반: 자연어 검색·별칭·related·코드 참조·해결 검증 상태. 신규 부분은 검색 결과를 적용 가능 조건 중심의 카드로 정리하는 것이다.
- 최소 구현: 증상, 적용 버전/조건, 배제 조건, 근거, 해결 상태, 마지막 확인 시점과 관련 Jira를 한 카드로 생성.
- 규모/토큰: S~M / 낮음. 초기는 키워드 검색+정적 렌더, 의미 검색은 실패 표본을 모은 뒤 평가.
- 조건/지표: 텍스트 유사성을 동일 원인 확정으로 쓰지 않음. 오래된/미검증 카드 명시. 해결책 재사용률과 잘못된 적용 비율 측정.

## 6. 규칙 보강 후보 수집과 초안

- 대상/가치: 관리자가 반복되는 미확정 사례 중 어떤 규칙을 먼저 보강할지 고른다.
- 기존 기반: unresolved, pending_causes, feedback, new-cause/new-type 계획, fixture 검증.
- 최소 구현: 마스킹된 이벤트 패턴·증상으로 미확정 묶음 후보를 생성하고 대표 사례·반례를 제시. 선택된 묶음에만 시그니처/fixture 초안을 만든다.
- 규모/토큰: M~L / 중간~높음. 전체 DB를 매번 LLM으로 군집화하지 않고 규칙 기반 후보 축소 후 선택 호출.
- 조건/지표: 빈도는 원인 증명이 아님. 사람의 의미 확정·음성/교차 회귀·홀드아웃 평가 후 PR. 자동 학습/자동 main 반영 금지. 초안 채택률·오탐·미확정 감소 측정.

## 7. 재현·검증 로그 수집 계획

- 대상/가치: QA가 '무엇을 재현하고 어떤 흔적을 확보해야 수정 확인이 가능한가'를 사전에 안다.
- 기존 기반: scenario/recovery signatures, failed_step/step_events, verify-fix의 unknown/partial 판정.
- 최소 구현: 특정 원인에 대해 필요한 시나리오 흔적·슬롯·빌드·로그 구간·누락 태그를 체크리스트로 생성.
- 규모/토큰: M / 낮음. 구조화된 검증 조건에서 생성하고 자연어 단계 초안만 선택적 LLM.
- 조건/지표: 기존 시그니처에 맞춰 시험을 과도하게 좁히지 않고 독립적인 정상/음성 시나리오도 포함. 장비 자동 제어는 별도 범위. 로그 부족으로 재시험한 비율 측정.

## 8. 신입 교육·사례 훈련 모드

- 대상/가치: 신입·타 분야 팀원이 근거를 읽고 원인과 추정을 구분하는 방법을 배운다.
- 기존 기반: 합성 fixtures, 기대값, 마스킹, log-tags/RIL 설명, 회귀 도구.
- 최소 구현: 합성 사례를 제시하고 사용자가 고른 원인·근거를 정답 규칙과 비교. 설명의 부족한 부분만 피드백.
- 규모/토큰: M / 낮음~중간. 채점은 결정적, 맞춤 설명에만 LLM.
- 조건/지표: 교육 workspace는 운영 DB·자격과 분리. 합성 태그를 실제 환경 사실로 가르치지 않음. 전후 평가·전문가 도움 요청 빈도 측정.

## 9. 빌드·릴리스별 검증 현황판

- 대상/가치: 릴리스 담당자가 어떤 수정은 확인됐고 어떤 위험은 아직 관측되지 않았는지 파악한다.
- 기존 기반: fix.status, fixed_in, verification_history, DB 품질 통계.
- 최소 구현: 빌드별 원인 목록, 검증 완료/실패/부분/미확인, 적용 버전과 근거 링크를 정적 보고서로 생성.
- 규모/토큰: M / 낮음. 집계는 Python; 웹 UI는 필요가 확인된 뒤 동일 출력 위에 구성.
- 조건/지표: '등록된 이슈의 검증 현황'이며 전체 제품 출시 안전성 판정이 아님. DB 누락·빌드 비교 불가를 표시. 검증 공백 발견·릴리스 회의 준비 시간 측정.

## 10. 범용 팀 이슈 분석 코어와 도메인 팩

- 대상/가치: Wi-Fi·Bluetooth·앱 크래시·서버 운영 등 다른 팀이 동일한 지식 축적·검증·PR 흐름을 사용한다. 이 도메인들은 후보이며 지원 완료 기능이 아니다.
- 기존 기반: 이벤트 인터페이스, 시그니처, Git 이슈 모델, 변경 계획, 검증, 승인 흐름.
- 최소 구현: 별도 저장소에서 비Android 합성 예제 팩 1개를 끝까지 실행. 도메인 팩에 파서/이벤트/카테고리/스키마 제약/근거 해설을 둔다.
- 규모/토큰: L / 작업에 따라 다름. 활성 도메인의 계약·규칙만 로딩해 모든 도메인 지식을 대화에 넣지 않는다.
- 조건/지표: Android 직접 import·고정 문구를 경계 밖으로 이동, 기존 회귀 보존. 코드 실행 가능한 어댑터는 단순 데이터 규칙보다 강한 배포 검토 필요. 두 번째 도메인 추가 시 코어 변경량으로 분리 품질 평가.

## 우선순위 선택

| 순서 | 묶음 | 이유 |
|---|---|---|
| 먼저 | 1 주간 브리핑 + 3 승인 패킷 | 기존 집계·검증 결과를 재사용하고 사용자/관리자/승인자의 시간을 함께 줄임. LLM 부담 낮음 |
| 다음 | 2 전후 비교 + 7 수집 계획 | 실제 원인 확인·수정 검증의 반복 작업과 불충분 로그 재수집 감소 |
| 파일럿 반응에 따라 | 4 진단 안내 + 5 재사용 카드 + 8 교육 | 초보자 접근성과 지식 재사용을 개선. 상태/리포트 계약을 먼저 안정화 |
| 데이터 축적 후 | 6 규칙 보강 후보 + 9 검증 현황판 | 충분한 사례·정확한 검증 메타·소유자 운영 필요 |
| 별도 트랙 | 10 범용 코어 | 현재 telephony 안정화와 분리. 두 번째 최소 도메인으로 경계 검증 |

한 번에 모두 구현하지 않는다. 첫 묶음은 읽기 전용·정적 결과 생성으로 시작하고 자동 전송·승인·설정 변경은 붙이지 않는다. 이후 파일럿에서 사용 빈도, 절약한 사람 시간, 올바른 완료 1건당 비용을 비교해 다음 기능을 고른다.

## 공통 확장 규칙

추가 사용자 제안인 **웹 기반 분석 포털**은 [별도 설계 제안](TEAM_PLUGIN_WEB_PORTAL_2026-10-07.md)에 정리했다. Jira 번호·실패 단계/증상·로그 첨부로 분석하고, 결과 확인 후 DB 등록을 요청하는 흐름이다. 팀의 주요 장애물이 로컬 설치·명령 사용이라면 범용 코어보다 먼저 추진할 수 있으며, 서버 권한·작업 격리·원문 보존 정책이 선행되어야 한다.

- 판단·집계·검증은 가능한 한 스크립트, LLM은 설명·새 가설·선택된 초안에 사용한다.
- 원문 로그·전체 이슈 DB 대신 필요한 마스킹 근거와 구조화 결과만 모델에 제공한다.
- 주간/릴리스 보고서는 기준 SHA·시각·관측 범위를 표시하고, 미확인을 정상으로 집계하지 않는다.
- 제품에 여러 에이전트를 넣더라도 단순 작업은 단일 흐름으로 처리한다. 새 원인·교차 카테고리 규칙·보안 영향 검토에만 역할별 독립 분석을 사용한다.
- 자동 게시·Jira 쓰기·장비 제어·서버 다중 사용자화는 각각 새로운 권한 경계다. 기존 로컬 승인 모델로 충분하다고 가정하지 않는다.
