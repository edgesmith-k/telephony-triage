Telephony 이슈 원인은 스크립트가 판정하고, 팀의 판단은 이슈 DB에 쌓입니다

Jira 이슈와 logcat을 받아 시그니처로 원인 후보와 해결책을 찾고, 엔지니어가 확인한 결과를 사내 GitHub 이슈 DB에 PR로 남깁니다. Jira는 읽기만 하고, 저장되는 로그는 모두 마스킹됩니다.

원인과 해결책이 Jira 코멘트와 개인 메모에 흩어져, 담당자가 바뀌면 같은 분석을 반복합니다.

logcat 판독이 사람마다 다릅니다

듀얼 SIM, 시계 차, 수만 줄의 로그. 같은 로그에서 엔지니어마다 다른 결론이 나옵니다.

“진짜 고쳐졌나?”

수정 이후가 추적되지 않습니다

CL이 머지돼도 수정 빌드에서 재발이 없는지 확인한 기록이 남지 않아, 회귀를 늦게 발견합니다.

핵심 기능

분석부터 수정 검증까지 한 흐름

/telephony-triage:analyze

로그 자동 분석 · 시그니처 판정

파서가 logcat을 이벤트로 바꾸고, 증상(S)·원인(C) 시그니처로 분류 후보를 매깁니다.

  • bugreport에서 logcat 섹션 추출
  • 듀얼 SIM은 슬롯별 판별
  • 발생 시각이 로그 범위 밖이면 따로 알림
telephony-issue-db

팀 지식이 쌓이는 이슈 DB

카테고리 > 이슈 유형(증상) > 원인 + 해결책 + Jira 이력을 사내 GitHub 레포에 누적합니다.

  • search로 증상 문장·Jira 키 검색
  • README·STATS 자동 생성
  • 카테고리 오너의 월간 review
/telephony-triage:verify-fix

수정 검증

수정 빌드 로그로 재발 여부를 판정합니다. 통과 · 부분 통과 · 실패 · 판단 불가.

  • fix-submitted로 CL 기록
  • fixed는 verify-fix로만
  • 통과 로그는 회귀 테스트에 추가
Jira MCP

Jira 연동 (읽기 전용)

이미 등록된 Jira MCP를 찾아 구조화 필드와 발생 시각을 읽습니다. 쓰기 도구 호출은 차단됩니다.

  • 모델·SW·Android 버전 필드 매핑
  • 시험 절차의 PASS 스텝으로 분석 구간 지정(선택)
guard hook

안전 장치

쓰기 단계마다 사용자 확인을 거칩니다. hook이 main 대상 push와 승인 없는 push를 거부합니다.

  • 마스킹 안 된 커밋 차단
  • 사용자 이슈 DB clone은 건드리지 않음
  • 건너뛴 검증은 통과로 표시 안 함
site-defaults.yaml

사내 환경 맞춤 설정

Jira 서버·도구·필드 매핑, GHE 주소, 카테고리별 팀을 한 파일에 둡니다. 기존 파서와 분석 스킬도 연결합니다.

  • 새 유형은 코드가 아닌 규칙 파일로 추가
  • 팀원 각자는 setup 한 번
작동 방식

분석, 확인, 기록

1 · 분석

Jira + logcat → 원인 후보

Jira 읽기(즉시 마스킹) → 로그 파싱 → 시그니처 매칭 → 코드 경로 분석. 리포트에 후보, 근거 로그, 해결책, 수정 상태, 기존 사례 Jira가 나옵니다.

스크립트가 판정 · Claude가 설명
2 · 확인

“이 분류가 맞나요?”

엔지니어가 고릅니다: 맞음 / 다른 원인 / 새 원인 / 새 유형 / 원인 미확정. 새 규칙은 R1~R5 자동 검증을 거칩니다.

사용자 결정
3 · 기록

승인 → 브랜치 PR → 오너 머지

push 전에 변경 파일, README 미리보기, 검증 결과, 커밋 메시지를 보여주고 승인을 받습니다. 카테고리 오너가 리뷰 후 머지합니다.

main 직접 push 없음

맞는 규칙이 없으면 “후보 없음”으로 알리고 설명 기반 유사 후보와 타임라인 요약을 보여줍니다. 원하면 Claude 탐색 분석으로 가설 1~3개를 받을 수 있지만, 가설은 점수와 분류에 쓰지 않습니다.

장치동작
마스킹IMSI·전화번호·SIP URI·인증 값 등을 자동 마스킹합니다. 같은 값은 같은 번호(<CELL#1>)로 바뀌어 비교 로직은 유지됩니다. 마스킹 안 된 커밋은 hook이 차단합니다.
원문 격리Jira 응답 원문은 모델 컨텍스트에 넣지 않고 권한 700 작업 폴더에 둔 뒤 읽고 지웁니다. 모델에는 마스킹된 요약만 보입니다. 처리에 실패하면 원문 대신 오류를 돌려줍니다.
저장 범위이슈 DB에는 Jira 구조화 필드와 사용자가 확인한 한 줄 요약만 남습니다. 요약·설명·코멘트 원문은 저장하지 않습니다.
승인 후 PR이슈 DB 쓰기는 확인 화면 → 승인 → 브랜치 PR입니다. main 대상 push와 승인 토큰 없는 push는 pre-push hook이 거부합니다. 서버 측 브랜치 보호와 CODEOWNERS 필수 리뷰를 함께 켜도록 안내합니다.
Jira 읽기 전용허용 목록에 없는 Jira 도구 호출은 모두 거부합니다.
작업 격리분석은 별도 읽기 스냅샷에서 합니다. 사용자의 이슈 DB clone은 브랜치도 파일도 바꾸지 않습니다. 동시 작업은 세션 lock으로 막습니다.
도입 과정

설치, 사내 값 설정, 파일럿

플러그인 코드는 그대로 두고, 사내 값과 사내 코드는 정해진 경로에만 넣습니다. 이후 새 버전을 받아도 사내 설정은 보존됩니다.

설치와 환경 확인

  1. S-0사내 로그 형식 사전 점검 (선택, Claude 없이 30분)
  2. S-1사내 값 조사, 오프라인 평가 기준(1위 정확도 등) 합의
  3. S-2사내 Claude Code에서 플러그인·hook·Jira MCP 동작 확인

사내 값과 기존 자산 연결

  1. S-3Jira 서버·필드 매핑, GHE, 카테고리별 팀 설정
  2. S-4a검증된 기존 파서 포팅(골든 출력으로 결과 동일 확인), 기존 분류 가져오기, 분석 스킬 연결
  3. S-4카테고리별 실제 로그로 규칙 반영, 자주 나오는 유형 5~10개 등록

시험과 파일럿

  1. S-5실제 Jira·로그로 dry-run, 샌드박스 PR, 과거 해결 Jira 20~30건으로 정확도 게이트
  2. S-6남은 검토 항목 정리
  3. S-7사내 마켓플레이스 배포, 카테고리별 파일럿(10~20건), 첫 월간 리뷰 후 확대 결정

준비할 것

  • Ubuntu PC, Python 3.11+, git 2.31+, gh
  • Claude Code와 사용자 범위로 등록된 Jira MCP
  • 사내 GitHub(GHE) 레포와 브랜치 보호 설정 권한
  • 카테고리별 실제 logcat, 샘플 Jira 키 2~3개
  • Android 16/17 소스 경로
  • 과거 해결 Jira 20~30건 목록(정확도 평가용)

파일럿 지표(PR까지 걸린 시간, 중도 취소 비율, 작업당 질문 수)는 플러그인에 포함된 집계 도구로 뽑습니다.

FAQ

자주 묻는 질문

LLM이 원인을 결정하나요?

아닙니다. 분류 후보와 점수는 파서·매처·검증 스크립트의 출력으로 정해집니다. Claude는 리포트 설명, 초안 작성, 확인 질문을 맡고, 분류 확정은 엔지니어가 합니다.

Jira에 코멘트나 상태 변경을 하나요?

하지 않습니다. Jira는 읽기 전용이고, 허용 목록 밖의 Jira 도구 호출은 hook이 거부합니다.

이슈 DB에는 어떤 정보가 남나요?

마스킹된 로그 구간(fixture), 원인·해결책·시그니처, Jira 구조화 필드(모델, SW, Android 버전 등)와 엔지니어가 확인한 한 줄 요약입니다. Jira 본문·코멘트 원문은 저장하지 않습니다.

등록된 규칙에 맞는 원인이 없으면요?

“후보 없음”으로 알리고 비슷한 유형과 타임라인 요약을 보여줍니다. 새 원인·새 유형으로 등록하면 시그니처와 파서 규칙 초안, 마스킹된 fixture를 함께 만들고, 기존 분류를 깨지 않는지 자동 검증한 뒤 PR로 올립니다.

사내에 이미 쓰는 로그 파서가 있습니다.

검증된 판별 로직은 코드 그대로 포팅해 연결하고, 포팅 전 골든 출력과 결과가 같은지 테스트합니다. 포팅이 어려우면 기존 파서를 그대로 실행하고 출력만 변환하는 어댑터 방식도 있습니다.
