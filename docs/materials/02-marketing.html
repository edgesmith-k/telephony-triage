Telephony Triage

데이터·통화가 안 되는 Android 이슈, Jira 번호와 로그 파일만 주면 팀이 전에 찾은 원인인지 도구가 먼저 맞춰 봅니다.

기준 2026-10-17 · 화면 예시는 합성 샘플 데이터

본문은 이 파일 하나로 읽을 수 있습니다. 안내서 링크는 docs 폴더 묶음이 함께 있어야 열립니다.

시간은 합성 로그 1건의 실측(179초)입니다. 결과 코멘트 게시까지 넣었고, 사람이 답하는 시간은 뺐습니다. PR은 팀 기록에 넣기 전에 리뷰를 요청하는 것입니다.

Why

왜 필요한가

같은 원인이 몇 달 뒤 다른 사람에게 또 들어오는데, 앞서 찾은 답은 개인 메모에 있습니다.

"데이터가 안 붙어요" 같은 이슈가 오면 담당자는 수만 줄의 logcat(단말이 남기는 기록)을 처음부터 읽습니다. 듀얼 SIM 기록이 섞이고 단말 시계가 튀어서, 같은 로그도 사람마다 결론이 다릅니다. 수정 코드(CL)가 반영돼도 재발을 확인한 기록은 남지 않습니다.

직접 할 때
  • 수만 줄 로그를 처음부터 읽는다
  • 예전 사례는 사람 기억과 메모에 있다
  • 같은 로그도 사람마다 결론이 다르다
  • "고쳤다"는 말만 남고 재발 확인 기록이 없다
이 도구로
  • 로그를 이벤트로 바꿔 팀 규칙과 자동으로 맞춰 본다
  • 원인·해결책·Jira 이력이 팀 이슈 DB에 있다
  • 판정은 스크립트라 같은 로그·조건·규칙이면 같은 판정을 재현한다
  • "고쳐짐"은 수정 빌드 로그 검증을 통과해야 붙는다

처음 카드는 합성 샘플로 돌린 행동 평가 실행 기록(eval 2)의 리포트 발췌입니다. 다음 카드는 같은 형식으로 적은 예상 화면입니다(가상 이슈 MOCK-9100). 흐름 전체는 안내서 2장에 있습니다.

올리기 전 확인 화면

이슈 DB에 올리기 전에 도구가 이 화면을 냅니다. 변경 파일, README 미리보기, 검증 결과, 커밋 메시지가 차례로 나옵니다. 사람이 승인해야 push(서버로 올리기)합니다.

Scope

할 수 있는 것과 한계

v1은 Android logcat으로 6개 카테고리 이슈를 판정하고, 실제 정확도는 아직 모릅니다.

할 수 있는 것
  • logcat(radio·main·system·crash)과 bugreport의 logcat 부분 분석
  • data · call · network · sim · sms · ims 카테고리
  • Jira 읽기와, 승인한 결과 코멘트 1건 추가
  • 팀 이슈 DB에 PR로 기록하고, 수정 빌드 로그로 재발 확인
한계
  • 모뎀(CP) 로그는 읽지 않는다
  • 규칙에 없는 원인은 찾지 못하고 "원인 미확인"·"후보 없음"으로 알린다
  • data 밖 5개 카테고리의 로그 문구는 아직 예시 값이다
  • 정확도는 사내 과거 Jira 20~30건으로 처음 잰다
  • 지원 OS는 Ubuntu뿐이다

근거는 안내서 1.4 v1 범위와 25장 한계와 대응입니다.

도구가 판정하는 방식과 사람이 정하는 부분을 나눠 봅니다.

How it works

어떻게 동작하나

판정은 스크립트가 하고, 사람이 확인한 것만 PR로 팀 이슈 DB에 쌓입니다.

읽기

Jira와 로그를 읽고 개인정보를 가린다

대조

로그 이벤트를 팀 규칙과 맞춰 본다

사람 확인

담당자가 분류를 고른다

모르면 원인 미확정 · 기록하지 않음
규칙 시험

새 규칙을 R1~R6로 시험한다

실패하면 기록이 막힌다
올리기

확인 화면 승인 뒤 PR

승인 전에는 push 없음

판정은 스크립트가 합니다. Python 스크립트가 규칙대로 원인 후보를 고릅니다. 그래서 같은 로그·분석 조건·규칙 버전에서는 같은 판정을 재현합니다. Claude는 결과를 사람 말로 설명하고, 초안을 쓰고, 질문합니다.

확정은 사람이 합니다. 담당자가 분류를 고르고, 새 원인 초안을 하나씩 승인합니다. 확신이 없으면 "원인 미확정"으로 남기면 됩니다.

기록은 PR로 쌓입니다. 카테고리 담당자가 PR을 리뷰한 뒤 main(팀 이슈 DB의 기준 본)에 들어갑니다. 들어간 규칙은 다음 분석부터 자동으로 쓰입니다.

원인이 규칙에 없으면 "원인 미확인", 증상까지 처음이면 "후보 없음"으로 알리고, 비슷한 유형 3개를 보여 줍니다. 원하면 Claude가 원인 가설 1~3개를 근거와 함께 냅니다. 가설은 점수와 분류에 쓰지 않습니다. 팀이 이미 쓰는 분석 스킬을 선택으로 연결해 더 깊이 볼 수도 있습니다.

누가 무엇을 정하는지는 안내서 4장, 리포트 읽는 법은 9장에 있습니다.

다음은 데이터가 어디에 머무는지와, 승인 없이 올라가지 않게 막는 장치입니다.

Safety

데이터와 안전

로그와 Jira 원문은 내 PC에 남고, 밖으로 나가는 것은 개인정보를 가린 것뿐입니다.

  • 승인 없이 올라가지 않습니다. 확인 화면을 승인해야 push합니다. main으로 바로 가는 push는 거부됩니다. 마지막 방어선은 서버의 브랜치 보호와 필수 리뷰입니다.
  • 연습 실행은 올라가지 않습니다. --dry-run으로 준비한 작업은 올리기 단계(publish)가 거부합니다.
  • Jira는 읽기와 승인한 코멘트 1건뿐입니다. 필드 수정, 상태 변경, 이슈 생성은 거부합니다. 본문이 바뀌면 다시 승인받습니다.
  • 개인정보는 가립니다. IMSI, 전화번호, SIP 주소의 사용자 부분, 자격 증명을 표식으로 바꿉니다. "password": "…" 같은 JSON 키 형태도 가립니다.
  • 내 이슈 DB clone(내 PC의 사본)은 건드리지 않습니다. 파일·브랜치는 바꾸지 않습니다(깨끗한 main일 때 최신으로 맞추는 것만 예외). 분석과 기록은 따로 받은 사본과 임시 작업 폴더에서 합니다.

사람 이름처럼 형식이 없는 값은 가리지 못합니다. 그래서 Jira 본문과 코멘트 원문은 저장하지 않습니다. 자세한 것은 안내서 22장과 23장에 있습니다.

Rollout

도입 순서

사내에서는 S-0부터 S-7까지 한 단계씩 하고, 정확도를 확인한 뒤에만 파일럿을 합니다.

도입 단계 다섯 개 펼치기

  1. 사전 점검 (S-0, 선택)

    Claude 없이 30분 동안 사내 로그 형식을 점검합니다.

  2. 사내 값과 동작 확인 (S-1~S-3)

    "사내 설정 시작"으로 시작합니다. 사내 Claude Code에서 hook(도구 호출을 자동으로 검사하는 장치)과 Jira 연결이 동작하는지 봅니다.

  3. 기존 자산과 실제 로그 (S-4a·S-4)

    검증된 기존 파서와, 팀이 이미 쓰는 분석 스킬을 선택으로 연결합니다. data 밖 카테고리마다 자주 나오는 유형 5~10개를 실제 로그로 등록합니다. data는 기존 분류를 가져옵니다.

  4. 정확도 확인 (S-5)

    해결된 과거 Jira 20~30건을 스크립트만으로 다시 분석합니다. 합의한 기준(예: 1위 정확도 60%)에 못 미치면 파일럿을 시작하지 않습니다.

  5. 파일럿 (S-6·S-7)

    남은 항목을 정리하고 배포합니다. 카테고리별 10~20건으로 시작하고, 첫 월간 리뷰 뒤에 넓힐지 정합니다.

단계마다 자동 점검을 통과하고 사람이 확인해야 다음 단계로 갑니다. 자세한 것은 안내서 20장에 있습니다.

FAQ

자주 묻는 질문

도입을 검토할 때 먼저 나오는 질문 여섯 개입니다.

AI가 원인을 정하나요?

아닙니다. 원인 판정은 규칙을 따르는 스크립트가 합니다. Claude는 설명·질문·초안만 맡습니다. 분류 확정은 엔지니어가, 팀 이슈 DB 반영은 카테고리 담당자의 리뷰가 합니다.

정확도는 얼마인가요?

아직 모릅니다. 지금까지는 합성 데이터로 개발했습니다. 사내에서 해결된 과거 Jira 20~30건으로 처음 잽니다(S-5). 기준에 못 미치면 파일럿을 시작하지 않습니다.

품질은 어떻게 확인했나요?

자동 테스트 2,047개가 서버의 자동 검사(CI, Ubuntu)에서 Python 세 버전으로 모두 통과했습니다. Claude가 절차를 지키는지 보는 행동 평가(eval)는 70개입니다. 개발 단계에서 59개가 통과했고 실패는 0개, 11개는 사내에서 확인합니다. 최신 값은 안내서 31장에 있습니다.
