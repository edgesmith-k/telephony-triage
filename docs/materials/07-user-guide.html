Jira 번호와 로그만 주면 됩니다

Telephony 이슈를 분석하는 엔지니어를 위한 안내입니다. 설치, 첫 연습, 요청하는 법, 리포트 읽는 법만 담았습니다. 기록·PR은 기여자 가이드, 구조는 설계 안내, 세부 옵션은 운영 매뉴얼에 있습니다.

기준 main 2026-10-09대상 처음 쓰는 팀원읽는 시간 약 10분

13분 요약

이 절에서 알 수 있는 것: 내가 하는 일과 도구가 하는 일

  1. "ABC-12345 로그 분석해줘" + 로그 파일 경로
  2. 도구가 Jira·로그를 읽고 과거 사례와 비교
  3. 리포트: 원인 후보, 근거 로그, 해결책
  4. 내가 원인을 확정 (또는 미확정)
  5. 확인 화면을 보고 승인
  6. PR이 올라가고 담당자가 리뷰

내가 하는 일

  • Jira 번호와 로그 파일 경로를 준다 (로그를 대화에 붙이지 않음)
  • 질문에 답한다 (발생 시각, 소스 트리 등)
  • 원인을 확정하고, 올라갈 내용을 승인한다

도구가 하는 일

  • 개인정보를 가리고(마스킹) 로그를 해석
  • 과거 사례와 비교해 후보 3개를 근거와 함께 제시
  • 기록할 변경을 만들고 검사한 뒤 PR까지
알아 둘 것판정(어떤 원인이 맞았나)은 스크립트가 규칙대로 합니다. Claude는 설명을 채우고 질문할 뿐 판정을 바꾸지 않습니다. 그래서 같은 로그는 언제 돌려도 같은 후보가 나옵니다.

2설치 (처음 한 번, 약 10분)

이 절에서 알 수 있는 것: 설치 순서와 setup이 묻는 것

  1. 사내 마켓플레이스에서 플러그인 설치
  2. gh auth login -h <GHE 호스트>
  3. claude mcp list로 Jira 연결 확인
  4. /telephony-triage:setup

setup은 하나씩 묻습니다: GHE 아이디, 이슈 DB clone 경로와 원격 주소, Jira·logcat 시각의 타임존, 로그 연도를 정하는 방법, 작업 폴더. 팀 기본값과 같으면 그대로 넘기면 되고, 다르게 답한 값만 저장됩니다.

마지막에 점검 표가 나옵니다. 모든 행이 ok면 끝입니다. fail·warn 행은 "다음" 열의 안내대로 하면 됩니다. GHE 로그인이 안 됐으면(gh warn) 분석과 연습은 되지만 기록(PR)은 못 합니다.

"사내 기본값 없음"으로 멈추면관리자가 사이트 설정을 아직 올리지 않은 상태입니다. 관리자에게 알리고 기다립니다.

3첫 연습: dry-run

이 절에서 알 수 있는 것: 아무것도 올리지 않고 전 과정을 따라 해 보는 법

--dry-run은 확인 화면까지만 가고 아무것도 올리지 않습니다. 내 clone도 바뀌지 않고, GHE 로그인 전에도 됩니다.

/telephony-triage:analyze ABC-12345 ~/logs/radio.txt --dry-run
# Jira 연결 없이 연습할 때 (샘플 Jira 요약 파일)
/telephony-triage:analyze ABC-12345 ~/logs/radio.txt --dry-run --jira-file ~/samples/ABC-12345.yaml

연습한 계획은 남아 있어서, 나중에 같은 Jira로 --dry-run 없이 다시 실행하면 이어서 진짜로 올릴 수 있습니다. 이슈 DB의 docs/getting-started.md에 10분 온보딩 순서가 있습니다.

4요청하는 법

이 절에서 알 수 있는 것: 말로 요청하는 예시와 꼭 커맨드로 해야 하는 것

커맨드를 외우지 않아도 됩니다. 말로 요청하면 같은 흐름으로 연결됩니다. 로그는 이때도 파일 경로로 줍니다.

이렇게 말하면하는 일
"ABC-12345 로그 분석해줘, 데이터 안 붙어. 로그는 ~/logs/radio.txt"분석 (analyze)
"데이터 안 붙는 이슈 예전에 있었어? 지라 번호 알려줘"검색 (search)
"ABC-777은 APN 설정 고쳐서 해결했어, 기록만 해줘"수동 기록 (record)
"CALL-001-01 수정 CL 머지됐어, 이슈 DB에 반영해줘"수정 CL 기록 (fix-submitted)
"CALL-001-01 수정 빌드 로그로 재발 안 하는지 확인해줘"수정 검증 (verify-fix)

커맨드로 실행할 것: setup, sync(DB 최신화·정리), preview, review, migrate, 인자 없는 validate. 무엇을 쓸지 모르면 /telephony-triage:help.

5리포트 읽는 법

이 절에서 알 수 있는 것: 리포트에서 먼저 볼 줄과 오해하기 쉬운 줄

후보가 없을 때

DB가 아직 작을 때 가장 흔합니다. 그래도 리포트는 빈손이 아닙니다: Jira 설명으로 찾은 비슷한 사례 3개, 로그의 오류·거부·타임아웃 줄(최대 8줄), 파서가 모르는 태그(규칙이 없어 놓쳤을 수 있다는 힌트), 로그 범위 판정. 원하면 탐색 분석으로 Claude의 원인 가설 1~3개를 받을 수 있습니다. 토큰을 더 쓰므로 실행 전에 묻습니다. 가설은 "추정" 칸에만 들어가고 판정에는 쓰이지 않습니다.

6분석 뒤에 할 일

이 절에서 알 수 있는 것: 리포트를 본 뒤의 선택지

상황할 일
1위 후보가 맞다"예"로 확정 → 확인 화면 승인 → PR. 자세한 건 기여자 가이드
다른 후보가 맞다 / 새 원인이다그 항목을 고름. 새 원인·유형이면 도구가 초안을 만들고 내가 확인
원인을 아직 모르겠다"원인 미확정"으로 기록하거나, 기록하지 않고 끝냄
리포트만 보고 기록은 안 하고 싶다--analysis-only로 실행하거나 확인 화면에서 취소. 계획은 남아 나중에 이어서 할 수 있음
로그를 더 줘야 한다 (범위 밖 등)--more-logs로 로그 추가해 다시 분석

7토큰과 모델

이 절에서 알 수 있는 것: 비용을 줄이는 습관

  • 기본 모델은 Sonnet입니다. 탐색 분석의 가설 품질이 중요하면 /model로 Opus를 고를 수 있습니다.
  • 로그는 파일 경로로 줍니다. 대화에 붙이면 토큰이 크게 늘고 개인정보도 대화에 남습니다.
  • 한 작업이 끝나면 세션을 닫습니다. 이전 대화가 계속 쌓이면 매번 다시 읽습니다.
  • 심층 분석·탐색 분석은 토큰을 더 쓰므로 필요할 때만 "예"라고 답합니다.

모의 데이터 기준 분석부터 기록까지 1건에 약 39만 토큰(약 $0.4)입니다. 실제 bugreport는 더 클 수 있습니다.

8막혔을 때

이 절에서 알 수 있는 것: 혼자 먼저 해 볼 것과 물어볼 곳

  1. /telephony-triage:setup 다시 실행
  2. 점검 표의 fail·warn 행 "다음" 안내대로
  3. 메시지 원문으로 매뉴얼 6.3 검색
  4. 그래도 안 되면 메시지 그대로 관리자에게
하지 말 것막힌 걸 풀려고 hook을 끄거나(--no-verify) main에 직접 push하지 않습니다. 도구가 거부하는 건 대부분 실수를 막는 장치입니다. 이유는 설계 안내 9장에 있습니다.

더 볼 곳: 기록과 PR은 기여자 가이드, 구조와 이유는 설계 안내, 모든 옵션과 메시지는 운영 매뉴얼.
