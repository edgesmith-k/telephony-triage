telephony-triage는 어떻게 동작하나

Android Telephony 이슈의 원인을 로그로 찾고, 확인된 원인을 팀 이슈 DB에 쌓는 도구입니다. 이 문서는 코드를 몰라도 구조와 흐름을 이해할 수 있게 썼습니다. 정확한 정의와 옵션은 11장의 개발자용 문서에 있습니다.

기준 main 2026-10-10대상 처음 쓰는 사람, 도입 검토자, 설계를 바꾸려는 사람읽는 시간 약 25분

1한눈에 보기

이 절에서 알 수 있는 것: 도구가 하는 일, 쓰기 전과 후의 차이, 전체 흐름

Jira 이슈 번호와 로그 파일을 주면, 도구가 로그를 읽어 예전에 본 원인과 같은지 비교하고 원인 후보와 근거를 보여줍니다. 사람이 "이 원인이 맞다"고 확정하면 그 사례를 팀이 함께 쓰는 이슈 DB(GitHub 레포)에 기록합니다. 기록이 쌓일수록 다음 이슈는 더 빨리 풀립니다.

예전

  • 같은 증상도 매번 로그를 처음부터 뒤진다
  • 원인과 해결 경험이 사람 머리와 메일에 흩어져 있다
  • "고쳤다"는 버그가 정말 고쳐졌는지 추적하기 어렵다

이 도구를 쓰면

  • 과거 사례와 자동 비교해 원인 후보 상위 3개를 근거와 함께 받는다
  • 확인된 원인과 해결책이 팀 DB에 남아 누구나 검색한다
  • 수정 빌드의 로그로 재발 여부를 판정해 수정 상태를 관리한다
  1. Jira 번호와 로그를 준다
  2. 스크립트가 로그를 읽고 과거 사례와 비교
  3. 리포트: 원인 후보와 근거 로그
  4. 사람이 원인을 확정
  5. 기록할 변경을 자동으로 만들고 검사
  6. 사람이 확인 화면을 승인
  7. 팀 DB에 PR, 담당자 리뷰 후 반영

색칠된 칸이 사람이 결정하는 곳입니다. 나머지는 도구가 하고, 그 사이에도 판단이 필요하면 멈추고 묻습니다.

한 문장으로로그는 스크립트가 규칙대로 판정하고, Claude는 설명을 돕고, 기록은 사람이 확인한 것만 PR로 들어갑니다.

2꼭 알아야 할 말 8개

이 절에서 알 수 있는 것: 이 문서와 도구 화면에 계속 나오는 낱말의 뜻

이슈 DB팀이 함께 쓰는 사례집입니다. "이 증상은 이 원인이었고 이렇게 고쳤다"를 GitHub 레포에 쌓습니다.
유형과 원인유형은 사용자가 보는 증상, 원인은 그 증상을 만든 이유입니다. "데이터가 안 붙음"이 유형, "모바일 데이터가 꺼져 있음"이 원인입니다.
시그니처로그에서 증상이나 원인을 알아보는 판별 조건입니다. "이 문구가 60초 안에 이 순서로 나오면"처럼 적습니다.
S와 CS는 증상 조건, C는 원인 조건이 맞았는지입니다. 둘 다 0 아니면 1이고(시그니처 시간 초과·오류면 판정 불가), 판정은 이 두 값으로만 합니다.
fixture원인마다 붙여 두는 기준 로그입니다. 규칙을 바꿀 때마다 이 로그로 결과가 그대로인지 다시 확인합니다.
마스킹IMSI, 전화번호, IP 같은 값을 <IMSI#1> 같은 표시로 바꾸는 일입니다. 저장되는 로그는 모두 마스킹된 것입니다.
작업 계획"이 Jira를 이 원인에 추가" 같은 할 일 목록입니다. 파일을 바로 고치지 않고 이 목록을 최신 상태 위에 다시 적용해 PR을 만듭니다.
스냅샷과 lock스냅샷은 분석할 때 읽는 이슈 DB 복사본이라 내 원본을 건드리지 않습니다. lock은 한 사람이 쓰기 작업 두 개를 동시에 못 하게 막습니다.

5분석 한 건의 흐름

이 절에서 알 수 있는 것: 이슈 하나를 분석해서 기록하기까지의 단계

  1. lock을 잡고 DB 스냅샷 최신화
  2. Jira 읽기(즉시 마스킹), 발생 시각·Android 버전
  3. 코드 경로 선택 (Android 16/17)
  4. 로그 해석 + 마스킹, 로그가 발생 시각을 덮는지 확인
  5. 시그니처 비교: 상위 3개 후보
  6. 코드 분석, 원하면 심층·탐색 분석
  7. 리포트
  8. 원인 확정 (사용자)
  9. 계획 → 최신 DB 위 적용 → 검증
  10. push 전 확인 화면 승인 (사용자)
  11. PR → 카테고리 담당자 리뷰·반영

후보가 없거나 1위 원인이 확인되지 않으면, 원할 때 탐색 분석을 돌려 새 원인 가설을 받을 수 있습니다(6장 그림 E). 로그가 발생 시각을 덮지 않거나 다른 사람이 작업 중일 때처럼 판단이 필요하면 도구가 멈추고 묻습니다. 대신 고르지 않습니다.

6시퀀스 다이어그램

이 절에서 알 수 있는 것: 주요 흐름 다섯 개에서 누가 누구를 어떤 순서로 부르는지

읽는 법세로선은 참여자, 가로 화살표는 호출 순서입니다. 실선은 호출, 점선은 결과입니다. 굵은 강조색 화살표가 사람이 결정하는 곳이고, 회색 상자는 그 참여자가 안에서 하는 일입니다. 그림마다 위의 "볼 것" 세 줄만 먼저 읽어도 됩니다.

A. 분석: 이슈를 받아 원인을 확정하기까지

  • Jira 응답 원문은 Claude에게 가지 않습니다. 원문은 내 PC 작업 폴더에, Claude에게는 마스킹된 요약만 갑니다.
  • 판정(S/C)은 triage.py가 하고, Claude는 리포트의 설명 칸만 채웁니다.
  • 발생 시각처럼 결정이 필요한 값이 없으면 도구가 멈추고 묻습니다.

B. 기록과 PR: 모든 쓰기가 거치는 공통 절차

  • 파일을 바로 고치지 않고, 작업 계획을 최신 DB 위에 다시 적용합니다.
  • 그사이 다른 사람이 같은 곳을 바꿨으면(drift) 덮어쓰지 않고 어느 값을 쓸지 묻습니다.
  • 확인 화면을 승인한 뒤 파일이 바뀌면 승인은 무효가 되고 다시 확인합니다.

C. 수정 검증: 고친 빌드에서 재발하지 않는지

  • 수정 상태 fixed는 이 흐름을 통과해야만 됩니다. 사람 말로 대신하지 않습니다.
  • 수정 빌드 로그에 원인 조건이 다시 나오면 실패로 보고 open으로 되돌립니다.
  • 재현 시나리오를 수행한 흔적이 로그에 없으면 판정은 "알 수 없음"입니다.

D. 동기화: DB 최신화와 열린 PR 맞추기

  • sync는 DB에 쓰지 않습니다. 내 clone은 깨끗할 때만 최신으로 당깁니다.
  • PR을 올린 뒤 main이 바뀌면 sync-pr이 계획을 다시 적용해 같은 PR을 갱신합니다.
  • 계획 파일이 있는 PC(PR을 만든 PC)에서만 됩니다.

E. 새 이슈: 규칙에 없는 이슈를 새 유형으로 등록하기까지

  • 탐색 분석은 토큰을 더 쓰므로 기본은 실행 전에 묻습니다.
  • Claude의 가설은 점수·순위에 쓰지 않고 리포트의 "탐색 분석 (추정)" 칸에만 들어갑니다.
  • 가설을 채택해도 새 규칙은 평소처럼 자동 검증과 확인 화면을 거칩니다.

7상태가 바뀌는 방식

이 절에서 알 수 있는 것: 원인과 유형에 붙는 두 종류의 상태, 각각 언제 바뀌고 무엇에 영향을 주는지

상태는 두 종류이고 서로 독립입니다. 헷갈리기 쉬우니 먼저 구분합니다.

종류묻는 것값매칭에 영향
수정 상태 (원인만)"이 버그가 고쳐졌나?"open · fix-submitted · fixed · wont-fix · not-a-bug없음. 판단 문구만 바뀜
원인·유형 상태"이 항목을 아직 쓰나?"active · deprecated · merged-into있음. active만 후보로 씀

수정 상태: 고쳐졌나

원인 하나하나에 수정 상태가 붙습니다. 상태는 사람이 확인한 뒤에만 바뀌고, fixed는 수정 빌드 로그 검증을 통과해야만 됩니다.

상태뜻어떻게 들어오나
open원인은 알지만 아직 안 고침새 원인 등록, 검증 실패, 재발 의심
fix-submitted수정 CL과 반영 빌드가 기록됨fix-submitted 커맨드
fixed수정 빌드 로그에서 재발 없음이 확인됨verify-fix 통과로만
wont-fix not-a-bug고치지 않기로 함, 또는 사용자 설정처럼 버그가 아님사용자 확인
verify-fix를 안 돌리면?

원인은 계속 fix-submitted에 머뭅니다. "고쳤다"는 말만으로 fixed를 만들 수 없게 한 대가입니다. 방치되지 않도록 세 가지가 알려줍니다.

  • 월간 리뷰: fix-submitted가 30일(fix_submitted_max_days)을 넘으면 "수정 검증 대기 방치"로 올리고, 누가 기록했는지를 함께 보여줍니다. 예: DATA-001-01 … (2026-09-01부터 38일, 기록: user1). 기록자는 그 상태를 만든 커밋의 작성자이고, 이 사람에게 verify-fix를 요청하면 됩니다.
  • STATS: "fix-submitted 대기 목록"이 늘 표시됩니다.
  • 재발 감지: 수정 빌드 이후 버전에서 같은 원인이 다시 분석되면 리포트에 "수정 미흡 의심"이 뜹니다.

자동으로 검증까지 돌리는 장치는 아직 없습니다. 사내 테스트 장비 로그로 자동 검증하는 방안은 한계·보완 문서에 있습니다.

수정 상태와 검색·매칭수정 상태는 검색이나 매칭에서 원인을 빼지 않습니다. open·fix-submitted·fixed 원인 모두 후보로 나오고, 리포트에 "미수정", "수정 반영 빌드에서 발생", "회귀 의심"처럼 상태에 맞는 판단이 붙습니다. 매칭에서 빠지는 건 원인 자체가 폐기(deprecated)되거나 다른 원인에 병합된 경우뿐이고, 시그니처가 아직 없는 원인은 후보 대신 별도 목록에 나옵니다.

원인·유형 상태: 아직 쓰나

원인과 유형은 지우지 않습니다. 예전 Jira 기록과 PR이 그 ID를 가리키고 있어서, 지우면 이력이 끊깁니다. 대신 상태를 바꿔 매칭에서만 뺍니다.

상태언제 되나매칭검색
active새로 만들면 기본후보로 씀나옴
deprecated월간 리뷰의 "오래 안 쓰인 원인"(stale_months 동안 Jira 없음)이나 "지원 종료 버전"(대상 Android 버전이 모두 지원 밖)에서 담당자가 결정빠짐나옴 (상태 표시)
merged-into월간 리뷰 "중복 후보"에서 담당자가 병합 결정. 원인은 합쳐지는 쪽에 새 ID로 옮기고 Jira 기록도 따라감빠짐옛 ID로 찾아도 합쳐진 쪽으로 이어서 보여줌
시그니처 대기 (pending)상태 값은 아니지만 함께 알아 둘 표시입니다. 로그 분석 없이 직접 기록(record)하면서 원인 판별 조건을 아직 못 쓴 원인에 붙습니다. 판별 조건이 없어서 매처가 이 원인을 판정할 수 없으므로, 증상이 맞을 때 "시그니처 없는 기존 원인"으로 참고 목록에만 나옵니다. 월간 리뷰에 "시그니처 없는 원인"으로 올라가고, 조건을 추가하면 표시가 사라집니다.

8안전장치가 걸리는 순간

이 절에서 알 수 있는 것: 실수나 위험한 동작을 어디에서 막는지, 그리고 그 한계

안전장치는 네 겹입니다. 앞쪽은 빠르게 막고 이유를 설명하는 장치이고, 뒤로 갈수록 우회하기 어렵습니다. 마지막 방어선은 GitHub 서버의 브랜치 보호입니다.

한계①~③은 PC에서 동작하는 장치라 최선 노력입니다. 복잡한 명령이나 스크립트 안의 호출은 놓칠 수 있고, Claude의 Read 도구로 로그를 통째로 읽는 것도 막지 못합니다(스킬 지침으로만 제한). 그래서 ④ 서버 브랜치 보호가 반드시 켜져 있어야 합니다.

위 네 겹은 동작을 막는 장치입니다. 들어가는 규칙의 품질은 자동 검증 R1~R6이 지킵니다(기여자 가이드 3절). R1~R6, 행동 eval, 정확도 평가가 각각 무엇을 재고 누가 만드는지는 용어집 8절에 있습니다.

9왜 이런 장치를 두었나

이 절에서 알 수 있는 것: 쓰다 보면 만나는 멈춤·질문·거부가 왜 거기 있는지, 없으면 무슨 일이 생기는지

도구를 쓰다 보면 "왜 여기서 멈추지?", "왜 이건 못 하게 하지?" 싶은 순간이 있습니다. 대부분 아래 중 하나이고, 모두 실제로 생길 수 있는 사고 하나씩을 막으려고 둔 것입니다.

동시 작업과 충돌

장치언제 걸리나왜없으면
세션 lock분석·기록·sync처럼 스냅샷을 옮기거나 작업 공간을 만드는 흐름을 시작할 때한 PC의 스냅샷과 작업 공간은 하나뿐입니다. 두 작업이 동시에 옮기면 분석 도중 DB가 바뀌거나 작업 공간이 섞입니다창 두 개에서 분석하다 한쪽 결과가 다른 쪽 DB 상태로 나옴
lock 이어받기 질문같은 작업의 lock이 10분 안에 갱신된 적이 있을 때다른 창에서 아직 진행 중일 수 있어서 묻습니다. 10분이 지났으면 비정상 종료로 보고 그냥 이어받습니다살아 있는 작업을 덮거나, 죽은 lock 때문에 영영 못 씀
읽기 스냅샷분석할 때 항상내 clone 대신 복사본을 읽어, 내가 손대던 파일과 분석 대상 DB를 분리합니다내 clone의 미완성 편집이 분석 결과에 섞임
작업 계획 재적용모든 기록파일 diff를 rebase하면 YAML 충돌과 ID 중복이 납니다. "무엇을 할지"만 적어 두고 최신 main 위에서 다시 실행합니다PR 대기 중 main이 바뀌면 수동 충돌 해결
drift 질문계획이 고치려는 곳을 그사이 다른 사람이 바꿨을 때남의 변경을 조용히 덮지 않으려고, 계획 값과 main 값 중 무엇을 쓸지 묻습니다동료가 고친 해결책이 내 PR로 되돌려짐
새 ID는 적용할 때 할당새 유형·원인 기록두 사람이 동시에 새 원인을 만들면 둘 다 같은 다음 번호를 쓰게 됩니다. 최신 main 기준으로 적용 시점에 정합니다DATA-003이 두 개 생김

확인과 승인

장치언제 걸리나왜없으면
원인 확정 질문리포트 직후점수 1위가 늘 정답은 아닙니다. 팀 DB에 들어가는 판단은 사람이 내립니다틀린 원인이 쌓여 다음 분석까지 틀림
push 전 확인 화면모든 PR 직전변경 파일, diff, 검증 결과, 커밋 메시지를 사람이 본 뒤에만 올립니다의도와 다른 내용이 리뷰어에게 감
승인 무효화 (approved_hash)승인한 뒤 파일이 바뀌었을 때승인은 "그때 본 내용"에 대한 것입니다. 내용 지문이 다르면 다시 묻습니다본 것과 다른 것이 올라감
멈추고 묻기 (대신 고르지 않음)발생 시각 없음, 로그 범위 밖, 코드 경로 불명 등도구가 추측으로 채우면 결과가 그럴듯하지만 틀릴 수 있습니다근거 없는 가정 위의 판정

개인정보와 Jira

장치언제 걸리나왜없으면
Jira 쓰기 차단 (허용 목록)Jira 도구를 부를 때마다허용한 읽기 도구만 통과시킵니다. 금지 목록 방식이면 새 쓰기 도구가 생겼을 때 뚫립니다Claude가 Jira 상태·댓글을 바꿈
Jira 원문 격리Jira 응답을 받을 때마다본문에 개인정보가 있고, "이전 지시를 무시하라" 같은 문장이 섞여 Claude를 조종할 수도 있습니다. 원문은 PC에 두고 마스킹 요약만 보여줍니다개인정보가 대화·로그에 남음, 지시 주입
처리 실패 시 오류로 대체요약 만들기에 실패했을 때실패하면 원문을 그냥 넘기는 대신 오류 문구를 줍니다. 안전한 쪽으로 실패합니다오류 한 번에 원문 노출
로그 원문 통독 차단cat 등으로 로그·bugreport 전체를 읽으려 할 때원문에 개인정보가 있고, bugreport는 수백 MB라 통째로 읽으면 토큰이 폭증합니다. 필요한 구간만 읽게 안내합니다개인정보 노출, 한 번에 큰 비용
마스킹된 것만 저장fixture·Jira 기록 저장팀 DB는 여러 사람이 보고 오래 남습니다개인정보가 레포 이력에 영구히 남음

저장소 보호

장치언제 걸리나왜없으면
내 clone 편집 차단Claude가 이슈 DB clone 안의 파일을 쓰거나 Bash로 clone 브랜치·파일을 바꾸려 할 때사용자가 하던 작업과 도구 작업을 분리합니다. 도구는 별도 작업 공간에서만 씁니다내 미커밋 변경이 덮이거나 브랜치가 바뀜
main 직접 push 차단git push 대상이 main일 때모든 변경은 PR과 담당자 리뷰를 거쳐야 합니다리뷰 없는 변경이 팀 전체에 바로 반영
hook 끄기 차단--no-verify, hooksPath 변경검사를 끄는 지름길을 막습니다개인정보·깨진 파일이 커밋됨
원격 쓰기 확인이슈 DB 대상 gh·GitHub MCP 쓰기를 하려 할 때PR·이슈 변경은 승인 질문을 거치고, 머지는 리뷰어 몫이라 거부합니다리뷰 없이 도구가 PR을 머지
pre-push 승인 확인이슈 DB에 push할 때도구가 승인받은 내용과 실제 push가 같은지 봅니다. 권한 통제가 아니라 실수 방지입니다승인 없이 손으로 push한 실수가 그대로 올라감
생성 파일은 도구로만README·STATS 손편집데이터에서 자동으로 만드는 파일이라 손으로 고치면 실제 데이터와 어긋납니다README와 실제 DB가 다름

판정의 정직함

장치언제 걸리나왜없으면
fixed는 수정 검증으로만수정 상태를 fixed로 바꾸려 할 때"고쳤어요"라는 말만으로 닫으면 재발을 놓칩니다. 수정 빌드 로그와 재현 흔적이 필요합니다고쳐지지 않은 버그가 fixed로 남음
건너뜀 ≠ 통과fixture가 없어 검증을 못 했을 때"skipped"로 따로 표시하고 리뷰가 필요하다고 붙입니다검증 안 된 규칙이 "통과"로 보임
로그 범위 확인로그가 발생 시각을 덮지 않을 때그 경우 "원인 없음"이 아니라 "판단 불가"입니다엉뚱한 구간을 보고 원인 없다고 결론
판정 불가 ≠ 후보 없음시그니처가 시간 초과·정규식 오류로 끝났을 때S·C를 0이 아니라 null로 두고 "판정 불가 유형" 줄을 꼭 보여줍니다. 후보가 없어도 "후보 없음" 대신 "판정 불완전"이고, 이 결과는 재사용 캐시에 남기지 않습니다. 회귀·검증에서도 통과로 보지 않습니다오류 난 규칙이 "안 맞음"으로 보여 엉뚱한 새 유형이 생김
사이트 설정 없으면 멈춤site-defaults.yaml이 없을 때사내 실제 값 없이 예시 값으로 돌면 그럴듯하게 틀린 결과가 나옵니다모르는 사이에 예시 규칙으로 판정
우회하지 않고 보고git 충돌, 인증 실패, MCP 없음, 버전 불일치자동 우회는 문제를 숨기고 다른 곳에서 더 크게 터집니다원인 모를 데이터 꼬임
공통된 생각멈추고 묻는 비용은 몇 초이고, 틀린 기록이 팀 DB에 들어가는 비용은 그 뒤의 모든 분석입니다. 그래서 애매하면 멈추는 쪽을 골랐습니다.

10설계 원칙 7개

이 절에서 알 수 있는 것: 위의 모든 구조가 지키려는 약속

#원칙왜
1판정은 스크립트 출력으로만 한다같은 입력이면 언제나 같은 결과가 나와야 믿고 쌓을 수 있다
2중요한 변경은 사람 확인 뒤에만 한다 (원인 확정, 새 유형·원인, 규칙 추가, 수정 상태)잘못된 기록은 팀 전체의 다음 분석을 틀리게 만든다
3push 전에 변경·diff·검증 결과·커밋 메시지를 보여주고 승인받는다무엇이 올라가는지 사람이 본 것만 올라가게
4사용자의 DB clone은 브랜치도 파일도 바꾸지 않는다내가 하던 작업이 도구 때문에 망가지지 않게
5파일 대신 작업 계획을 최신 상태 위에 적용한다. 충돌은 묻는다여러 사람이 동시에 기록해도 남의 변경을 덮지 않게
6마스킹된 것만 저장하고, Jira는 읽기만 한다개인정보와 원본 시스템을 보호
7건너뛴 검증을 통과로 표시하지 않고, 문제는 우회하지 않고 보고한다"통과"라는 표시를 믿을 수 있게
