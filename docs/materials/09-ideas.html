이 도구로 더 할 수 있는 것

이슈 DB와 판정·검증 흐름을 다른 업무에 넓혀 쓰는 아이디어 12개입니다. 아이디어마다 흐름 그림, 좋아지는 것, 필요한 것, 원칙과 맞는지, 시점을 붙였습니다.

기준 main 2026-10-10대상 도입 검토자, 팀 리더, 메인테이너상태 후보 (확정 계획 아님)

1한눈에 보기

이 절에서 알 수 있는 것: 아이디어 12개의 효과·노력과 추천 순서

이 도구가 쌓는 것은 "어떤 증상이 어떤 원인이었고, 어떻게 고쳤고, 정말 고쳐졌나"입니다. 이 데이터와 이미 있는 판정·검증 흐름을 다른 일에도 쓸 수 있습니다. 아이디어는 모두 도입과 파일럿이 끝난 뒤의 후보이고, 지금 확정된 계획이 아닙니다.

추천 순서

그림 읽는 법아래 아이디어마다 흐름 그림이 있습니다. 강조 칸은 사람이 결정하는 곳, 회색 칸은 이미 있는 기능, 점선 칸은 새로 필요한 것입니다.

2이미 쌓인 데이터를 더 쓰기

1. 릴리스 품질 대시보드

빌드마다 열린 원인·회귀 의심을 한 화면에

좋아지는 것릴리스 판정 회의에서 "이 빌드에 아직 열린 telephony 원인이 몇 개인가"를 바로 봄
필요한 것STATS가 이미 모델·SW·버전별 분포를 냄. 빌드 비교 규칙(build_compare)이 사내 빌드명에 맞게 설정돼 있어야 함
원칙 확인읽기만 함. 판정은 기존 매칭 결과 그대로
시점파일럿 뒤 (데이터가 쌓인 뒤)

2. 테스트 케이스 개선

어떤 테스트 스텝에서 어떤 원인이 자주 나는지

좋아지는 것테스트 절차의 약한 곳을 찾고, 같은 정보로 수정 검증용 재현 흔적 규칙도 채움
필요한 것Jira에 실패 스텝 필드가 있어야 함(사내 S-1·S-3에서 확인)
원칙 확인실패 스텝은 분석 범위만 정하고 판정에 쓰지 않는다는 결정(10/04) 유지
시점파일럿 뒤

3. 신규 입사자 교육

실제 해결 사례를 교재로

좋아지는 것telephony 신규 인력이 실제 사례로 로그 보는 법을 익힘. 시니어 시간을 덜 씀
필요한 것dry-run은 이미 있음(아무것도 올리지 않음). 연습용 문제 선정만 필요
원칙 확인fixture는 이미 마스킹돼 있어 교육 자료로 써도 됨
시점파일럿 뒤 바로 가능

4. 벤더·모뎀 쪽 전달 리포트

AP·CP 판단 근거를 정리해 넘기기

좋아지는 것"AP 문제인지 모뎀 문제인지"를 근거와 함께 빠르게 넘김. 왕복 횟수 감소
필요한 것벤더 RIL 층 연결(platform.ril.vendor)이 사내에서 켜져 있어야 함(S-4a)
원칙 확인마스킹된 내용만. 외부 전달은 사내 반출 규정을 따름. 사람이 보낼지 결정
시점S-4a 뒤

3사람이 챙기던 일을 자동으로

5. 수정 검증 자동 실행

테스트 장비 로그로 verify-fix를 자동으로

좋아지는 것fix-submitted 방치가 사라짐. 고친 버그가 정말 고쳐졌는지 자동 확인
필요한 것사내 테스트 장비가 로그를 모으는 구조, 원인별 재현 시나리오 시그니처
원칙 확인판정은 스크립트, 반영은 사람 승인. 자동 게시는 별도 품질 기준을 통과할 때만(결정 10/01)
시점사내 로그 구조를 안 뒤

6. 방치·급증 알림

월간 리뷰를 기다리지 않고 알려주기

좋아지는 것리뷰 목록을 찾아보지 않아도 할 일이 사람에게 감
필요한 것알림 채널(GHE 이슈 또는 사내 메신저) 연결. RF-8
원칙 확인읽기와 알림만. DB를 고치지 않음
시점파일럿 뒤

7. 재발 조기 경보

고친 원인이 다시 나오면 즉시

좋아지는 것회귀를 분석한 사람만 아는 게 아니라 수정한 사람에게 바로 전달
필요한 것회귀 의심 판정은 이미 있음. 알림 연결만 필요(아이디어 6과 같은 채널)
원칙 확인상태 변경은 자동으로 하지 않음. 사람 확인 뒤에만
시점파일럿 뒤

8. Jira 접수 시 1차 분석

담당자가 열기 전에 리포트가 준비됨

좋아지는 것담당자가 이슈를 열 때 후보 3개와 근거가 이미 있음. 첫 응답 시간 단축
필요한 것Jira 첨부를 받는 커넥터(RF-6), 실행 환경, 비용 상한
원칙 확인Jira 읽기 전용 유지(댓글 금지) → 리포트는 다른 채널로. 확정은 사람
시점사내 환경을 안 뒤

4보기 쉽게

9. 규칙 변경 영향 화면

파서 규칙을 바꾸면 무엇이 달라지나

좋아지는 것"승인 필요" 표를 읽기 쉬운 화면으로. 규칙 리뷰가 빨라짐
필요한 것의미 단위 변경 계산은 이미 있음. 화면만 새로
원칙 확인판정 로직은 그대로, 보여주는 방식만
시점파일럿 뒤

10. 읽기 전용 웹 포털

설치 없이 검색·통계 보기

좋아지는 것플러그인을 안 쓰는 사람(QA, 기획, 관리자)도 사례를 찾아봄
필요한 것사내 웹 호스팅. 마스킹된 DB만 노출. 분석 결과만 소비하는 화면이 생기면 출력 계약 재검토
원칙 확인읽기 전용. 쓰기는 지금처럼 PR로만
시점파일럿 뒤 (보류 중)

5더 넓게

11. 다른 팀으로 넓히기 (범용판)

같은 구조를 오디오·카메라 등 다른 도메인에

좋아지는 것검증된 운영 구조(판정·승인·안전장치)를 재사용. 팀마다 처음부터 만들지 않음
필요한 것Android·RIL에 묶인 곳(약 30파일)을 분리하는 설계. 별도 로컬 레포에서 시작(10/07 보류)
원칙 확인판정 결정성·사람 승인 원칙을 코어가 그대로 가짐
시점보류, 재개 시점은 사용자 결정

12. 다른 플랫폼 지원

Android 외 텔레포니 스택

좋아지는 것같은 팀이 다른 플랫폼 이슈도 같은 방식으로 관리
필요한 것플랫폼 분리 구조는 일부 완료(RF-3·RF-4). 실제 대상 플랫폼 결정(RF-5)
원칙 확인변화 없음
시점사내 환경을 안 뒤

6아이디어를 고를 때 지킬 것

이 절에서 알 수 있는 것: 새 아이디어를 평가하는 다섯 가지 질문

  1. 판정은 여전히 스크립트가 하나? LLM이 원인을 정하거나 점수를 바꾸면 안 됩니다. 보조 정보는 보조 칸에만.
  2. 기록은 사람이 승인하나? 자동으로 DB에 반영하려면 신뢰도 점수가 아니라 별도 품질 기준을 통과해야 합니다(결정 10/01).
  3. Jira는 읽기만 하나? 결과를 Jira 댓글로 쓰지 않습니다. 다른 채널로 전달합니다.
  4. 마스킹된 것만 다루나? 화면·알림·외부 전달 모두 마스킹된 값만. 사외 반출은 사내 규정을 따릅니다.
  5. 비용 상한이 있나? 자동 실행은 토큰을 계속 씁니다. 건당 비용과 하루 상한을 먼저 정합니다.
