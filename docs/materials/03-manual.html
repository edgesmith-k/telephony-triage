꼭 알아야 할 개념 여덟 가지

이 도구의 낯선 말은 대부분 아래 여덟 가지로 설명됩니다. 정확한 정의는 용어집에 있습니다.

이슈 DB팀이 함께 쓰는 사례집입니다. "이 증상은 이 원인이었고 이렇게 고쳤다"를 GHE 레포에 쌓습니다.
유형과 원인유형은 사용자가 보는 증상, 원인은 그 증상을 만든 이유입니다. 예를 들어 "데이터가 안 붙음"이 유형이고 "로밍 설정이 꺼짐"이 원인입니다.
시그니처로그에서 그 증상이나 원인을 알아보는 판별 조건입니다. "이 문구가 이 시간 안에 나오면"처럼 적습니다.
S와 CS는 증상 조건이 맞았는지, C는 원인 조건이 맞았는지입니다. 둘 다 0 아니면 1이고, 판정은 이 두 값으로만 합니다.
fixture원인마다 붙여 두는 기준 로그입니다. 개인정보를 가린 짧은 조각이고, 규칙을 바꿀 때마다 이 로그로 결과가 그대로인지 다시 확인합니다.
마스킹IMSI, 전화번호, IP 같은 값을 <IMSI#1> 같은 표시로 바꾸는 일입니다. 저장되는 로그는 모두 마스킹된 것입니다.
작업 계획"이 Jira를 이 원인에 추가" 같은 할 일 목록입니다. 파일을 바로 고치지 않고 이 목록을 최신 main 위에 다시 적용해 PR을 만듭니다.
스냅샷과 lock스냅샷은 분석할 때 읽는 이슈 DB 복사본입니다. 내 clone은 건드리지 않습니다. lock은 한 사람이 쓰기 작업 두 개를 동시에 하지 못하게 막습니다.
한 문장으로로그는 스크립트가 규칙대로 판정하고, Claude는 설명을 돕고, 기록은 사람이 확인한 것만 PR로 들어갑니다.

시퀀스 다이어그램

세로선은 참여자, 가로 화살표는 호출 순서입니다. 실선은 호출, 점선은 결과, 굵은 글씨의 강조색 화살표는 사람이 결정하는 곳입니다. 회색 상자는 그 참여자가 안에서 하는 일입니다.

A. analyze: 분석에서 분류 확정까지

B. 공통 쓰기 절차: 계획 적용에서 PR까지

C. verify-fix: 수정 빌드 검증

D. sync와 sync-pr: 최신화와 PR 재동기화

E. 새 이슈: 탐색 분석에서 새 유형 등록까지

1개요

하는 일과 하지 않는 일

한 줄 흐름: Jira + 로그 → 파서(이벤트) → 시그니처 매칭 → 원인·해결책 제시 → 사용자 확인 → 이슈 DB에 PR → 리뷰어 머지.

하는 일

  • Jira 이슈(읽기)와 logcat·bugreport로 원인 후보, 근거 로그, 해결책, 수정 상태를 리포트로 보여줍니다.
  • 판정은 스크립트가 합니다. 증상(S)·원인(C) 시그니처가 맞았는지 0/1로 냅니다.
  • 사용자가 분류를 확정하면 작업 계획을 만들고, 최신 main 위에 적용해 확인 화면을 보여준 뒤 승인받아 PR을 올립니다.
  • 새 원인·유형·파서 규칙을 넣을 때 자동 검증(R1~R6)을 돌립니다.
  • 수정 CL 기록(fix-submitted)과 수정 빌드 검증(verify-fix)으로 수정 상태를 추적합니다.
  • 로그·Jira 텍스트의 개인정보를 마스킹하고, 마스킹된 것만 저장합니다.

하지 않는 일

  • Jira에 쓰지 않습니다. 허용 목록에 없는 Jira 도구 호출은 hook이 거부합니다.
  • main에 직접 push하지 않습니다. 항상 브랜치 + PR이고, push 전에 사용자 승인을 받습니다.
  • 사용자의 이슈 DB clone에서 브랜치를 바꾸거나 파일을 고치지 않습니다. 작업은 별도 worktree에서 합니다.
  • Claude(LLM)의 의견으로 분류·점수·검증을 정하지 않습니다. LLM 결과는 리포트 보조 칸에만 들어갑니다.
  • 건너뛴 검증을 통과로 표시하지 않습니다.
  • Jira 첨부를 자동으로 내려받지 않습니다(v1). 로그 경로는 사용자가 줍니다.
원칙판정 기준은 스크립트 출력(S/C)입니다. 분류 확정, 새 유형·원인, 시그니처·파서 규칙 추가, 수정 상태 변경은 사용자 확인 뒤에만 합니다. git 충돌·인증 실패·MCP 부재·버전 불일치는 우회하지 않고 보고합니다.

  2. Jira 읽기(즉시 마스킹), 발생 시각·Android 버전
  3. 코드 경로 선택(16/17 프로필)
  4. logcat 파싱 + 마스킹, 로그 범위 확인

예정·알려진 한계
  • data 카테고리의 태그와 문구는 실제 단말 로그와 AOSP 공개 소스로 형식을 확인했습니다. 예를 들어 데이터 설정 태그는 DSMGR-<n>이고, 평가 거부는 Data disallowed reasons: 한 줄입니다. 나머지 카테고리의 규칙은 아직 placeholder이고 S-4에서 실제 문구로 바꿉니다. 그 전에는 파일럿에 쓰지 않습니다.
  • 사내 마켓플레이스 등록(marketplace.json)은 S-7에서 합니다.
  • 계획 없는 브랜치를 자동으로 합치는 3-way replay, 사후 lint 정리 PR 자동화는 v1에 없습니다. 메인테이너가 수동으로 정리합니다.
  • Read 도구로 로그를 한 번에 통째로 읽는 것은 hook이 막지 못합니다(스킬 지침으로만 제한). 사내 S-2 확인 뒤 다룹니다.
  • 반입 뒤로 넘긴 항목(작업 상태 JSON 원자 쓰기, 성능 재측정, analyze 질문 수 등)은 docs/development/ARCHITECTURE_REVIEW_2026-10.md에 있습니다.

setup은 항목을 하나씩 묻습니다: GHE 아이디, 이슈 DB 로컬 clone 경로, 원격 URL, base 브랜치, GHE 호스트, Jira 시각 타임존, logcat 시각 타임존, 연도 결정 방식(jira | file-mtime | ask), logcat 기본 탐색 경로(선택), 작업 디렉토리. 소스 트리 프로필(code_profiles)은 건너뛸 수 있습니다.

첫 연습: dry-run

--dry-run은 확인 화면까지만 가고 아무것도 올리지 않습니다. 작업 worktree와 임시 브랜치를 지우고, 사용자 clone은 바뀌지 않으며, pending 피드백도 만들지 않습니다. gh 로그인 전에도 됩니다. 작업 계획은 남아서 같은 Jira를 다시 analyze하면 이어서 할 수 있습니다.

/telephony-triage:analyze ABC-12345 ~/logs/radio.txt --dry-run
# Jira MCP 없이 연습할 때 (샘플 Jira 요약 파일)
/telephony-triage:analyze ABC-12345 ~/logs/radio.txt --dry-run --jira-file ~/samples/ABC-12345.yaml
/telephony-triage:record ABC-12346 --dry-run

커맨드 없이 말로 요청하기

커맨드를 외우지 않아도 됩니다. telephony 증상의 원인 분석·분류를 말로 요청하면 스킬 설명(description)에 맞춰 Claude가 스킬을 불러 같은 흐름으로 연결합니다. 로그는 이때도 파일 경로로 줍니다.

이렇게 말하면가는 흐름
"ABC-12345 로그 분석해줘, 데이터 안 붙어"analyze
"콜이 왜 끊겼는지 logcat 좀 봐줘"analyze
"데이터 안 붙는 이슈 예전에 있었어? 지라 번호 알려줘"search (증상 문장 검색)
"ABC-777은 내가 APN 설정 고쳐서 해결했어, 이슈 DB에 기록만 해줘"record
"CALL-001-01 수정 CL 머지됐어, 이슈 DB에 반영해줘"fix-submitted
"CALL-001-01 수정 빌드 로그로 재발 안 하는지 확인해줘"verify-fix

해결책 검증(validate --cause)과 PR 재동기화(sync-pr)도 스킬 설명 기준으로는 말로 연결됩니다. 다만 아래 측정 문장에는 sync-pr 1건만 있고 validate --cause는 없습니다. 커맨드로 실행할 것: setup, sync, preview, review, migrate, 인자 없는 validate는 스킬 설명에 없어 말로는 확실하지 않습니다.

스킬이 불리지 않는 요청: 앱 빌드 에러, Jira 요약만, 개념 질문("RIL이 뭐야?"). 이런 요청은 일반 대화로 처리됩니다. 어떤 커맨드를 쓸지 모르면 help를 먼저 부릅니다.

측정 근거: 트리거 문장 24개×2회에서 recall·precision 100% (2026-10-05, 실제 플러그인을 로드한 모의 환경 측정). 사내 환경에서는 S-2에서 다시 측정합니다.

  • 버전이 안 맞아 쓰기가 막히면 읽기 전용으로 계속하고 계획 저장까지만 합니다(6.3).

  • 실패 스텝 구간이 너무 좁아 원인이 안 잡히면 --answer anchor=off로 Jira 발생 시각 기준으로 다시 분석합니다(스킬이 안내).

목적

형식
/telephony-triage:record <JIRA-KEY> [--cause <원인 ID> | --new-cause <유형 ID> | --new-type <category> | --unresolved <유형 ID>]

  [--failed-step <한 줄>] [--steps-file <파일>]
입력
분류 옵션이 없으면 비슷한 유형을 보여주고 대화로 고릅니다. --fixture는 새 원인의 양성 로그, --resolved-fixture는 해결책 적용 후 로그입니다.
출력
확인 화면(실행한 검증과 건너뛴 검증, 사유 포함) → PR issue/<JIRA-KEY>.

/telephony-triage:record ABC-12346

  • "고쳤다"는 fix-submitted까지만 기록됩니다. fixed는 verify-fix로만 됩니다.
  • 해결책 효과는 근거(다른 Jira 키 또는 적용 후 로그)가 있어야 "검증됨"입니다. 사용자 말만 있으면 "사용자 진술 — 카테고리 오너 리뷰 필요"로 남고 미검증 상태입니다.
  • record는 --jira-file을 --dry-run 없이도 받습니다. 이때 확인 화면과 PR에 "Jira 메타데이터: 오프라인 파일"이 표시됩니다.

/telephony-triage:search

누구나 · 읽기 전용

목적
이슈 DB에 이미 있는 기록을 찾습니다. 로그·Jira를 분석하지 않습니다.
형식
/telephony-triage:search <증상 문장|keyword|JIRA-KEY|ID>
출력
맨 위에 이슈(Jira) 번호 모음, 이어서 유형 > 원인 · 해결책(검증 여부) · 수정 상태 · 최근 Jira · 맞은 단어. 병합·재번호된 ID는 옛 ID → 새 ID로 연결해 보여줍니다.
예시
/telephony-triage:search 데이터 안 붙어, 이슈 번호 알려줘
/telephony-triage:search DATA-001-02
/telephony-triage:search ABC-12345
주의
검색 순위는 검색용이며 분류 근거가 아닙니다. 결과가 없으면 "일치 없음"과 다른 검색어를 제안하고, 이슈 번호를 지어내지 않습니다. 스냅샷이 없으면 최신 main 기준이 아닐 수 있으니 sync를 권합니다.

/telephony-triage:sync

누구나 · 최신화

목적
이슈 DB 읽기 스냅샷을 최신 origin/main으로 옮기고, 사후 lint 결과와 정리할 작업 디렉토리, 내 열린 PR을 보여줍니다.
형식
/telephony-triage:sync
출력
스냅샷 SHA와 base 변경 한 줄(base 변경 abc1234→def5678 / 변경 없음), 사후 lint 문제(있으면 "메인테이너 정리 필요"), 90일 넘은 닫힌·머지된 PR의 작업 디렉토리 목록, 내 PR마다 #번호 제목 — base 이동 | 이동 없음 | 확인 불가.
정리 대상
지울 후보는 PR이 닫히거나 머지된 오래된 작업 폴더, 계획 없이 원문만 남은 중단 작업, 남은 worktree·도구 브랜치입니다. 기준일은 기본 90일이고 후보를 고르는 기준일 뿐 자동 삭제가 아닙니다. 계획은 있는데 PR 번호가 없는 폴더는 지우지 않고 따로 보여줍니다.
  • 미게시 계획 보존: push하지 않은 계획입니다. 이어서 하거나 명시적으로 폐기합니다.
  • push 기록 있음, PR 연결 미확인: 원격 브랜치와 열린 PR을 확인한 뒤 publish를 다시 하거나 sync-pr <브랜치>로 복구합니다. PR 생성 실패로 단정하지 않습니다.
주의
정리는 사용자가 동의할 때만 지웁니다. base가 이동한 PR에는 sync-pr를 안내만 하고 실행하지 않습니다. 사용자 clone은 현재 브랜치가 base이고 깨끗할 때만 fast-forward합니다.

/telephony-triage:sync-pr

PR 작성자

목적
머지 대기 중에 main이 바뀌었을 때, 원래 작업 계획을 최신 main 위에 다시 적용합니다. 새 ID와 fixture 번호는 적용 시점에 다시 할당됩니다.
쉽게
git rebase로 글자를 합치는 대신 "무엇을 하려 했는지" 목록을 새 main에 처음부터 다시 실행합니다. 그래서 충돌이 거의 없고, 남이 먼저 바꾼 값(drift)이 있을 때만 어느 쪽을 쓸지 묻습니다.
형식
/telephony-triage:sync-pr [branch] (없으면 계획에 기록된 열린 PR에서 고름)
출력
확인 화면(ID 재할당 내역, drift 결정 포함) → 승인 → 원격 SHA를 지정한 lease push. 바뀐 ID는 PR 제목·본문에도 반영됩니다.
주의
  • 계획은 작성자 PC에만 있으므로 작성자가 실행합니다. 다른 PC로 옮기기 전에 끝내 두세요.
  • 마지막 publish 뒤 다른 사람이 브랜치에 push했으면 diff를 보여주고 덮어쓰기 / 중단을 묻습니다.
  • 계획이 없는 브랜치(직접 편집한 review/, chore/ 등)는 수동 절차만 안내합니다(7.5).

/telephony-triage:fix-submitted

누구나 · 수정 CL 머지 후

목적
원인의 fix.status를 fix-submitted로 바꾸는 PR을 만듭니다.
형식
/telephony-triage:fix-submitted <원인 ID> --ref <CL> --fixed-in <branch>[:<build>] (--fixed-in은 여러 번 가능, 빌드는 선택)
출력
PR 브랜치 fix-submit/<원인 ID>, 커밋 메시지 [<원인 ID>] fix-submitted: <ref>.
예시
/telephony-triage:fix-submitted CALL-001-01 --ref <CL> --fixed-in main-dev:BUILD_X
주의
  • --ref는 fix_ref_regex에 맞아야 합니다. 빌드가 없으면 회귀 판정도 verify-fix 통과도 할 수 없습니다. 나중에 같은 커맨드로 빌드를 추가합니다.
  • 이미 fixed인 원인은 거부합니다. 회귀라면 analyze 분류 단계에서 open으로 되돌립니다.
  • 코드·설정 수정 유형인데 시나리오·복구 시그니처가 없으면 나중의 verify-fix를 위해 지금 추가할지 묻습니다.

/telephony-triage:verify-fix

누구나 · 수정 빌드 로그가 있을 때

목적
수정 빌드 로그로 재발 여부를 판정하고 결과 PR을 만듭니다. 통과해야만 fixed가 됩니다.
형식
/telephony-triage:verify-fix <원인 ID> <수정 빌드 logcat...> [--jira <검증 Jira 키>]
출력
판정(통과·부분 통과·실패·판단 불가, 5.7)과 근거, PR 브랜치 verify-fix/<원인 ID>-<build>. 통과하면 수정 빌드 로그가 fixed fixture로 회귀 테스트에 들어갑니다.
예시
/telephony-triage:verify-fix CALL-001-01 ~/logs/after_fix.txt
주의
원인이 fix-submitted(재검증이면 fixed)여야 하고, fixed_in에 빌드가 있어야 하며, 로그 빌드가 그 이후(같은 빌드 포함)여야 합니다. 시나리오 흔적이 없으면 "판단 불가"이고, 사용자 말로 흔적을 대신하지 않습니다.

/telephony-triage:validate

직접 편집 기여자 · 해결책 검증

목적
인자가 없으면 내 브랜치 변경분을 검사합니다(아무것도 바꾸거나 push하지 않음). --cause면 해결책 효과를 로그로 검증하고 통과 시 PR을 만듭니다.
형식
/telephony-triage:validate [--cause <원인 ID> <적용 후 logcat...>] [--extra <logcat...>]
출력

변경분 검사: 검사별 통과 / 실패 / 승인 필요 / 건너뜀(사유) 표. 실행하는 검사는 다음과 같습니다(<ref> = origin/<base>).

db_lint.py --changed <ref> --db <db>
mask_pii.py --check --changed <ref> --db <db>
db_regress.py --all --db <db>
db_verify.py rules --changed <ref> --db <db>      # R1~R5, --extra면 R6

주의
건너뜀은 통과가 아닙니다. 생성 파일 검사가 실패하면 db_build.py --write로 다시 만든 뒤 커밋합니다. R6 실패는 진행을 막지 않고 사용자가 고릅니다.

5결과 읽기

분석 리포트 줄별 읽기

리포트 예시(값은 자리표시자, 근거 로그는 마스킹된 상태):

## ABC-12345 분석
- 분류 후보: data > DATA-001 > DATA-001-02 Roaming disabled (규칙 일치 점수 1.0, 일치 수준 높음 — 진단 확신도 아님)
- 근거 로그 (마스킹, 슬롯 phone 0):
  - 09-26 10:05:12.345 DNC-0 Data evaluation: ... Data disallowed reasons: ROAMING_DISABLED ... (f0:L1532)
- 로그 범위: 10:02 ~ 10:12 (발생 시각 포함), 시계 이상 없음
- 원인: (로그로 확인한 것 / 코드로 추정한 것 / placeholder 규칙 결과를 나눠 씀)
- 코드 위치: 파일:라인 + 분기 조건 (분석 트리: android16-main, Android 16)
- 해결책: 데이터 로밍 설정을 켠다   해결책 검증: ⚠ 미검증
- 수정 상태: not-a-bug — ...
- 기존 사례: Jira 1건 (ABC-333)
- 관련 원인: 없음
- 기타 후보: DATA-001-01 (규칙 일치 점수 0.4)
- 심층 분석: 해당 없음(1위 카테고리에 분석 스킬 설정 없음)
- 열린 PR: 없음
줄읽는 법
분류 후보카테고리 > 유형 > 원인. 원인 자리가 "원인 미확인"이면 증상만 맞은 것(S=1, C=0). 원인 시그니처가 시간 초과·오류(C: null)면 "원인 판정 불가(… 원인 미확인으로 단정하지 않음)"이고, 이때는 새 원인·유형을 만들지 않고 타임아웃·시그니처를 고친 뒤 다시 분석합니다
판정 불가 유형시그니처 시간 초과(matcher.pattern_timeout_ms)·정규식 오류로 판정 못 한 유형·원인: "판정 불가 유형: N·원인 M개 (…) — … 후보 순위·'후보 없음'은 불완전하다". match.json에는 S: null(0이 아님)로 남고, 이 실행은 재사용 캐시에 저장하지 않습니다
슬롯 불일치"슬롯 불일치: 1위 후보 근거는 phone N, Jira SIM 슬롯은 M — 다른 슬롯의 로그로 판정됐을 수 있다". Jira에 SIM 슬롯 숫자가 있을 때만
시계 이상 구간의 근거1위 후보의 근거가 시계 역행 구간에 있거나 sequence 줄 순서가 뒤집혔을 때 "… 근거 줄의 (f:L) 위치로 순서를 확인한다 [clock_anomaly, line_order]". 표시 전용이고 판정은 바뀌지 않습니다
근거 로그시그니처를 충족한 줄. (f0:L1532)는 입력 로그 순번(0부터)과 줄 번호. 슬롯은 듀얼 SIM에서 판별된 phone_id
로그 범위발생 시각이 로그 안에 있는지. "로그 범위 밖"은 "매칭 없음"과 다릅니다. "해석한 줄 없음(형식·인코딩)"은 형식 문제
원인 · 코드 위치Claude가 채우는 칸(TODO(LLM)). 판정이 아니라 설명입니다
해결책 검증"검증됨" 또는 "⚠ 미검증". 미검증이어도 후보로 씁니다(분류는 로그 근거)
수정 상태fix.status와 Jira SW 비교 판단(5.5)
다른 버전 원인5.6
RIL 이벤트의 hal사내에서 벤더 RIL 층 연결(7.7 platform.ril.vendor)을 켰을 때만 나옵니다. RILJ 요청이 벤더 층 어디까지 갔는지입니다. responded: 벤더 소켓 층에 응답이 있음, RILJ 응답이 없으면 AP 쪽 전달 유실 근거. reached: HAL까지 갔고 응답은 없음, 모뎀·벤더 쪽을 봄. not_reached: 주변에 벤더 줄은 있는데 이 요청만 없음, 같은 창에 다른 요청의 HAL 줄이 있을 때만 AP 쪽 근거. unknown: 벤더 줄이 수집되지 않음, 판단 근거로 쓰지 않음
순위 참고점수 동점 후보가 여럿이면 발생 시각 근접·키워드로 정렬했다는 표시. 원인 확정이 아님
재사용 / 재분석같은 입력이면 "재사용", 입력이 바뀌었으면 "재분석: 실행 m 대비 바뀐 입력 [...] — 1위 X → Y". 판정 불가 유형·시그니처 오류가 있던 실행은 캐시에 저장하지 않으므로 다음 실행은 항상 재계산
읽기 전용 / 분석 전용쓰기가 막힌 이유 또는 --analysis-only 안내. 리포트를 요약할 때도 빠지지 않는 줄입니다(must_show)

판정: S와 C

매처는 시그니처마다 0/1을 냅니다. S는 이슈 유형의 증상 시그니처, C는 원인 시그니처 충족 여부입니다. 분류·회귀·검증은 이 값으로 정하고, 점수와 일치 수준은 참고입니다.

예로 보면로밍 중 데이터가 안 붙는 로그라고 합시다. "데이터 연결 시도가 없다"는 증상 조건이 맞으면 S=1입니다. 같은 슬롯, 같은 시간대에 "로밍 설정이 꺼져서 거부됨" 줄이 있으면 로밍 원인의 C=1입니다. 증상만 맞고 아는 원인이 하나도 맞지 않으면 S=1, C=0이고, 이때가 새 원인을 등록할 기회입니다.
SC리포트 표현다음
11원인 후보 (점수 보통 1.0)분류 수락 또는 다른 원인 선택
10유형 일치, 원인 미확인 (점수 약 0.4)새 원인 작성, 원인 미확정 기록, 탐색 분석
0—후보 없음 (S=1인 유형 없음)새 유형 / 원인 미확정 / 기록하지 않음
null—판정 불가 (시그니처 시간 초과·오류). S=1인 유형이 없으면 머리줄이 "판정 불완전 — S=1인 유형 없음, 판정 불가 유형 N개 (후보 없음으로 단정하지 않음)"새 유형·원인을 만들지 않음. 시그니처·pattern_timeout_ms를 확인하고 다시 분석
  • 분석 모드에서는 S=1인 유형의 원인만 평가하고, 증상 근거와 원인 근거가 같은 슬롯·같은 시간 창 안에 있을 때만 C=1입니다.
  • 점수 = 증상 가중치 0.4 × S + 원인 가중치 0.6 × C + 보너스(발생 시각 근접 ≤ 0.1, 키워드 ≤ 0.05), 최대 1. 가중치는 issue-db.config.yaml의 scoring.
  • 일치 수준: 점수 ≥ 0.9 높음, ≥ 0.6 중간, 그 외 낮음. 진단 확신도가 아니며 자동 게시 근거로 쓰지 않습니다.
  • 시그니처 수락률 표본이 5건 이상이면 점수에 수락률 가중치가 곱해집니다(분석 모드만).
  • 실패 스텝으로 정한 "우선 유형"은 순위에만 반영되고 점수·S·C는 바뀌지 않습니다.

후보가 없을 때

초기 DB가 비어 있을 때 가장 흔합니다. 이때도 리포트는 빈손이 아닙니다. 단, 시그니처 시간 초과·오류로 판정 못 한 유형이 있으면 "후보 없음"으로 단정하지 않고 머리줄이 "판정 불완전"입니다(5.2).

  • 설명 기반 유사 후보: 마스킹된 Jira 요약(실패 스텝 포함)으로 검색한 상위 3개. 같은 이슈라는 뜻은 아닙니다.
  • 오류·거부·타임아웃 이벤트: 카테고리 타임라인에서 뽑은 최대 8줄(마스킹된 값만). 머리줄은 "오류·거부·타임아웃 이벤트: 추출 이벤트 기준 N건 (수집 태그 W/E/F 줄 중 이벤트로 추출 안 된 줄 M건: TAG a줄, …)"이고, N=0인데 M>0이면 must_show로 꼭 보입니다(이벤트가 0건이어도 오류 줄이 없다는 뜻이 아님).
  • 파서 규칙에 없는 태그: 같은 프로세스에서 tags.yaml에 없어 버려진 태그 상위 3개. 파서가 이벤트를 못 뽑아 후보가 없을 수 있다는 힌트입니다.
  • 로그 범위·시계 판정.
  • 원하면 탐색 분석(Claude 가설)을 실행합니다. 처음부터 끝까지는 5.4 규칙에 없는 새 이슈: 탐색 분석.

규칙에 없는 새 이슈: 탐색 분석

이슈 DB에 맞는 규칙이 없을 때(후보 없음, 또는 유형은 맞는데 1위 원인이 미확인) Claude가 마스킹된 타임라인과 소스 코드로 원인 가설을 세웁니다. 분석 단계 5-2이며, 시퀀스는 0장 그림 E입니다. 판정 기준은 그대로 스크립트 출력이고, 이 결과는 리포트의 "탐색 분석 (추정)" 칸에만 들어갑니다.

쉽게 말하면규칙에 없는 이슈가 와도 빈손으로 끝나지 않습니다. Claude가 로그 타임라인과 소스를 보고 "이런 원인일 수 있다"는 가설을 근거와 함께 세워 줍니다. 다만 그것은 판정이 아니라, 사람이 고를 출발점입니다.

push 전 확인 화면과 검증 결과표

이슈 DB에 쓰는 모든 흐름은 push 전에 이 화면을 그대로 보여주고 승인을 받습니다. 요약하거나 생략하지 않습니다.

이 화면에서 볼 세 가지첫째, 변경 파일과 ID가 내가 의도한 것인지 봅니다. 둘째, 자동 검사와 검증에 실패나 "건너뜀"이 없는지 봅니다. 건너뜀은 통과가 아닙니다. 셋째, 커밋 메시지와 한 줄 요약에 사람 이름이나 원문이 들어가지 않았는지 봅니다.

순서: 머리(대상 → 원인/유형, 구분, 브랜치, 리뷰어, 열린 PR) → 변경 파일 → ID 할당(예 NEW-CAUSE-1 → DATA-001-04) → 수정 상태 변경 → drift 결정 → 추가 설명 → README 반영 미리보기 → 주요 diff → 자동 검사 → 검증 결과 → 커밋 메시지·PR 제목 → approved_hash.

유형·원인·시그니처·fixture 추가와 검토

추가는 보통 analyze 분류 단계에서 "새 원인" 또는 "새 유형"을 고르며 시작됩니다. 도구가 제목·해결책·시그니처·파서 규칙·fixture 초안을 만들고 사용자가 모두 승인합니다.

무엇을 함께 넣나

점검부족하면
새 시그니처가 참조하는 태그가 tags.yaml에 있나태그 추가. 없으면 파서가 그 로그를 버려 매칭이 안 됨
RIL 요청·unsol이 ril.yaml에 있나요청 이름·카테고리·timeout 추가

원인 fixture가 있나parse_logcat.py cut으로 판별 근거 주변 최소 구간을 잘라 마스킹된 양성 fixture로
전체 회귀기존 fixture 기대값이 바뀌면 차단·보고

작성 규칙

  • 새 유형은 증상 시그니처가 필수입니다. 새 원인은 record에서만 시그니처를 나중으로 미룰 수 있습니다(signatures_pending, 리뷰 대상).
  • 시그니처와 extractor 패턴은 마스킹된 텍스트 기준으로 씁니다. 원본 식별자 패턴(15자리 숫자 등)은 lint가 금지합니다. 토큰은 번호가 아니라 종류(<CELL#\d+>)로 씁니다.
  • 태그·정규식은 실제 로그에서 확인한 문구로만 씁니다. extractor id는 kebab-case이고 바꾸지 않습니다.
  • 정규식 안전: 중첩 수량자·길이 제한 없는 역참조는 lint가 거부하고, 패턴당 실행 시간 상한(matcher.pattern_timeout_ms, 기본 2000)이 있습니다.
  • 코드·설정 수정 유형 원인은 나중에 fixed로 가려면 시나리오 또는 복구 시그니처가 필요합니다.
  • 새 시그니처가 다른 유형의 fixture에서도 잡히면(그 로그에 실제로 두 현상이 있을 때) "시그니처 좁히기 / 그 fixture에서 이 원인도 허용(also_allowed)"을 고릅니다. 허용하면 그 카테고리 오너가 리뷰어로 붙습니다.

python3 $S/db_verify.py rules --db . --changed origin/main  # R1~R5

PR 리뷰와 머지

PR 템플릿의 머지 전 체크리스트:

  • GHE에 충돌 표시가 없다.
  • 이 PR의 마지막 push 이후 main에 다른 PR이 머지되지 않았다(머지됐다면 작성자에게 sync-pr 요청).
  • 새 유형·원인의 제목·해결책이 CONTRIBUTING.md 작성 규칙에 맞다.
  • parser-rules 변경이나 "승인 필요" 검증 결과가 있으면 메인테이너가 승인했다.
  • 머지는 한 번에 하나씩. 대기 PR이 여럿이면 하나를 머지한 뒤 다음 작성자에게 sync-pr를 요청합니다.
  • PR 하나 = Jira 하나(또는 리뷰 정리 한 묶음). 제목은 [<원인 ID 또는 유형 ID>] <요약>.
  • "검증 못 함 — 리뷰 대상", "사용자 진술 — 카테고리 오너 리뷰 필요" 표시는 리뷰어가 근거를 확인할 항목입니다.

계획이 없는 브랜치 (직접 편집)

  1. git fetch origin 후 git rebase origin/<base>.
  2. 충돌이 생성 파일뿐이면 main 쪽을 받고 db_build --write로 다시 만듭니다.
  3. 새 ID가 main과 겹치면(db_add check-ids --base origin/<base>) db_add renumber <옛 ID> 후 db_lint --residual <옛 ID>=<새 ID>.
  4. /telephony-triage:validate 통과 후 커밋, TT_PUBLISH_TOKEN=manual git push --force-with-lease(pre-push hook이 토큰 없는 push를 거부).

사후 lint 정리 (메인테이너, 수동)

  • main에 같은 ID가 두 번: 먼저 머지된 쪽이 소유. 나중 쪽을 chore/fix-db-<문제 ID>에서 다음 빈 ID로 옮기고, 커밋에 Renumbered: <옛 ID> -> <새 ID> 트레일러를 남깁니다. "main ID는 바꾸지 않는다"의 유일한 예외입니다.
  • Jira 중복: 나중에 머지된 쪽 파일을 지우고 두 작성자에게 알립니다. 어느 분류가 맞는지는 작성자와 카테고리 오너가 정합니다.

이슈 DB 레포 안의 .githooks/에 있고, Claude 밖 터미널에서 직접 커밋·push할 때도 걸립니다.

이름언제 걸리나무엇을막히면할 일
pre-commit이슈 DB에서 git commit이 커밋을 만들기 직전 (db_pr publish --commit의 커밋 포함)staged 변경에 lint·마스킹·회귀·생성 파일 검사(db_precommit.py). 승인 필요(3)는 경고만 하고 통과"[telephony-triage pre-commit] ✗ <검사>: <사유>" 뒤에 "커밋을 막았다. 위 문제를 고친 뒤 다시 커밋한다. 우회(--no-verify 등)는 금지다 (CONTRIBUTING.md)." 플러그인 경로가 무효하면 plugin.scripts_path 안내✗ 항목을 고치고 다시 커밋합니다. 경로 안내면 Claude Code 세션을 한 번 열어(1번 hook) 경로를 갱신합니다
pre-push이슈 DB에서 git push가 원격에 보내기 직전대상이 base 브랜치면 거부. 환경변수 TT_PUBLISH_TOKEN이 없거나 승인 해시와 다르면 거부. 토큰은 db_pr publish가 자기 push에만 넣습니다"[telephony-triage pre-push] push를 거부했다: TT_PUBLISH_TOKEN이 없다. 도구 흐름은 확인 화면 승인 뒤 db_pr publish가 push한다. 직접 편집한 브랜치는 /telephony-triage:validate 통과 후 TT_PUBLISH_TOKEN=manual 을 붙여 push한다 …"도구 흐름이면 확인 화면을 승인해 publish가 push하게 둡니다. 직접 편집 브랜치면 validate 통과 후 TT_PUBLISH_TOKEN=manual git push origin <브랜치>

3·4번과 pre-commit은 검사 내용이 겹치는 이중 장치입니다. Claude 세션 안에서는 3·4번이 더 빨리, 더 분명한 메시지로 막고, 진짜 강제는 pre-commit입니다. 목적은 도구 경로 밖의 실수 방지이지 권한 통제가 아닙니다.

한계명령 판정은 최선 노력입니다. 변수 치환, 별칭, 스크립트 파일 안의 git 호출, $( ), GIT_DIR= 같은 우회는 보지 못합니다. Read 도구의 통독도 막지 못합니다. 그래서 진짜 강제는 git pre-commit hook과 서버 측 브랜치 보호입니다.
