1가치: 왜 써야 하나

이 절에서 알 수 있는 것: 가치 관련 질문과 답

Q1한 줄로 무엇인가요?

Jira와 logcat을 받아 과거에 확인된 원인 규칙과 대조해 원인 후보와 근거 로그를 보여주고, 엔지니어가 확정한 결과를 팀 이슈 DB에 쌓아 다음 분석에 재사용하는 Claude Code 플러그인입니다.

근거: 결재용 요약

Q2어떤 문제에 쓰면 좋을까요?

같은 증상의 data·call 이슈가 반복될 때 과거 원인부터 확인하는 데, 담당자가 바뀔 때 원인·해결 경험을 넘겨주는 데, 수정 CL 이후 재발 여부를 확인하는 데 쓰면 효과가 클 것으로 봅니다. 신규 인원이 로그를 볼 때 어디부터 볼지 근거 줄로 안내받는 용도로도 쓸 수 있습니다.

근거: 사례집

Q3지금 방식과 무엇이 달라지나요?

원인과 해결 경험이 개인 메모·Jira 댓글이 아니라 리뷰를 거친 팀 DB에 남습니다. 같은 로그면 누가 돌려도 같은 후보가 나오고, 수정 이후 재발 여부도 기록으로 추적됩니다.

근거: 소개 페이지

Q4효과를 어떻게 확인하나요?

파일럿에서 PR까지 걸린 시간, 중도 취소 비율, 작업당 질문 수, 오탐·누락, 신규 사용자 온보딩을 잽니다. 숫자는 플러그인에 포함된 집계 도구가 뽑고, 기준값은 도입 초기(S-1)에 합의합니다.

근거: 파일럿 평가표 3절

Q5효과가 바로 나오나요?

아닙니다. 규칙이 쌓일수록 효과가 커지는 구조라 초기에는 "후보 없음"이 자주 나옵니다. 그래서 도입 때 카테고리마다 자주 나오는 유형 5~10개를 실제 로그로 먼저 등록하고 시작합니다.

근거: 도입 로드맵 S-4

2정확도·신뢰: 믿을 수 있나

이 절에서 알 수 있는 것: 정확도·신뢰 관련 질문과 답

Q6AI가 원인을 정하나요? 틀리면요?

아닙니다. 원인 판정은 규칙을 따르는 스크립트가 하고, Claude는 설명·질문·초안만 맡습니다. 분류 확정은 엔지니어가, 팀 DB 반영은 카테고리 담당자 리뷰가 합니다. AI가 틀린 말을 해도 판정은 바뀌지 않습니다.

근거: 설계 결정 1

Q7정확도는 얼마인가요?

아직 모릅니다. 지금까지는 합성 데이터로 개발했습니다. 사내에서 해결된 과거 Jira 20~30건으로 1위 정확도·오탐률을 재고(S-5), 합의한 기준에 못 미치면 파일럿을 시작하지 않습니다.

근거: 파일럿 평가표 2절

Q8규칙이 잘못 들어가면요?

새 규칙은 들어갈 때마다 자동 검증 R1~R6(의도한 로그만 잡는지, 기존 분류를 깨지 않는지)을 거치고, 실패하면 push가 막힙니다. 그 뒤 담당자 리뷰와 월간 리뷰가 한 번 더 봅니다.

근거: 기여자 가이드 3절

Q9품질은 어떻게 검증됐나요?

플러그인 코드 자동 테스트 약 1,100개가 CI(Ubuntu)에서 통과하고, 샘플 이슈 DB 회귀 23/23, Claude 행동 시나리오 eval 60개를 정의했습니다. 모두 합성 데이터 기준이며 실제 로그 검증은 사내 단계에서 합니다.

근거: 용어집 8절

3보안: 위험하지 않나

이 절에서 알 수 있는 것: 보안 관련 질문과 답

Q10개인정보가 밖으로 나가나요?

IMSI·전화번호·SIP URI·자격 증명 등은 자동 마스킹되고, 팀 DB와 Claude 대화에는 마스킹된 값만 갑니다. Jira 응답 원문은 PC 작업 폴더에만 두고 Claude에는 마스킹 요약만 보입니다. 사람 이름처럼 패턴이 없는 값은 잡지 못해 Jira에서 저장하는 정보 자체를 최소화했습니다.

근거: 보안과 데이터

Q11Claude(외부 모델)로 무엇이 전송되나요?

마스킹된 요약과 마스킹된 로그 구간, 사용자와의 대화입니다. 로그 원문 통째 읽기는 hook이 막습니다. 다만 Claude Code를 쓰는 것 자체의 데이터 정책은 회사의 Claude Code 사용 조건을 따르므로 보안 부서 확인이 필요합니다.

근거: 보안과 데이터 2절

Q12Jira나 소스 코드가 바뀔 수 있나요?

Jira는 허용 목록의 읽기 도구만 통과하고 나머지는 거부됩니다. 이 도구가 쓰는 곳은 팀 이슈 DB 레포뿐이며, 그것도 승인 → 브랜치 → PR → 담당자 리뷰를 거칩니다. 제품 소스 코드는 읽기만 합니다.

근거: 설계 안내 8절

Q13PC 쪽 안전장치를 누가 끄면요?

PC 장치(Claude hook, git hook)는 빠른 차단용입니다. 최종 방어선은 GHE 서버의 main 브랜치 보호와 담당자 필수 리뷰라서, PC에서 우회해도 리뷰 없이 main에 들어가지 않습니다. 이를 위해 GHE 관리 권한이 필요합니다.

근거: 설계 결정 10

4비용·인력: 얼마나 드나

이 절에서 알 수 있는 것: 비용·인력 관련 질문과 답

Q14돈은 얼마나 드나요?

토큰 기준으로 이슈 1건(분석 → 기록)에 약 39만 토큰, 약 $0.4입니다(모의 데이터 실측, Sonnet). 실제 bugreport는 1.5~2배로 추정합니다. 도입 준비를 data 카테고리만 하면 3천만~6천만 토큰(약 $25~60)으로 추정합니다. Claude Code 사용 계약 비용은 별도입니다.

근거: 결재용 요약 4절

Q15사람은 몇 명이 필요한가요?

도입 단계는 담당자 1명이 S-0~S-7을 진행하고, 카테고리별 실제 로그와 과거 Jira 정답 정리에 각 팀 도움이 필요합니다. 운영 중에는 메인테이너 1~2명, 카테고리마다 담당자 1~2명(PR 리뷰·월간 리뷰)이 필요합니다.

근거: 관리자 런북

Q16엔지니어 한 명당 부담은요?

처음 한 번 설치(setup)하고, 이슈 1건은 아는 원인이면 약 10분, 새 원인을 등록하면 20~30분입니다(합성 시나리오 기준). 기여 부담은 파일럿에서 중도 취소 비율로 따로 잽니다.

근거: 사례집

Q17기간은 얼마나 걸리나요?

단계는 기간이 아니라 완료 기준으로 끝냅니다(S-0~S-7). 실제 기간은 S-1에서 사내 로그·Jira 준비 상황을 보고 산정합니다. 근거 없는 주 단위 일정은 아직 적지 않았습니다.

근거: 도입 로드맵

5운영·리스크: 잘못되면

이 절에서 알 수 있는 것: 운영·리스크 관련 질문과 답

Q18쓰다가 그만두면 무엇이 남나요?

팀 이슈 DB는 일반 GitHub 레포의 Markdown·YAML 파일과 마스킹된 로그라서 플러그인 없이도 읽고 검색할 수 있습니다. Jira는 바뀐 것이 없습니다. 플러그인은 제거하면 끝입니다.

근거: 설계 안내 4절

Q19특정 업체(Claude)에 묶이나요?

판정·검증·DB 생성은 Python 스크립트라 Claude 없이도 돕니다(정확도 평가도 스크립트만 씀). Claude는 대화·설명·초안을 맡는 부분이라, 바꾸려면 그 부분(스킬)을 다시 만들어야 합니다.

근거: 설계 결정 1

Q20만든 사람이 없어도 유지되나요?

설계 문서, 운영 매뉴얼, 관리자 런북, 설계 결정 기록이 있고 메인테이너 1~2명이 맡도록 역할을 정했습니다. 작성자가 없는 PR은 리뷰어가 직접 편집 절차로 인수하며, 이 절차는 파일럿에서 실제로 시험합니다.

근거: 파일럿 평가표 4절

Q21알려진 한계는요?

규칙에 없는 이슈는 못 찾고(탐색 분석으로 보조), data 외 카테고리 규칙은 아직 예시이며, 수정 검증을 안 돌리면 fixed로 가지 않는 등이 있습니다. 한계마다 대응을 정리했습니다.

근거: 한계와 보완

6확장: 다음은

이 절에서 알 수 있는 것: 확장 관련 질문과 답

Q22다른 팀·플랫폼에도 쓸 수 있나요?

Android 전용 코드는 플랫폼 어댑터로 분리돼 있어 새 플랫폼은 로그 해석 부분만 추가하면 됩니다. 다른 도메인 팀용 범용판은 계획 단계입니다. 지금 지원은 Android입니다.

근거: 소개 페이지 확장 절

Q23자동화(사람 없이 처리)도 되나요?

지금은 모든 기록에 사람 확인이 들어갑니다. 자동화를 하더라도 점수가 아니라 별도 품질 기준을 통과한 것만 자동 게시하도록 원칙을 정했고, 파일럿 뒤 설계합니다.

근거: 설계 결정 13

7아직 모르는 것

이 절에서 알 수 있는 것: 답할 수 없는 질문과, 언제 답이 나오나

아직 모르는 것언제 알 수 있나지금 있는 것
실제 로그에서의 정확도S-5 정확도 관문합성 데이터로만 개발함
실제 토큰·비용S-2 측정, 파일럿모의 데이터 eval 기준만 있음
사내 Claude Code·Jira MCP에서의 동작S-2사외 실험 환경 결과만 있음
리뷰·기여 부담S-7 파일럿PR 시간·취소율로 측정 예정
도입 기간S-1 산정사내 준비 상황에 따라 다름
정직하게이 항목들은 사외에서 합성 데이터로 개발한 한계라서, 수치를 미리 약속하지 않았습니다. 대신 각 단계에 관문을 두어 기준에 못 미치면 다음 단계로 가지 않습니다.

8결정 전 확인할 것

  • 데이터: 카테고리별 실제 logcat과 해결된 과거 Jira 20~30건(정답 원인)을 준비할 수 있는가
