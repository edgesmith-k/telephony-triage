설계를 바꾸려는 사람, "이건 왜 이렇게 했어?"가 궁금한 사람을 위한 기록입니다. 결정마다 배경, 고려한 대안, 선택한 이유, 그 대가와 대가를 줄이는 방법을 적었습니다. 결정을 바꾸려면 여기 적힌 "대가"와 "근거"를 먼저 보세요.

그림 읽는 법결정마다 대안 비교 그림이 있습니다. 강조 상자가 선택한 것, 점선 상자가 고려했지만 고르지 않은 것입니다. + 는 장점, 주황 − 는 단점입니다.

1판정은 스크립트가, LLM은 보조로

신뢰 · 설계 초기 · (c) 10/04

결정원인 판정(S/C)과 점수·검증은 결정적인 스크립트 출력으로만 한다. Claude의 결과는 리포트 보조 칸에만.

배경: 팀이 함께 쌓는 DB라서, 같은 로그를 누가 언제 돌려도 같은 결과가 나와야 기록을 믿을 수 있다.

대가와 대응규칙에 없는 이슈는 못 찾는다 → 탐색 분석(가설은 보조 칸)으로 새 규칙을 만들게 했다.
근거 문서12-principles.md, 결정 (c)

2실패 스텝과 Claude 가설은 판정에 쓰지 않음

신뢰 · 10/04

결정테스트 실패 스텝과 탐색 분석 가설은 분석 범위·순위·검색·리포트 보조에만 쓴다.

배경: 실패 스텝은 "어디를 볼지"에는 유용하지만 원인 자체의 증거는 아니다.

대가와 대응실패 스텝으로 범위를 좁혀도 S/C는 로그가 정한다.
근거 문서DRAFT_NOTES 결정 (c)

3도구와 데이터를 두 레포로

협업 · 설계 초기

결정플러그인(도구)과 이슈 DB(데이터)를 별도 레포로 둔다.

배경: 플러그인은 설치될 때 캐시 경로로 복사되므로 그 안에서 git push를 할 수 없다. 또 규칙은 자주, 도구는 드물게 바뀐다.

대가와 대응DB 스키마·생성기 버전과 플러그인 지원 범위를 비교하는 호환 검사(읽기 전용 전환, 쓰기 차단)를 넣었다.
근거 문서01-architecture.md §2.1

4이슈 DB는 GitHub 레포 + PR

협업 · 설계 초기

결정이슈 DB를 사내 GHE git 레포로 두고, 모든 변경은 브랜치 + PR + 카테고리 담당자 리뷰로 반영한다.

배경: 기록이 곧 팀의 판단 기준이 되므로, 누가 무엇을 왜 바꿨는지 남고 되돌릴 수 있어야 한다.

대가와 대응리뷰 병목 → 한 번에 하나씩 병합 + sync-pr로 충돌을 없애고, 파일럿에서 PR까지 걸린 시간을 잰다.
근거 문서01-architecture.md §1, 06-collaboration.md

5파일 대신 작업 계획을 최신 main에 다시 적용

협업 · 설계 초기

결정도구는 파일을 직접 고쳐 rebase하지 않고, "무엇을 할지"(계획)를 최신 main 위에서 다시 실행해 PR을 만든다. 새 ID는 적용할 때 정한다.

배경: 여러 사람이 동시에 같은 유형에 원인을 추가하면 파일 충돌과 ID 중복이 생긴다.

대가와 대응다른 PC에서는 sync-pr 불가 → 작성자 부재 시 리뷰어가 직접 편집 절차로 인수.
근거 문서06-collaboration.md §6.3, contracts.md §작업 계획

6사용자의 clone은 건드리지 않음

협업 · 설계 초기

결정분석은 읽기 스냅샷, 쓰기는 별도 작업 공간과 도구 브랜치(tt/*)에서 한다. 사용자 clone에는 fetch와 조건부 fast-forward만.

배경: 사용자가 직접 편집하던 내용이 도구 때문에 망가지면 도구를 믿지 않게 된다.

대가와 대응남은 작업 공간은 sync가 목록을 보여주고 동의를 받아 지운다.
근거 문서12-principles.md, 08-safety.md 규칙 8

7한 사람은 한 번에 한 작업 (세션 lock)

협업 · 설계 초기

결정스냅샷을 옮기거나 작업 공간을 만드는 흐름은 lock을 잡는다. 같은 작업의 lock이 10분 안에 갱신됐으면 이어받을지 묻는다.

배경: 한 PC의 스냅샷과 작업 공간은 하나뿐이다.

대가와 대응한 작업을 끝내고 다음으로. 남은 lock은 보유자 확인 뒤 강제 해제.
근거 문서contracts.md §3.2 lock

8push 전 확인 화면과 승인 지문

안전 · 설계 초기

결정push 직전에 변경 파일·diff·검증 결과·커밋 메시지를 한 번에 보여주고 승인받는다. 승인한 내용의 지문(approved_hash)과 실제 push가 다르면 거부한다.

배경: 사람이 본 것만 팀 DB에 올라가야 한다.

대가와 대응확인 화면은 요약하지 않고 그대로 보여주게 해 Claude가 내용을 바꿔 말할 여지를 없앴다.
근거 문서12-principles.md, 07-workflow.md Step 8

9Jira는 읽기만, 원문은 격리

안전 · 설계 초기

결정허용한 Jira 읽기 도구만 통과시키고(허용 목록), Jira 응답 원문은 PC 작업 폴더에 두고 Claude에게는 마스킹 요약만 보인다. 처리 실패 시 원문 대신 오류.

배경: Jira 본문에는 개인정보와, Claude를 조종하려는 문장이 섞일 수 있다.

대가와 대응결과를 Jira 댓글로 남길 수 없다 → 확장 아이디어도 다른 채널로 전달하도록 설계.
근거 문서08-safety.md 규칙 2·9

10최종 방어선은 서버 브랜치 보호

안전 · 설계 초기

결정Claude hook과 git hook은 빠른 차단·설명용(최선 노력)이고, main 보호와 CODEOWNERS 필수 리뷰는 GHE 서버가 강제한다.

배경: PC의 장치는 명령 형태를 다 볼 수 없고 설정으로 끌 수 있다.

대가와 대응서버 보호를 설정할 수 없는 GHE면 git hook 방식 채택부터 다시 결정한다.
근거 문서08-safety.md §9, 06-collaboration.md §6.1

11fixed는 수정 검증 통과로만

판정 · 10/04

결정수정 상태 fixed는 verify-fix 통과로만. 코드·설정 수정 유형은 재현 시나리오 흔적이 필수이고, 흔적 규칙이 없는 비코드 유형만 사용자 확인으로 판정해 기록에 남긴다.

배경: "고쳤다"는 말만으로 닫으면 재발을 놓친다.

대가와 대응방치 → 월간 리뷰가 30일 초과 건을 기록자와 함께 표시(10/09), 알림·자동 검증은 확장 후보.
근거 문서DRAFT_NOTES 결정 (e), 05-verification.md §5.12

12건너뛴 검증은 통과가 아님

판정 · 설계 초기

결정fixture가 없어 못 돌린 검증은 skipped로 따로 표시하고 리뷰 대상으로 붙인다.

배경: "통과" 표시를 믿을 수 있어야 리뷰가 빨라진다.

대가와 대응fixture 없는 원인 수를 STATS와 월간 리뷰로 관리.
근거 문서12-principles.md, contracts.md §상태 값

13자동 게시는 별도 품질 기준으로만

판정 · 10/01

결정앞으로 자동화(RF-8)를 하더라도 confidence 점수가 아니라 별도 품질 게이트를 통과할 때만 자동 게시한다.

배경: 점수는 규칙 일치 정도이지 진단 확신도가 아니다.

대가와 대응자동화는 파일럿 뒤 사내 환경을 안 다음에 설계.
근거 문서DRAFT_NOTES 결정 (b)

14사외에서 초안, 사내에서 보완

개발 · 10/01 · 10/04 · 10/05

결정사외에서 합성 데이터로 최대한 완성·안정화하고, 사내에서는 실제 값만 채운다. 사내→사외로는 사람이 직접 쓴 사내 정보 없는 문장만 가져온다.

배경: 사내 정보를 밖으로 가져올 수 없고, 사내 작업 시간은 비싸다.

대가와 대응실제 로그 문구·정확도는 사내 S-4·S-5 전에는 파일럿에 쓰지 않는다. 반입 전 스키마는 직접 고치고, 배포 뒤에는 항상 버전을 올린다(결정 d).
근거 문서DRAFT_NOTES 결정 (a)·(d)·(f), 15-local-draft.md
