§1 왜 만들었나

같은 이슈를 매번 처음부터 분석하고 있었다

문제

  • 비슷한 증상의 이슈를 사람마다 로그부터 다시 읽는다
  • 원인과 해결책이 개인 메모·Jira 코멘트에 흩어져 있다
  • "전에 본 것 같은데" 이슈 번호를 찾기 어렵다
  • 고친 뒤 재발했는지 확인할 기준 로그가 없다

목표

  • 로그 판정을 규칙(시그니처)으로 남겨 누구나 같은 결과를 얻는다
  • 원인·해결책·Jira 이력을 한 레포(이슈 DB)에 쌓는다
  • 기록은 사람이 확인한 것만, PR과 리뷰로 들어간다
  • 수정 후 로그로 재발 여부를 회귀 테스트로 지킨다

분류 계층: 카테고리(data · call · network · sim · sms · ims) > 이슈 유형(증상) > 원인 + 해결책 + Jira 이력

핵심은 "분석 결과를 재사용 가능한 규칙으로 바꾼다"입니다. Claude가 똑똑하게 추측해 주는 도구가 아니라, 팀이 확인한 규칙으로 판정하고 Claude는 설명과 정리를 돕는 구조라는 점을 먼저 강조합니다.
§2 전체 구조

한 장으로 보는 흐름

파란 상자 = 스크립트가 결정적으로 판정, 주황 상자 = 사람이 결정, 점선 = 이슈 DB에서 읽어 오는 규칙.

위 줄은 분석, 아래 줄은 기록입니다. 판정(파란 상자)은 전부 파이썬 스크립트가 하고, 같은 입력이면 누가 돌려도 같은 결과가 나옵니다. 주황 상자 두 곳에서 반드시 사람이 결정합니다.

내 PC

  • config.yaml 사용자 설정

  • work/<KEY>/ 리포트·계획·임시 worktree

내 이슈 DB clone은 도구가 건드리지 않습니다. 분석은 스냅샷에서, 쓰기는 임시 worktree와 도구 브랜치(tt/*)에서 합니다. 내 clone에는 main이고 깨끗할 때 fast-forward만 합니다.

자주 받는 질문이 "내 clone에서 브랜치를 바꿔 놨는데 괜찮나"입니다. 괜찮습니다. 도구는 clone을 읽기만 하고, 작업은 work 디렉토리 아래에서 합니다. 작업 계획과 lock은 PC에만 있어서 다른 PC로 따라오지 않습니다.

Jira 원문은 없다

구조화 필드(모델·SW·Android 버전 등)와 사용자가 확인한 한 줄 요약만 저장합니다.

README와 STATS는 손으로 고치지 않습니다. 고쳐도 다음 생성 때 덮이고, 커밋 hook이 막습니다. fixture는 회귀 테스트의 기준이 되는 로그 조각이라 반드시 마스킹돼 있습니다. 예시의 ID와 Jira 키는 모두 가상의 값입니다.

이슈 DB에 쓰는 커맨드는 시작할 때 세션 lock을 잡고 끝나는 모든 경로에서 풉니다. 한 사람이 동시에 두 작업을 할 수 없습니다.

§4 커맨드별 사용법

analyze: 기본형과 자주 쓰는 옵션

/telephony-triage:analyze ABC-12345 ~/logs/radio.txt ~/logs/main.txt
옵션언제
--analysis-only결과만 보고 이슈 DB에 기록하지 않을 때. 리포트로 끝나고 lock을 풂
--dry-run기록 흐름을 확인 화면까지 연습. push 없음, gh 인증 불필요
--more-logs <로그…>첫 분석 뒤 로그를 더 받았을 때. 이전 로그 뒤에 붙여 전체를 다시 계산
--code <프로필|경로>분석할 소스 트리(Android 16/17 등). 없으면 물어봄
--failed-step · --steps-file시험 실패 스텝·절차. 분석 구간과 순위 참고만, S/C에는 안 씀
--jira-file <yaml>Jira 대신 파일. --dry-run·--analysis-only와만

로그 자리에 bugreport(.zip/.txt)를 주면 logcat 섹션만 꺼내 씁니다. --analyzer/--explore는 다음 장.

로그는 채팅에 붙이지 말고 파일 경로로 주세요. 붙이면 마스킹 전 원문이 대화에 들어갑니다. 처음 몇 번은 --analysis-only로 결과만 보는 것을 권합니다.

분석 전용으로 본 뒤 기록하고 싶으면 옵션 없이 다시 실행하면 됩니다. 입력이 같으니 분석은 재사용되고, 건너뛴 사전 질문만 그때 나옵니다. --analysis-only와 --dry-run은 함께 쓸 수 없습니다.
§4 커맨드별 사용법

record와 search

record: 직접 해결한 이슈 남기기

/telephony-triage:record ABC-12345 --cause DATA-001-02 /telephony-triage:record ABC-12346 # 대화형
  • 로그 분석·매칭 없이 기록. 검증과 PR 절차는 analyze와 같다
  • 확인 화면과 PR에 "수동 기록" 표시
  • fixed는 기록 불가. fix-submitted까지만
  • 새 원인·유형이면 시그니처 필수, fixture가 없으면 검증은 "건너뜀"

search: 전에 본 이슈 찾기

/telephony-triage:search 데이터 안 붙어, 이슈 번호 알려줘 /telephony-triage:search ABC-12345 /telephony-triage:search DATA-001-02
  • 증상 문장·키워드·Jira 키·ID 모두 받음
  • 유형·원인·해결책·수정 상태와 Jira 번호 요약
  • 옛 ID → 새 ID 연결도 따라감
  • 읽기 전용, lock 없음
record는 지름길이 아닙니다. 쓰기 경로와 검증이 analyze와 똑같고 로그 분석만 건너뜁니다. 분석을 시작하기 전에 search로 이미 기록된 이슈인지 먼저 보는 습관을 권합니다.

§5 판정 읽는 법

S와 C, 두 개의 0/1

S = 증상(유형) 시그니처 충족, C = 원인 시그니처 충족. 판정은 이 두 값으로 합니다.

C = 1 원인 확인
C = 0 원인 미확인
S = 1
증상 확인
원인 후보증상과 원인 근거가 같은 슬롯·같은 시간 창에서 결합될 때만
유형 일치, 원인 미확인새 원인일 수도. 탐색 분석을 제안받음
S = 0
분석에서는 후보 아님증상이 확인된 유형의 원인만 평가. 회귀 검증에서는 오탐으로 잡힘
후보 없음"후보 없음" 절에 설명 기반 유사 유형과 타임라인 요약
분석 모드는 2단계입니다. 먼저 모든 유형의 S를 보고, S=1인 유형 안에서만 원인 C를 봅니다. 듀얼 SIM이면 같은 슬롯의 근거끼리만 묶습니다. 회귀·검증 모드는 반대로 모든 원인의 C를 독립적으로 봐서 다른 유형 로그에서의 오탐을 잡습니다.
§5 판정 읽는 법

점수와 순위는 정렬용이다

score = min(1, 증상가중치×S + 원인가중치×C + bonus) bonus = 근접(근거 시각이 발생 시각에 가까울수록) + 키워드(Jira 텍스트와 원인 제목·태그)

보너스는 동점 정렬만

S=C=1이면 점수가 1로 포화돼서 보너스는 같은 점수 안의 순서만 바꿉니다.

일치 수준 ≠ 확신도

"높음·중간·낮음"은 규칙이 얼마나 맞았는지의 구간입니다. 진단 확신도가 아니고 자동 게시 근거로 쓰지 않습니다.

실패 스텝은 순위만

스텝 기준 우선 유형은 순위 키에만 더해지고 score·S·C는 그대로입니다.

회귀·검증 모드는 보너스 0, 피드백 가중치 끔. 판정은 S/C 값만 봅니다.

1위와 2위의 점수 차이를 확신의 차이로 읽지 마세요. 실제 판단은 S와 C, 그리고 근거 로그를 보고 합니다. 가중치 설정을 바꿔도 회귀 결과가 바뀌지 않도록 일부러 이렇게 만들었습니다.

버전 불일치 → 읽기 전용분석은 계속, 계획 저장까지만. 플러그인 업데이트 또는 메인테이너에게 마이그레이션 요청
사내 기본값 없음 (S-3 미완료)설치본에 사내 설정이 없음. 직접 고치지 말고 메인테이너에게
hook: core.hooksPath가 .githooks가 아님setup 재실행(config.py install-hooks)
대부분은 doctor 표에서 미리 보입니다. lock은 이전 세션이 비정상 종료했을 때 남는데, 다른 창에서 작업 중인 게 아닌지 꼭 확인하고 푸세요. 메시지 문구는 실제 도구 출력에서 가져왔습니다.
§7 오류가 났을 때

메시지뜻과 다음 행동
해석한 logcat 줄이 없습니다 — 로그 범위 밖이 아니라 형식·인코딩 문제파싱 0줄. 로그 형식이나 인코딩 확인. UTF-8과 BOM 있는 UTF-16은 읽음

"로그 범위 밖"과 "매칭 없음"을 구분하는 게 핵심입니다. 범위 밖인데 매칭 없음으로 읽으면 엉뚱한 결론이 납니다. 발생 시각 근처 로그가 아예 없는 경우라면 로그를 더 받아 --more-logs로 붙이세요.
§8 안전 장치

마스킹: 저장되는 것은 토큰뿐

# 합성 예시 전 imsi=001010123456789 msisdn=+15550100 ip=10.0.0.5 mCi=12345 후 imsi=<IMSI#1> msisdn=<MSISDN#1> ip=<IP#1> mCi=<CELL#1>
  • IMSI·IMEI·ICCID, 전화번호, SIP URI, 셀 ID, IP·MAC, 인증 값 등을 토큰으로 바꾼다
  • 같은 값은 같은 번호라서 "셀이 바뀌었다" 같은 비교는 그대로 된다
  • 파싱·매칭부터 마스킹된 텍스트로 돈다. 시그니처도 마스킹 기준으로 쓴다
  • Jira는 원문을 모델에 넣지 않고, 구조화 필드와 확인한 요약만 저장

마스킹 안 된 내용이 있으면 커밋이 막힙니다(커밋 hook + pre-commit).

사람 이름은 마스킹 패턴으로 잡히지 않습니다. 그래서 Jira 원문 자체를 저장하지 않는 쪽으로 설계했습니다. 한 줄 요약을 확인할 때 이름이 들어가 있지 않은지 한 번 더 봐 주세요.
§8 안전 장치

guard hook과 사람이 승인하는 곳

자동으로 막는 것 (hook 10종 중)

  • Jira 쓰기 도구 호출. 허용 목록의 읽기 도구만
  • main 대상 push, 승인 토큰 없는 push
  • --no-verify 같은 hook 우회 커밋
  • Claude가 내 이슈 DB clone 파일을 직접 편집
  • 로그 원문을 통째로 읽는 명령(cat 등)

반드시 내가 승인하는 것

  • 분류 확정, 새 유형·원인
  • 시그니처·파서 규칙 추가, also_allowed
  • 수정 상태 변경
  • drift 항목 선택, 오래된 작업 정리
  • push 전 확인 화면 (push마다 권한 프롬프트도 뜸)

로컬 장치는 우회될 수 있어서 GHE 브랜치 보호(main 직접 push 금지, CODEOWNERS 필수 리뷰)가 서버에서 최종 방어선입니다.

hook 판정은 최선 노력 방식이라 모든 우회를 막지는 못합니다. 그래서 서버 측 브랜치 보호가 전제입니다. 사용자는 이 장치들을 끄려고 하지 말고, 막히면 메시지를 그대로 공유해 주세요.

§9 관리와 운영

유형·원인·시그니처를 바꾸는 절차

초안

새 원인·유형, 시그니처, 파서 규칙(parser-rules/). 시그니처는 마스킹된 로그 기준

fixture

근거 주변 최소 구간을 잘라 마스킹. 정상 로그는 음성 fixture

검증

db_verify R1~R6, db_regress --all

생성 파일

db_build.py --write로 README·STATS·CHANGELOG 재생성

PR → 리뷰

파서 규칙·공통 변경은 메인테이너 리뷰

엔진과 규칙은 분리돼 있다

새 유형은 코드가 아니라 규칙 파일로 추가합니다. 팀원이 PR만으로 파서를 넓힐 수 있습니다.

직접 편집할 때

편집 → db_build --write → validate → 커밋 → push. 생성 파일은 손대지 않습니다.

대화로 분석하다가 새 원인이 나오면 이 절차를 도구가 대신 밟아 줍니다. 직접 편집은 리뷰 정리나 대량 수정 때 씁니다. 어느 쪽이든 검증과 생성 파일 규칙은 같습니다.
§9 관리와 운영

버전 업그레이드와 스키마

상황플러그인 동작할 일
이슈 DB 스키마가 지원 범위 안정상—
이슈 DB가 플러그인보다 새 버전읽기 전용 분석만플러그인 업데이트
이슈 DB가 플러그인보다 옛 버전쓰기 막힘, 분석 가능메인테이너 마이그레이션
생성기 버전 불일치쓰기 막힘플러그인 업데이트

스키마 올리기(메인테이너): migrate/schema-v<N> 브랜치 → migrate --to <N> → db_build --write → validate → 승인 후 커밋 → 직접 PR. 머지 뒤 남은 PR은 sync-pr이 계획을 새 스키마로 올립니다.

버전 판정은 config.py check가 하고 doctor의 compat 행에 나옵니다. 마이그레이션 PR을 머지할 때는 다른 PR 머지를 잠시 멈추도록 공지합니다.
§9 관리와 운영

사내 적용 단계 S-0 ~ S-7

사외에서 모의 환경으로 구현을 끝냈고, 사내에서는 실제 값만 끼워 맞춥니다. 아래는 모두 예정입니다.

S-0선택. 실제 로그 형식 선행 확인, 설정 초안 제안 도구
S-1사내 값 조사, 평가 기준 합의
S-2사내 Claude Code 동작 확인
S-3사내 설정(site-defaults) 입력
S-4a기존 파서 포팅, 분류 import, 분석 스킬 연결
S-4카테고리별 실제 로그로 규칙 교체
S-5dry-run·샌드박스 PR, 정확도·오류율 게이트
S-6남은 검토 항목 정리
S-7배포, 카테고리별 파일럿

data 규칙은 실제 단말 로그와 AOSP 소스로 형식을 확인했습니다. 나머지 카테고리의 규칙은 아직 placeholder이고, S-4에서 실제 태그·문구로 바뀌기 전에는 결과에 "placeholder 규칙"이 표시됩니다.

파일럿은 카테고리별 10~20건, 첫 월간 리뷰 뒤 전체 확대를 결정합니다. 지표는 PR까지 시간, 중도 취소 비율, 작업당 저장된 답 수, PR 연결 미확인 건수입니다.

여러분이 이 플러그인을 실제로 받는 시점은 S-7 파일럿입니다. 그 전에 S-5에서 과거 해결 Jira 20~30건으로 정확도를 미리 확인합니다. 파일럿 동안 불편한 점을 모아 주시면 반입 뒤 개선 항목으로 넣습니다.
