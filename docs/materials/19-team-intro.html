Telephony 이슈 원인은 스크립트가 판정하고, 팀의 판단은 이슈 DB에 쌓입니다

Jira 이슈와 logcat을 받아 시그니처로 원인 후보와 해결책을 찾고, 엔지니어가 확인한 결과를 사내 GitHub 이슈 DB에 PR로 남깁니다. Jira는 읽기와, 확인 화면에서 승인한 결과 코멘트 추가만 하고, 저장되는 로그는 모두 마스킹됩니다.

“진짜 고쳐졌나?”

CL이 머지돼도 수정 빌드에서 재발이 없는지 확인한 기록이 남지 않아, 회귀를 늦게 발견합니다.

작동 방식

분석, 확인, 기록

1 · 분석

Jira + logcat → 원인 후보

Jira 읽기(즉시 마스킹) → 로그 파싱 → 시그니처 매칭 → 코드 경로 분석. 리포트에 후보, 근거 로그, 해결책, 수정 상태, 기존 사례 Jira가 나옵니다.

스크립트가 판정 · Claude가 설명
2 · 확인

“이 분류가 맞나요?”

엔지니어가 고릅니다: 1위 후보 / 다른 원인·유형(기존 원인·새 원인·새 유형) / 원인 미확정 / 기록하지 않음. 새 규칙은 R1~R6(R6은 선택) 자동 검증을 거칩니다.

사용자 결정
3 · 기록

승인 → 브랜치 PR → 오너 머지

push 전에 변경 파일, README 미리보기, 검증 결과, 커밋 메시지를 보여주고 승인을 받습니다. 카테고리 오너가 리뷰 후 머지합니다.

main 직접 push 없음
맞는 규칙이 없을 때

처음 보는 원인도 팀 지식이 됩니다

  1. 1스크립트가 “후보 없음”(또는 유형만 맞고 원인 미확인)을 알리고, “후보 없음”이면 비슷한 유형 · 오류 타임라인 요약도 보여 줍니다.
  2. 2원하면 Claude 탐색 분석이 마스킹된 타임라인과 (코드 경로를 골랐으면) 소스로 원인 가설 1~3개를 근거 · 반대 근거와 함께 냅니다. 가설은 점수 · 분류에 쓰지 않습니다.
  3. 3엔지니어가 가설을 채택하면 새 원인 · 새 유형 초안의 출발점이 되고, 보류하면 “원인 미확정”으로 남길 수 있고, “기록하지 않음”도 고를 수 있습니다.
  4. 4시그니처 · 파서 규칙 초안과 마스킹된 로그 조각(fixture)을 만들어 확인받고, R1~R5(추가 로그를 주면 R6도)로 기존 분류를 깨지 않는지 자동 검증합니다.
  5. 5승인 · PR · 담당자 리뷰를 거쳐 병합되면, 다음부터 같은 로그는 스크립트가 그 원인을 후보로 바로 찾습니다.

모르던 이슈 하나가 다음에는 자동으로 판정되는 규칙으로 쌓입니다. 탐색 분석은 토큰을 더 쓰므로 실행 전에 묻습니다(비용).

장치동작
마스킹IMSI·전화번호·SIP URI·인증 값 등을 자동 마스킹합니다. 같은 값은 같은 번호(<CELL#1>)로 바뀌어 비교 로직은 유지됩니다. 마스킹 안 된 커밋은 hook이 차단합니다.
원문 격리Jira 응답 원문은 모델 컨텍스트에 넣지 않고 내 계정만 읽을 수 있는 작업 폴더(권한 700)에 잠깐 둔 뒤 읽고 지웁니다. 모델에는 마스킹된 요약만 보입니다. 처리에 실패하면 원문 대신 오류를 돌려줍니다.
저장 범위이슈 DB에는 Jira 구조화 필드와 사용자가 확인한 한 줄 요약만 남습니다. 요약·설명·코멘트 원문은 저장하지 않습니다.
승인 후 PR이슈 DB 쓰기는 확인 화면 → 승인 → 브랜치 PR입니다. main 대상 push와, 승인 지문(승인 해시)이 맞지 않는 push는 pre-push hook이 거부합니다. 서버 측 브랜치 보호와 CODEOWNERS 필수 리뷰를 함께 켜도록 안내합니다.
Jira 쓰기 제한허용 목록의 읽기 도구와, 확인 화면에서 승인한 본문의 코멘트 추가만 통과합니다(본문이 바뀌면 다시 승인). 필드 수정·상태 전환·이슈 생성은 모두 거부합니다.
작업 격리분석은 별도 읽기 스냅샷에서 합니다. 사용자의 이슈 DB clone은 브랜치도 파일도 바꾸지 않습니다. 같은 이슈 DB(플랫폼)의 동시 작업은 세션 lock으로 막습니다.

확장

이걸 바탕으로 넓힐 수 있는 것

이슈 DB에는 "어떤 증상이 어떤 원인이었고, 어떻게 고쳤고, 정말 고쳐졌나"가 쌓입니다. 이 데이터와 이미 있는 판정 · 검증 흐름을 다른 플랫폼과 다른 일에도 쓸 수 있습니다. 맨 위 플랫폼 확장은 뼈대가 들어가 있고, 그 아래 "아이디어" 표시 묶음은 아직 만들지 않았습니다(도입과 파일럿 뒤의 후보, 확정 계획 아님).

다른 플랫폼으로 넓히기 뼈대 있음

Android 말고 oFono 같은 다른 Telephony 스택의 이슈도 같은 도구, 같은 검증, 같은 리뷰 절차로 다룰 수 있게 나눠 두었습니다. 플랫폼마다 로그를 읽는 부분과 이슈 DB만 따로 두고, 원인 판정 · 기록 전 검증 · 승인과 PR 흐름은 함께 씁니다. 지금 실제로 지원하는 플랫폼은 Android입니다.

이미 있는 것
  • 플랫폼 폴더 분리: 로그 해석 · 파서처럼 플랫폼마다 다른 코드는 platforms/<이름>/ 폴더 하나에 둡니다. 매칭 · 기록 전 검증(R1~R6) · PR · 안전 관문 같은 핵심 스크립트는 특정 플랫폼 코드를 직접 부르지 않고, 이 규칙은 테스트로 지킵니다.
  • 플랫폼마다 이슈 DB를 따로 두고 --platform으로 고릅니다(동작 · 원인 · 해결책이 플랫폼마다 달라서). 고른 플랫폼과 이슈 DB가 다르면 멈춥니다. 작업 잠금도 플랫폼별이라 Android와 oFono 작업을 동시에 할 수 있습니다.
  • oFono 뼈대: 로그 형식은 가정(journald · syslog 모양)이며, 합성 로그로 파싱 → 매칭 → 회귀까지 플랫폼 전환을 테스트로 확인합니다.
새 플랫폼에 필요한 것
  • 로그 줄 해석과 파서 백엔드(플랫폼 폴더 하나)
  • 팀 설정에 플랫폼 이름 등록(platform.enabled)
  • 그 플랫폼의 이슈 DB 레포: 카테고리 · 태그 · 파서 규칙(뼈대 생성 도구 있음), 그다음 실제 로그로 원인 · 유형 채우기
  • 실제 로그 형식 확인 — oFono도 사내 로그를 받은 뒤 채웁니다

이미 쌓인 데이터를 더 쓰기 아이디어 · 아직 만들지 않음

  • 릴리스 품질 대시보드: 릴리스 회의에서 빌드에 남은 열린 원인 · 회귀 의심을 바로 봄 — STATS(모델 · SW · 버전별 분포)와 원인 수정 상태 위에
  • 테스트 케이스 개선: 자주 실패하는 테스트 스텝을 찾아 재현 조건을 보강 — Jira 실패 스텝 기록 위에(판정에는 쓰지 않음)
  • 신규 입사자 교육: 실제 해결 사례로 로그 보는 법을 익혀 시니어 시간을 아낌 — 마스킹된 fixture와 dry-run 위에
  • 벤더 · 모뎀 쪽 전달 리포트: "AP 문제인지 모뎀 문제인지"를 근거와 함께 빨리 넘김 — RIL 요청 추적 결과 위에(보낼지는 사람이 결정)

사람이 챙기던 일을 자동으로 아이디어 · 아직 만들지 않음

  • 수정 검증 자동 실행: 고친 버그가 정말 고쳐졌는지 자동 확인 — 테스트 장비 로그 + verify-fix(반영은 사람 승인)
  • 방치 · 급증 알림: 월간 리뷰를 기다리지 않고 할 일이 담당자에게 감 — 리뷰 리포트(읽기 전용) + 알림 채널
  • 재발 조기 경보: 고친 원인이 다시 나오면 수정한 사람에게 바로 알림 — 이미 있는 회귀 의심 판정 + 알림
  • Jira 접수 시 1차 분석: 담당자가 이슈를 열 때 후보와 근거가 준비됨 — 기록하지 않는 분석 전용 실행 위에(Jira에는 쓰지 않음)

보기 쉽게 아이디어 · 아직 만들지 않음

  • 규칙 변경 영향 화면: 파서 규칙 리뷰가 빨라짐 — 이미 있는 바뀐 이벤트 계산(R5) 위에 화면만 새로
  • 읽기 전용 웹 포털(보류 중): QA · 기획 · 관리자도 설치 없이 사례 검색 · 통계 — 이슈 DB · STATS, 마스킹된 DB만 노출, 쓰기는 지금처럼 PR로만

같은 팀 안에서, 다른 도메인으로 일부 있음

  • 지금 가능 · 같은 팀 안에서: 새 카테고리 · 유형 · 원인은 코드가 아니라 규칙 파일로 추가. 사내 파서 · 분석 스킬 연결, Android 버전별 소스 프로필, 이슈 트래커 선택(Jira 기본, GitHub Issues는 실험적 — 모의 환경으로만 검증, 알려진 한계 있음)
  • 아이디어 · 다른 도메인의 팀(범용판): 위 플랫폼 확장(같은 Telephony 도메인)과 다릅니다. 오디오 · 카메라처럼 로그로 원인을 가리는 팀이 검증된 판정 · 승인 · 안전장치를 재사용 — 공통 코어에 도메인 팩(카테고리 · 태그 · 파서)을 얹음. Android · RIL에 묶인 곳을 떼어 내는 설계가 먼저이고 지금은 보류. 판정 결정성 · 사람 승인 원칙은 그대로

"뼈대 있음"은 플랫폼 분리와 oFono 뼈대가 들어갔다는 뜻이며 oFono 지원이 완성됐다는 뜻은 아닙니다. 대상 플랫폼과 범용판 착수 시점은 파일럿 뒤에 정합니다. 어떤 아이디어든 판정은 스크립트가 하고, 기록 · Jira 코멘트는 사람이 승인하며, 다루는 값은 마스킹된 것뿐이라는 원칙을 지킵니다. 아이디어마다 흐름 · 필요한 것 · 시점과 고를 때 지킬 것은 확장 아이디어(지킬 것)에 있습니다.

FAQ

자주 묻는 질문

LLM이 원인을 결정하나요?

아닙니다. 분류 후보와 점수는 파서·매처·검증 스크립트의 출력으로 정해집니다. Claude는 리포트 설명, 초안 작성, 확인 질문을 맡고, 분류 확정은 엔지니어가 합니다.

Jira에 코멘트나 상태 변경을 하나요?

상태 변경은 하지 않습니다. 분석 결과 코멘트는 엔지니어가 확인 화면에서 본문을 승인했을 때만 1건 올리고(본문이 바뀌면 다시 승인), 그 밖의 Jira 도구 호출은 hook이 거부합니다.

이슈 DB에는 어떤 정보가 남나요?

마스킹된 로그 구간(fixture), 원인·해결책·시그니처, Jira 구조화 필드(모델, SW, Android 버전 등)와 엔지니어가 확인한 한 줄 요약입니다. Jira 본문·코멘트 원문은 저장하지 않습니다.

등록된 규칙에 맞는 원인이 없으면요?

“후보 없음”으로 알리고 비슷한 유형과 타임라인 요약을 보여줍니다. 원하면 Claude 탐색 분석이 마스킹된 타임라인과 (코드 경로를 골랐으면) 소스로 원인 가설 1~3개를 근거·반대 근거와 함께 제시합니다. 가설은 점수·분류에 쓰지 않고, 엔지니어가 채택하면 새 원인·새 유형 초안의 출발점이 됩니다. 등록하면 시그니처와 파서 규칙 초안, 마스킹된 fixture를 함께 만들고, 기존 분류를 깨지 않는지 R1~R5(추가 로그를 주면 R6도)로 자동 검증한 뒤 PR로 올립니다. 흐름은 작동 방식의 “처음 보는 원인도 팀 지식이 됩니다”에 있습니다.

사내에 이미 쓰는 로그 파서가 있습니다.

검증된 판별 로직은 코드 그대로 포팅해 연결하고, 포팅 전 골든 출력과 결과가 같은지 테스트합니다. 포팅이 어려우면 기존 파서를 그대로 실행하고 출력만 변환하는 어댑터 방식도 있습니다.

Android가 아닌 플랫폼이나 다른 팀에서도 쓸 수 있나요?

다른 Telephony 플랫폼은 그렇게 나눠 두었습니다. Android 전용 코드는 플랫폼 폴더로 분리돼 있어, 새 플랫폼은 로그 해석 부분과 그 플랫폼의 이슈 DB를 더하면 판정 · 검증 · PR 흐름을 그대로 씁니다. 플랫폼마다 이슈 DB를 따로 두고 --platform으로 고릅니다. 지금 실제로 지원하는 플랫폼은 Android이고 oFono는 뼈대 단계입니다. 다른 도메인 팀을 위한 범용판은 아직 아이디어(보류)입니다. 자세한 내용은 넓힐 수 있는 것에 있습니다.
