1

플랫폼 정하기

이후 모든 단계가 이 결정을 따릅니다. 작업 폴더와 lock을 만들기 전에 정합니다.

켠 플랫폼이 둘 이상이면 스크립트가 로그 앞부분(파일마다 최대 200줄)을 각 플랫폼의 줄 형식으로 검사합니다. 한 플랫폼만 맞으면 그걸로 진행하고, 결과 알림에 로그 형식으로 oFono 선택 (기본 Android 대신), 리포트 머리에 - 플랫폼: oFono (로그 형식으로 선택)을 남깁니다. 형식을 모르는 파일이 섞여 있으면 나머지로 정하고 그 수를 알립니다. Android만 켠 설치는 검사도 파일 읽기도 없이 예전 그대로입니다.

사용자가 플랫폼을 말하면(--answer platform= > --platform 순) 그것이 우선합니다. 개인 설정의 기본 플랫폼은 기본값일 뿐이라 분명한 로그 형식에 집니다. 로그 형식이 둘 이상이거나 단서끼리 다르거나 말한 플랫폼과 로그가 다르면 작업을 시작하기 전에 묻고, 로그를 주지 않았으면 켠 플랫폼 모두의 로그 폴더에서 고르게 합니다. 결과에 platform이 나오면 이후 명령에 같은 --platform이 붙습니다.

ANDROID 로그 모양

09-20 14:32:09.100 1234 5678 I RILJ : [0123]> SETUP_DATA_CALL [PHONE0]

logcat 줄. 연도 없는 날짜, pid·tid, 레벨, 태그가 있습니다. bugreport(zip 포함)도 Android로 봅니다.

OFONO 로그 모양 (형식 가정)

2026-09-20T14:32:09.100+09:00 host ofonod[812]: src/network.c:… 2026-09-20T14:32:09.140+09:00 host daemon-a[640]: …

journald/syslog 줄. 줄마다 어느 데몬인지(ident)가 붙습니다. 실제 형식은 사내 로그로 확인할 항목(S24)입니다.

한 번 묻고, 답은 기억합니다

답한 플랫폼은 그 작업이 다음 질문(코드 경로 등)에서 멈춰 있는 동안 남아, 다음 실행에 답을 다시 붙이지 않아도 되묻지 않습니다. 단, 그 질문이 이 이슈의 가장 늦은 활동일 때만입니다. 답한 뒤 다른 플랫폼 쪽에서 질문이 나왔거나 분석이 끝났다면 사용자가 옮겨 간 것으로 보고 옛 답은 쓰지 않습니다.

상황도구가 하는 일
Android 로그 + oFono 로그를 섞어 줌, 플랫폼 말 없음묻는다 고르면 그 플랫폼으로 진행
위에서 oFono로 답했고, 코드 질문 뒤 답 없이 다시 실행잇는다 oFono 작업 그대로
"android로 해" + oFono 형식 로그(자동으로 고른 oFono 작업이 있어도)묻는다 답으로 정한 적 없는 작업은 지정을 덮지 않는다
자동 선택 → 플랫폼을 바로잡아 답함 → 다음 실행엔 코드 답만잇는다 바로잡은 쪽, 질문이 되풀이되지 않는다
android로 답한 뒤 oFono로 옮겨 진행, 나중에 다시 Android 형식 로그 + oFono 지정묻는다 옛 android 답은 더 이상 쓰지 않는다
답한 작업이 이미 끝났고 같은 이슈를 다시 실행묻는다 답은 질문에서 멈춘 동안만 남는다

Jira 이슈 원문은 hook이 기본 플랫폼 작업 폴더에 받아 두므로, 고른 플랫폼이 다르면 그 원문을 이 작업 폴더로 옮겨 씁니다.

2

로그 읽기

줄을 시각·태그·요청 짝이 붙은 이벤트로 바꿉니다.

파서 백엔드가 플랫폼마다 따로 있습니다(reference / ofono_reference 0.0.2). 시계가 튀거나 재부팅된 곳은 끊어서 보고, 시각 범위 밖 로그는 "로그 범위 밖"으로 따로 알립니다. 이슈 DB·매칭에 쓰는 값은 모두 마스킹됩니다.

ANDROID

  • logcat 여러 버퍼, bugreport 묶음이면 필요한 섹션만 꺼냄
  • RILJ 요청과 응답을 serial로 짝지어 지연·무응답·오류 표시
  • 슬롯 표기([PHONE0])로 SIM 구분

OFONO

  • 모든 데몬이 한 스트림에 섞여 오고, ident가 태그가 됨
  • 데몬 목록은 팀 설정 components에 둠(예: daemon-a, daemon-b)
  • 데몬 사이 요청·응답 짝은 팀이 정규식으로 정의(기본 꺼짐). 다른 데몬의 응답도 같은 serial이면 짝. 이름·오류 값은 식별자 모양만 싣고 한 번 더 마스킹
  • 데몬별 메시지 하위 형식, 모듈 단위 태그 나누기(split_tag)는 선택
3

이슈 DB와 비교

이미 알려진 원인의 시그니처가 이 로그에 있는지 봅니다.

판정은 스크립트가 합니다. 원인마다 시그니처가 로그에서 확인됐는지(C)와 증상이 맞는지(S)를 보고 순위를 냅니다. 세션 플랫폼과 이슈 DB가 선언한 플랫폼이 다르면 바로 멈춥니다(platform-mismatch).

ANDROID 이슈 DB

  • 지금 쓰는 이슈 DB 레포
  • 카테고리·태그 매핑은 그 DB의 parser-rules/tags.yaml

OFONO 이슈 DB

  • 새 레포 하나, platform: ofono 선언
  • oFono와 함께 도는 데몬 이슈도 모두 여기에. 데몬 구분은 카테고리와 tags.yaml(ident → 카테고리)
4

코드 근거 찾기

로그 문구가 어느 소스에서 나왔는지 찾아 원인 설명을 받칩니다.

사용자가 고른 소스 루트에서만 찾습니다. 근거를 못 찾으면 "코드 근거 없음"으로 밝힙니다.

ANDROID

  • AOSP 소스 루트 하나(aosp), 버전은 빌드 설정에서 추정

OFONO

  • ofono 주 루트는 필수, 데몬마다 소스 루트를 더 둘 수 있음
  • 데몬별 버전은 참고로만 보여줌(component_versions)
5

규칙이 없을 때 가설 분석

이슈 DB로 원인이 안 잡히면 스킬이 가설을 세웁니다. 토큰을 더 쓰므로 먼저 묻습니다.

결과는 리포트의 "추정" 칸에만 들어가고 판정·순위에는 쓰지 않습니다. 다른 플랫폼의 스킬이나 자료로 넘어가지 않습니다.

ANDROID

  • 심층 분석(5-1): 설정 최상위 analyzers.<카테고리>의 분석 스킬
  • 탐색 분석(5-2): Android 참고 자료(log-tags · ril-requests · fail-causes)

OFONO

  • 심층 분석(5-1): platforms.ofono.analyzers.<카테고리>만. 없으면 제안하지 않고 리포트에 "해당 없음"
  • 탐색 분석(5-2): triage.py explore가 알려 주는 reference/platforms/ofono/ 자료만 읽음
6

리포트와 사용자 확인

원인을 로그로 확인 / 코드로 추정 / 가설로 나눠 보여줍니다.

분류 확정, 새 유형·원인, 시그니처·파서 규칙 추가·삭제, 수정 상태 변경은 모두 사람이 확인한 뒤에만 계획에 들어갑니다. 두 플랫폼이 같은 규칙을 따릅니다.

7

기록

승인한 변경을 그 플랫폼 이슈 DB에 PR로 올립니다.

변경·diff·검증 결과·커밋 메시지를 보여주고 승인받은 뒤에만 push합니다. main에 직접 push하지 않습니다.

ANDROID

  • Android 이슈 DB 레포에 PR

OFONO

  • oFono 이슈 DB 레포에 PR

두 플랫폼이 섞이지 않게 막는 장치

이슈 DB가 다르다

DB마다 platform을 선언합니다. 세션과 다르면 분석도 기록도 멈춥니다.

Android DBoFono DB

작업 폴더와 lock이 다르다

Android 작업과 oFono 작업을 동시에 해도 서로 덮지 않습니다.

work/work-ofono/

플랫폼은 lock 전에 정한다

질문은 작업 폴더·lock을 만들기 전에 나가므로, 잘못 고른 쪽에 작업이 남지 않습니다.

needs_input platformlock_owner: null

옛 답은 다시 확인한다

저장된 플랫폼 답은 그 질문이 이슈의 가장 늦은 활동일 때만 씁니다. 다른 플랫폼으로 옮겨 간 뒤엔 묻습니다.

platform_answerpending.asked_at

분석 스킬이 다르다

oFono에 분석 스킬이 없어도 Android 스킬로 대신하지 않습니다. 스킬 소스 보호(guard)는 모든 플랫폼에 걸립니다.

analyzersplatforms.ofono.analyzers

참고 자료가 다르다

탐색 분석은 그 플랫폼 자료 목록만 받습니다.

log-tags.md …platforms/ofono/…

oFono 쪽에 데몬 하나를 더하려면

코드를 고치지 않고 설정과 이슈 DB 데이터만으로 됩니다. 메시지 안 형식을 따로 풀어야 할 때만 해석기를 더합니다.
