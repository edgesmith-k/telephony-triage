내 분석을 팀 이슈 DB에 남기려면

이슈를 분석하거나 직접 해결한 뒤 그 결과를 팀 이슈 DB에 남기는 사람을 위한 안내입니다. 무엇을 기록할지, 브랜치와 PR은 어떻게 만들어지는지, 리뷰는 어떻게 받는지를 순서대로 정리했습니다. 대부분은 도구가 해 주고, 사람은 확인과 승인만 하면 됩니다.

기준 main 2026-10-10대상 분석·기록하는 엔지니어, 새 원인을 제안하는 사람읽는 시간 약 12분

2브랜치와 PR 정책

이 절에서 알 수 있는 것: 브랜치가 언제, 누구에 의해, 어떤 이름으로 만들어지는지

  1. main에는 직접 쓰지 않습니다. 모든 변경은 브랜치 → PR → 카테고리 담당자 승인 → 병합입니다. 서버가 강제합니다.
  2. 작업 하나에 브랜치 하나. 월별·사람별로 묶지 않습니다. PR 하나에는 Jira 하나(또는 리뷰 정리 한 묶음)만 넣습니다.
  3. 이름은 정해진 규칙대로 작업 종류와 대상 ID로 짓습니다. 이름만 보고 무슨 작업인지 알 수 있고, 같은 작업을 다시 시작하면 도구가 기존 PR을 찾아 이어서 할지 묻습니다.
  4. 대부분은 도구가 만듭니다. 확인 화면을 승인하면 브랜치 생성, 커밋, push, PR까지 한 번에 됩니다. 내 clone의 브랜치는 건드리지 않습니다.
  5. PR 제목은 [원인 ID 또는 유형 ID] 요약입니다. 도구가 만듭니다.
브랜치 이름언제예
issue/<JIRA-KEY>분석·수동 기록issue/ABC-12345
fix-submit/<원인 ID>수정 CL 기록fix-submit/DATA-001-01
verify-fix/<원인 ID>-<빌드>수정 빌드 검증verify-fix/DATA-001-01-B20261001
verify-res/<원인 ID>-<날짜>해결책 검증verify-res/DATA-001-01-20261009
review/<카테고리>-<YYYY-MM>월간 리뷰 정리review/data-2026-10
move/<옛 ID>-to-<새 ID>유형 이동·병합move/DATA-009-to-DATA-001
import/<카테고리>-<n>기존 분류 가져오기 (PR당 유형 10개 이하)import/data-1
chore/fix-db-…, migrate/…, category/…DB 사후 정리, 스키마 변경, 새 카테고리메인테이너 전용

3확인 화면에서 볼 것

이 절에서 알 수 있는 것: push 직전에 무엇을 확인하고 승인하나

PR을 올리기 직전에 도구가 확인 화면을 한 번에 보여줍니다. 이 화면을 승인해야만 push됩니다.

화면 항목볼 것
변경 파일, ID 할당새로 생기는 원인·유형·fixture 번호가 의도와 맞나
README 미리보기, 주요 diff제목·해결책 문구가 2절 규칙에 맞나, 엉뚱한 파일이 바뀌지 않았나
검사·검증 결과표모두 통과인가. "건너뜀"은 통과가 아니므로 사유를 확인
승인 필요 항목, 리뷰어메인테이너 승인이 필요한 변화가 있나, 누가 리뷰하나
커밋 메시지그대로 PR 제목이 됨

고를 수 있는 것: 승인 / 수정 요청(말로 고칠 곳을 알려주면 반영해 화면을 다시 보여줌) / 전체 diff / 취소(계획은 남아서 나중에 이어서 할 수 있음).

검증 결과 R1~R6 읽는 법

새 원인·유형·시그니처·파서 규칙·해결책이 들어가면 도구가 자동으로 R1~R6을 돌립니다. 사람이 따로 실행하지 않습니다. 각 항목은 어떤 로그에 새 규칙을 대 보는지가 다릅니다.

항목실패하면
R1 파서규칙이 쓰는 태그·문구가 로그에서 안 뽑힘 → 파서 규칙·시그니처 초안 수정
R2 양성이 로그를 못 잡거나 다른 원인도 같이 잡힘 → 시그니처 수정
R3 음성정상·다른 원인 로그를 잡음 → 시그니처를 좁힘. 다른 유형 로그면 "좁히기 / 함께 허용(also_allowed)" 중 내가 고름
R4 교차 회귀기존 fixture 결과가 바뀜 → push 차단. 원인을 보고 시그니처 수정
R5 이벤트 변화실패가 아니라 승인 필요: 영향 표가 PR에 붙고 메인테이너가 승인
R6 추가 표본결과만 보여주고 진행 여부는 내가 고름
누가 만드나검증 규칙(R1~R6이 무엇을 보는지)은 플러그인 코드에 있고 플러그인 개발자가 바꿉니다. 검증에 쓰는 로그(fixture)는 기여하면서 쌓입니다: 양성 fixture는 내가 기록할 때 Claude가 근거 구간을 잘라 마스킹한 초안을 내가 승인한 것이고, R6에 준 로그는 원하면 마스킹해 fixture로 추가할 수 있습니다. 그래서 fixture가 없는 원인은 R1·R2가 "건너뜀"이 되고 월간 리뷰의 "fixture 없는 원인"에 올라갑니다. eval·정확도 평가와의 차이는 용어집 8절.

4리뷰 받고 반영하기

이 절에서 알 수 있는 것: PR을 올린 뒤 생기는 상황별 대처

상황할 일
리뷰어가 수정을 요청함같은 Jira로 다시 실행하고 "이어서 하기"를 고른 뒤 고칠 내용을 말합니다. 같은 브랜치·같은 PR이 갱신됩니다
리뷰어가 "main이 바뀌었으니 맞춰 주세요"/telephony-triage:sync-pr. PR을 만든 PC에서만 됩니다(계획 파일이 그 PC에 있음)
다른 사람이 내 PR 브랜치에 push함도구가 원격 변경 요약을 보여주고 "덮어쓰기 / 중단"을 묻습니다. 자동으로 합치지 않습니다
PR 대신 처음부터 다시 하고 싶음PR을 닫고 같은 Jira로 새로 분석합니다
오래 자리를 비움리뷰어가 대신 맞출 수 있지만 손이 많이 갑니다. 가능하면 병합까지 마치고 비웁니다

5새 원인·유형 작성 규칙

이 절에서 알 수 있는 것: 리뷰에서 자주 돌아오는 항목의 좋은 예와 나쁜 예

새 원인이나 유형을 고르면 도구가 초안을 만들어 줍니다. 승인 전에 아래 규칙에 맞는지만 보면 됩니다.

항목규칙좋은 예나쁜 예
유형 제목증상, "~하지 않음 / ~됨", 30자 이내SETUP_DATA_CALL이 발생하지 않음DataNetworkController 버그
원인 제목원인 명사구, 20자 이내Roaming disabled설정 문제인 듯
해결책행동 지시 1~2문장, "~한다"로 끝. 임시 조치면 앞에 [WA]데이터 로밍 설정을 켠다확인 필요
시그니처마스킹된 로그 기준, 실제로 확인한 문구만. 개인 식별 값 패턴 금지특정 이벤트·문구 조합.*error.*
fixture원인마다 1개 이상, 판별에 필요한 최소 구간(20~100줄), 마스킹근거 줄 주변만 자른 로그전체 logcat
해결책 검증새 원인은 "미검증"으로 시작. "검증됨"은 근거(다른 Jira, 해결 후 로그) 필수근거 Jira 키근거 없이 검증됨
재현 시나리오코드·설정을 고쳐야 하는 원인은 재현 순서를 적음. 나중에 수정 검증(verify-fix)에 쓰임로밍 SIM → 데이터 로밍 OFF → 앱 실행(비워 둠)
넣으면 안 되는 것마스킹 안 된 로그, Jira 요약·설명·댓글 원문, 사람 이름·고객명. 도구가 마스킹하고 검사하지만, 확인 화면에서 한 번 더 보세요.

6직접 편집할 때 (드묾)

이 절에서 알 수 있는 것: 도구 없이 파일을 고쳐야 할 때의 순서

대부분은 도구로 충분합니다. 월간 리뷰 정리처럼 직접 고치는 게 빠를 때만 씁니다.

  1. 규칙대로 이름 지은 내 브랜치
  2. 파일 수정 (생성 파일은 손대지 않음)
  3. validate 통과
  4. 커밋 (hook 끄지 않음)
  5. TT_PUBLISH_TOKEN=manual 로 push → PR
  1. 정해진 이름으로 내 로컬 브랜치를 만듭니다. 예: review/data-2026-10
  2. 파일을 고칩니다. README·STATS 같은 생성 파일은 손대지 않고 db_build.py --write로 다시 만듭니다.
  3. /telephony-triage:validate를 통과시킵니다(전체 회귀와 자동 검증).
  4. 커밋합니다. hook을 끄지 않습니다(--no-verify 금지).
  5. TT_PUBLISH_TOKEN=manual git push origin <브랜치>로 push하고 PR을 만듭니다. 이 표시가 없으면 이슈 DB의 push 검사가 거부합니다.

7자주 하는 실수

이 절에서 알 수 있는 것: 처음 기여할 때 흔히 막히는 곳

실수왜 안 되나대신
원인을 짐작으로 확정틀린 원인이 쌓이면 다음 분석까지 틀림"원인 미확정"으로 기록
여러 Jira를 PR 하나에리뷰와 되돌리기가 어려움Jira마다 따로 (도구가 자동으로 나눔)
다른 PC에서 sync-pr계획 파일이 PR을 만든 PC에만 있음PR을 만든 PC에서 실행
"고쳤다"고 바로 fixed 요청fixed는 수정 빌드 검증으로만 됨fix-submitted 기록 → 수정 빌드 로그로 verify-fix
막혀서 hook을 끔개인정보·깨진 파일이 들어감메시지대로 원인을 고치거나 관리자에게 문의
