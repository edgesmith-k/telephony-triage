아직 안 되는 것과 그 대응

도입을 검토하거나 운영하는 사람이 알아야 할 한계를 숨김없이 정리했습니다. 항목마다 영향, 지금의 대응, 보완 방법, 언제 해소되는지를 붙였습니다. 대부분은 사내 환경에서 실제 로그와 사람으로 확인해야 풀리는 것들입니다.

기준 main 2026-10-09 (사외 초안 완료, 사내 보완 전)대상 도입 검토자, 관리자읽는 시간 약 12분

1한눈에 보기

이 절에서 알 수 있는 것: 한계가 언제 풀리는지 한 장으로

가장 중요한 두 가지실제 로그 문구: data 카테고리만 실제 단말 로그와 AOSP 소스로 형식을 확인했고, 나머지 5개 카테고리 규칙은 예시 값(placeholder)입니다. 정확도: 아직 실제 사례로 재지 않았습니다. 둘 다 사내 S-4·S-5에서 풀기 전에는 파일럿에 쓰지 않습니다.

2아직 검증되지 않은 것

이 절에서 알 수 있는 것: 사외에서 합성 데이터로만 확인해 사내에서 다시 봐야 하는 것

사외 개발은 사내 정보를 가져올 수 없어서 합성 데이터로만 재현했습니다. 자동 테스트 약 1,100개와 CI는 통과하지만, 아래는 실제 환경에서만 확인할 수 있습니다.

한계영향보완 방법언제
실제 로그 문구data 외 카테고리는 예시 규칙이라 실제 로그에서 후보가 안 나오거나 틀림실제 로그로 태그·문구 교체(s0_suggest.py가 초안 제안), 카테고리별 시드 유형 5~10개S-4
정확도1위 정확도, 상위 3개 포함률, 오탐률을 모름해결된 과거 Jira 20~30건 라벨셋으로 offline_eval.py. 조정용과 최종 확인용을 나누고, 기준과 오류율 상한을 둘 다 충족해야 통과S-5
Jira 필드·시계발생 시각 필드 이름, 장비와 단말 시계 차이를 모르면 분석 범위가 어긋남실제 Jira 필드 매핑, 시계 관계 확인S-1·S-3
사내 Claude Code 동작hook과 Jira 원문 격리가 사내 버전에서 그대로 동작하는지 모름빈 플러그인 실험과 실제 Jira MCP로 확인, 다르면 그것만 고침S-2
지시 주입 방어Jira 본문의 "이전 지시를 무시하라" 같은 문장에 흔들리는지 실제로 재지 않음주입 eval 59·60을 실제 환경에서 실행, 안전 eval 위반 0 확인S-2
파서 모델 적합성사내 로그 형식이 참고 파서 가정과 다르면 여러 지표가 동시에 나빠짐S-0 진단(Claude 없이 30분)으로 먼저 확인, 맞지 않으면 검증된 기존 파서를 백엔드로 포팅S-0·S-4a

3설계에서 오는 한계

이 절에서 알 수 있는 것: 일부러 그렇게 만들어서 생기는 단점과 감수한 이유

한계영향지금의 대응 / 보완언제
규칙에 없는 이슈는 못 찾음처음 보는 증상은 후보 없음. 판정이 규칙 기반이라 LLM처럼 "그럴듯한 답"을 내지 않음후보가 없어도 유사 사례·오류 줄·모르는 태그를 보여줌. 탐색 분석으로 가설을 받고, 채택하면 새 규칙으로 등록지금
초기 기여 부담DB가 비어 있으면 처리할 때마다 새 유형을 만들어야 해서 기여자가 지침카테고리별 시드 유형 5~10개를 먼저 넣고 시작. 기존 분류는 import로 가져옴S-4·S-4a
계획이 만든 PC에만 있음다른 PC나 다른 사람은 그 PR을 sync-pr로 맞출 수 없음작성자가 맞추거나, 리뷰어가 직접 편집 절차로 인수v1 밖
원격 변경을 자동으로 합치지 않음내 PR 브랜치에 남이 push하면 덮어쓰기 / 중단만 고를 수 있음남의 변경은 먼저 계획에 반영. 계획 없는 브랜치 자동 병합(3-way)도 v1에 없음v1 밖
Jira 첨부를 자동으로 받지 않음로그 파일을 사용자가 받아 경로로 줘야 함사내 커넥터 설계(RF-6) 때 검토v1 밖
점수는 확신도가 아님"점수 1.0"을 "확실하다"로 오해하기 쉬움리포트에 "진단 확신도 아님"을 함께 표시, 사람이 확정지금
왜 감수했나같은 로그면 언제 돌려도 같은 결과가 나와야 팀이 결과를 믿고 쌓을 수 있습니다. 그래서 판정은 규칙으로만 하고, 규칙이 모르는 것은 "모른다"고 말하게 했습니다. 틀린 기록 한 건이 그 뒤 모든 분석을 흐리는 비용이 더 크다고 봤습니다.

4운영 부담

이 절에서 알 수 있는 것: 사람이 꾸준히 챙겨야 하는 것

한계영향지금의 대응 / 보완언제
리뷰어가 필요함카테고리 담당자가 리뷰하지 않으면 PR이 쌓임CODEOWNERS로 자동 지정. 파일럿에서 PR까지 걸린 시간·대기 PR 수를 잼S-7
한 번에 하나씩 병합대기 PR이 많으면 병합 → sync-pr 요청이 반복됨ID 중복을 막는 대가. 병합 간격을 짧게, sync-pr는 작성자 PC에서 1회 실행지금
월간 리뷰를 사람이 해야 함안 하면 방치 항목·오탐 시그니처가 쌓임리포트는 도구가 만들고 기준값은 팀 설정. 정리는 담당자 몫지금
분석 중 질문이 많을 수 있음발생 시각, 소스 트리 등 매번 묻는 게 귀찮을 수 있음추측으로 채우지 않으려는 설계. 파일럿에서 작업당 질문 수를 재고 줄일 곳을 정함S-7 뒤

수정 검증(verify-fix)을 안 돌리면 fixed가 안 됨

fixed는 수정 빌드 로그 검증을 통과해야만 됩니다. "고쳤다"는 말만으로 닫으면 재발을 놓치기 때문입니다. 대신 아무도 검증을 돌리지 않으면 원인이 계속 fix-submitted에 머뭅니다. 분석과 검색에는 지장이 없고(수정 상태는 후보에서 빼지 않음), 수정 빌드 이후 재발하면 "수정 미흡 의심"으로 알려줍니다.

5안전장치의 한계

이 절에서 알 수 있는 것: 막지 못하는 것과 그 대신 기대는 장치

한계영향대신 기대는 것언제
PC의 hook은 우회 가능변수·스크립트 안의 git 호출, 별칭, 일부 래퍼 명령은 판정 못 함. git hook은 설정을 바꾸면 꺼짐GHE 서버 브랜치 보호와 CODEOWNERS 필수 리뷰. 설정할 수 없는 GHE라면 git hook 방식 채택부터 다시 결정도입 전 필수
Read 도구로 로그 통독Claude가 Read 도구로 로그를 통째로 읽는 것은 hook이 막지 못함스킬 지침(필요한 구간만)과 사내 확인 뒤 대책S-2 뒤
사람 이름은 마스킹 못 함정해진 형식이 없어 패턴으로 잡을 수 없음Jira에서 저장하는 정보 자체를 최소화(요약·설명·댓글 원문 저장 안 함). 리포트·PR에 이름을 넣지 않음지금
Jira 원문 보존 기간올리지 않은 작업 폴더에 원문이 남을 수 있음cleanup이 후보를 보여주지만 보존 기간과 정리 주체는 미정사내 결정(S14)

6비용과 성능

이 절에서 알 수 있는 것: 돈과 시간 쪽 단점

한계현재 수치보완언제
이슈 1건 토큰모의 데이터 기준 분석→기록 약 39만 토큰(약 $0.4), 어려운 dry-run은 80만~130만(약 $0.7)실제 bugreport는 1.5~2배로 예상. S-2에서 실측, 파일럿에서 건당 비용 확인S-2·S-7
준비 단계 토큰data만 해도 추정 3천만~6천만 토큰(약 $25~60, 실측 아님). 행동 eval 52개 재실행이 가장 큼data 관련 eval만 골라 돌리면 1/2~1/3S-2
DB가 커질 때 속도DB 읽기 0.7~1.1초, 일부 비교가 사례 수 × 규칙 수에 비례사내 로그·DB 크기로 재측정한 뒤 색인·범위 제한 검토파일럿 뒤
Windows 개발 환경환경 문제로 테스트 4건이 늘 실패, 반입 묶음은 Ubuntu(WSL)에서 만들어야 함CI(Ubuntu)로 확인. 사내 사용 자체는 영향 없음지금
