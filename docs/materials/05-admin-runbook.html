RUNBOOK · 관리자용 실무 안내

언제, 무엇을 하면 되나

이슈 DB와 플러그인을 운영하는 사람을 위한 안내입니다. 매일·매주·매월 할 일과, 문제가 생겼을 때 어디부터 볼지를 순서대로 정리했습니다. 명령 옵션과 메시지별 조치 같은 세부 내용은 운영 매뉴얼(03-manual.html) 6·7장에 있고, 여기서는 그 장으로 연결만 합니다.

기준 main 2026-10-09대상 메인테이너, 카테고리 담당자, 도입 담당자읽는 시간 약 12분

1관리자 역할

이 절에서 알 수 있는 것: 관리자 역할 세 가지와 각자 맡는 일

역할누가맡는 일
카테고리 담당자data·call·network·sim·sms·ims 카테고리마다 한 팀 (CODEOWNERS)자기 카테고리 PR 리뷰·병합, 월간 리뷰, 해결책·수정 검증 요청
메인테이너이슈 DB 공통 영역 담당 팀파서 규칙·스키마·hook·설정 변경 리뷰, 새 카테고리, 스키마 버전 올리기, DB 사후 정리, 브랜치 보호 관리, 플러그인 업데이트
도입 담당자사내 도입을 맡은 사람 (보통 메인테이너가 겸함)사이트 설정, 운영 DB 생성, 사내 보완 단계(S-0~S-7), 파일럿 지표 수집
원칙도구는 PR을 병합하지 않습니다. 병합과 "승인 필요" 항목 판단은 항상 사람(카테고리 담당자·메인테이너)이 합니다.

  • GHE 레포 3개: 플러그인, 샌드박스 이슈 DB(시험용), 운영 이슈 DB

  • plugin/site-defaults.yaml 작성·커밋 (S-3)

  • 운영 DB를 뼈대로 만들고 main에 첫 push

  • 카테고리 담당 팀 6개와 메인테이너 팀을 CODEOWNERS에 연결

  • 파서 규칙의 예시 값(placeholder)을 실제 태그·문구로 교체, 카테고리별 시드 유형 5~10개 (S-4)
예시 규칙으로 판정해 결과를 믿을 수 없음. 빈 DB로 시작하면 처리할 때마다 새 유형을 만들어야 해서 기여자가 지침매뉴얼 7.9, 7.13
  • 샌드박스에서 dry-run과 실제 PR 1건 (S-5)
  • 사내 마켓플레이스 등록 (S-7)
설치·권한 문제를 팀원이 처음 발견함매뉴얼 7.13

3정기 작업 달력

이 절에서 알 수 있는 것: 주기별로 할 일. 이것만 지키면 DB가 스스로 망가지지 않습니다

매일카테고리 담당자
  • 들어온 PR 리뷰 (6절 체크리스트)
  • 한 번에 하나씩 병합
  • 병합 뒤 다른 대기 PR 작성자에게 sync-pr 요청
매주메인테이너
  • sync 결과의 사후 검사 경고 확인 (ID 중복·Jira 중복이면 5절)
  • 오래 열린 PR 점검, 작성자 부재면 7절
매월카테고리 담당자
  • /telephony-triage:review <카테고리>
  • 방치 항목은 리포트의 "기록: 이름"에게 요청
  • 정리 내용은 review/… PR로
  • STATS의 급증·수락률 확인
분기메인테이너
  • 지원 Android 버전(android_versions_supported) 갱신
  • 오래 안 쓰인 원인·지원 종료 원인 폐기 정리
  • 10절 숫자 점검
플러그인 업데이트 때메인테이너
  • 릴리스 노트에 지원 스키마·생성기 버전
  • 버전이 바뀌면 DB 쪽 버전 올림 PR
  • 팀원에게 업데이트 공지
월간 리뷰가 잡아 주는 것시그니처 없는 원인, fixture 없는 원인, 오래 미확정인 Jira, 수락률 낮은 시그니처, 중복 후보, 오래 안 쓰인 원인, 수정 검증 대기 방치(30일), 해결책 미검증 방치(60일), 급증. 기준값은 이슈 DB의 issue-db.config.yaml에 있고 바꾸려면 PR입니다. 항목별 조치는 매뉴얼 7.7.

4사용자가 "막혔어요" 할 때

이 절에서 알 수 있는 것: 문의가 오면 어디부터 볼지

먼저 사용자에게 /telephony-triage:setup을 다시 실행해 달라고 하세요. 마지막에 나오는 점검 표(doctor)의 fail·warn 행이 원인을 거의 다 알려줍니다. 점검 표는 읽기만 하고 아무것도 고치지 않습니다.

하지 말 것막힌 걸 풀려고 hook을 끄거나(--no-verify), main에 직접 push하거나, 버전 검사를 건너뛰지 않습니다. 그 장치가 막는 사고가 그대로 생깁니다. 막힘의 원인을 고치세요.

5DB에 문제가 생겼을 때

이 절에서 알 수 있는 것: 운영 중 생길 수 있는 DB 문제와 처리 방법

상황어떻게 알게 되나처리자세히
main에 같은 ID가 두 번sync 뒤 사후 검사 경고먼저 병합된 쪽이 주인. 나중 쪽을 chore/fix-db-… 브랜치에서 다음 빈 ID로 옮기고 커밋에 Renumbered: 표시. "main의 ID는 바꾸지 않는다"의 유일한 예외매뉴얼 7.6
같은 Jira가 두 번 기록사후 검사 경고나중에 병합된 파일을 지우고 두 작성자에게 알림. 어느 분류가 맞는지는 작성자와 카테고리 담당자가 정함매뉴얼 7.6
잘못 병합된 PR리뷰·사용자 신고main을 직접 고치지 않고 PR로 되돌림. 원인·유형은 지우지 말고 폐기·병합 상태로, 잘못된 분류는 재분류, 잘못된 수정 상태는 open으로 되돌림(이전 값은 이력에 남음)매뉴얼 7.12
오탐 신고 ("이 원인이 아닌데 1위로 나와요")사용자 신고, 월간 리뷰 "수락률 낮은 시그니처"그 로그 구간을 음성 fixture로 추가하고 시그니처를 좁히는 PR. 회귀 검사가 다른 사례를 깨지 않는지 확인매뉴얼 7.4
급증월간 리뷰 "급증"최근 30일이 이전 월평균의 2배 이상. 특정 빌드·모델·통신사에 몰렸는지 STATS 분포로 보고 원인 조사매뉴얼 7.7
Jira 원문 격리가 안 됨사용자가 "격리 hook 미동작" 메시지 보고그 Claude Code 버전에서 hook이 동작하는지 확인(S-2 항목). 그 사이에도 리포트·계획에는 마스킹 값만 저장됨매뉴얼 6.3

6PR 리뷰와 병합

이 절에서 알 수 있는 것: 리뷰할 때 볼 것과, 병합 순서를 지켜야 하는 이유

왜 한 번에 하나씩PR 둘을 연달아 병합하면, 둘 다 같은 "다음 번호"로 새 원인을 만들었을 때 ID가 겹칩니다. 하나를 병합하고 다음 PR을 sync-pr로 맞추면 새 ID가 최신 main 기준으로 다시 정해져 겹치지 않습니다.

PR 본문의 "검증 못 함 — 리뷰 대상", "사용자 진술 — 카테고리 오너 리뷰 필요" 표시는 리뷰어가 근거를 직접 확인할 항목입니다. 다른 카테고리가 내 fixture에 also_allowed를 넣은 PR에도 리뷰어로 붙습니다.

7사람이 바뀔 때

이 절에서 알 수 있는 것: 작성자 부재, 담당자 교체, 퇴사 때 챙길 것

상황알아 둘 점처리
작성자가 없는 열린 PR작업 계획은 작성자 PC에만 있어서 다른 사람은 sync-pr를 못 함리뷰어가 "계획이 없는 브랜치" 절차로 맞춤: rebase → 생성 파일 다시 만들기(db_build --write) → validate → TT_PUBLISH_TOKEN=manual로 push. 손이 많이 가면 PR을 닫고 같은 Jira를 새로 분석
카테고리 담당자 교체리뷰 요청은 CODEOWNERS로 감CODEOWNERS 팀 구성원 변경(GHE 팀 관리) 또는 CODEOWNERS 수정 PR
퇴사·장기 부재그 사람 PC의 진행 중 작업(계획·lock·작업 공간)은 사라짐. 병합된 기록은 DB에 그대로열린 PR은 위처럼 인수하거나 닫기. 월간 리뷰에서 그 사람이 "기록"으로 나온 방치 항목은 새 담당 지정
사용자가 PC를 바꿈계획·lock·작업 공간은 PC 로컬이라 따라오지 않음진행 중인 쓰기 작업을 끝내거나 버린 뒤 옮기고, 새 PC에서 setup

8변경 관리

이 절에서 알 수 있는 것: 규칙·플러그인·스키마를 바꿀 때 지킬 순서

무엇을 바꾸나어디서지킬 것자세히
유형·원인·시그니처·fixture이슈 DB PR보통 분석 중 "새 원인·새 유형" 선택으로 시작. 자동 검증 R1~R6과 회귀 통과매뉴얼 7.4
파서 규칙 (태그·RIL·extractor)이슈 DB PR, 메인테이너 리뷰 필수이벤트 변화(R5)가 나오면 "승인 필요" → 영향 표를 PR에 붙이고 메인테이너가 승인. 플러그인 재배포는 필요 없음매뉴얼 7.9
팀 공통 기준값 (issue-db.config.yaml)이슈 DB PR, 메인테이너 리뷰방치 기준일, 점수, 마스킹 예외 등. 마스킹 예외를 너무 넓게(.*) 쓰면 lint가 거부매뉴얼 9.4
사이트 설정 (site-defaults.yaml)플러그인 레포platform.*를 바꾸면 파서 출력이 달라질 수 있어 DB에서 전체 회귀를 다시 돌림매뉴얼 7.8
플러그인 업데이트플러그인 레포 → 마켓플레이스새 초안은 import_draft.py로 반입(사내 전용 경로 보존, 통째 교체 금지). 생성기 버전이 바뀌면 DB 버전 올림 PR이 먼저. 되돌리기 절차는 파일럿(S-7)에서 확정매뉴얼 7.10
스키마 버전 올리기메인테이너 migrate/schema-v<N> 브랜치열린 PR을 최대한 정리하고 병합 중지 공지 → migrate --dry-run → 실행 → PR. 남은 PR은 작성자의 sync-pr가 계획을 새 형식으로 올림매뉴얼 7.11

9하면 안 되는 것 5가지

이 절에서 알 수 있는 것: 급할 때 손이 가기 쉬운 지름길과 그 결과

하지 말 것대신왜
main 직접 수정·push항상 브랜치 + PR리뷰 없는 변경이 팀 전체 분석에 바로 반영됨
README·STATS·CHANGELOG 손편집db_build.py --write데이터와 어긋나고 다음 커밋 검사에서 막힘
hook 끄기·버전 검사 건너뛰기막힌 원인을 고침 (4절)개인정보나 깨진 파일이 커밋됨
원인·유형 파일 삭제폐기(deprecated)·병합(merged-into) 상태로예전 Jira 기록과 PR이 그 ID를 가리키고 있어 이력이 끊김
사내 로그·값을 사외로 가져가기사람이 직접 쓴 사내 정보 없는 문장만사외 개발은 합성 데이터로만 재현하는 것이 원칙

10볼 숫자

이 절에서 알 수 있는 것: 도구가 잘 쓰이고 있는지 판단할 숫자와 나쁠 때 할 일

숫자어디서나쁘면
시그니처 수락률 (1위 후보를 사용자가 받아들인 비율)STATS "수락률 하위 10개", 월간 리뷰 (0.7 미만, 표본 5건 이상)시그니처 좁히기·음성 fixture 추가. 단, 수락률은 정답률이 아님(틀린 1위를 받아들일 수도 있음)
