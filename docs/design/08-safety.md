## 8. 개인정보 마스킹 (`mask_pii.py`)

이슈 DB에 들어가는 모든 로그 예시, fixture, 본문, 리포트에 적용한다. **extractor와 매칭 전 로그 줄에도 적용한다** (`parse_logcat.py parse --mask`, `07-workflow.md §Step 3`). 마스킹 함수는 `common/`에 있고 `mask_pii.py`와 `parse_logcat.py`가 공유한다.

| 항목 | 탐지 방법 (참고) | 치환 |
|---|---|---|
| IMSI | 키 이름 문맥(`imsi=`, `IMSI:` 등) 우선, 문맥 없는 15자리는 MCC/MNC 유효성 확인 | `<IMSI#n>` (MCC/MNC 유지 옵션) |
| IMEI | 키 이름 문맥 우선(`imei`·`imeisv`·`meid`·`device_id`, 앞에 `m` 허용; 구분자(`-`·공백) 포함 14~16자리, 키에 붙은 값·뒤에 `_`·영문이 붙은 값도 값 부분), 문맥 없는 15자리 + Luhn, 문맥 없는 `NN-NNNNNN-NNNNNN-N` + Luhn. 같은 IMEI의 표기 변형(공백·대시)은 같은 번호 | `<IMEI#n>` |
| EID (eUICC) | 키 이름 문맥 `eid` 32자리 | `<EID#n>` |
| ICCID | `89`로 시작하는 19~20자리 + 문맥 | `<ICCID#n>` |
| SUPI / SUCI | `imsi-…`, `suci-…` 형식 | `<SUPI#n>` / `<SUCI#n>` |
| TMSI / GUTI / 5G-GUTI | 키 이름 문맥 | `<TMSI#n>` / `<GUTI#n>` |
| MSISDN / 전화번호 | `+`국가번호, 국내 번호 형식, `tel:` URI | `<MSISDN#n>` |
| SIP URI / IMPU / IMPI | `sip:…@…`, `tel:…`, IMS 도메인의 사용자 부분 | 사용자 부분만 `<IMPU#n>` / `<IMPI#n>` (도메인은 유지 옵션) |
| Cell ID / TAC / CI / PCI 등 셀 식별자 | `mCi=`, `mTac=`, `cid=` 등 키 이름 문맥 | `<CELL#n>` |
| IP 주소 | IPv4/IPv6. IPv4 값 바로 앞이 `version`·`build`·`release`·`rev`·`fw`·`sw`·`baseband`·`kernel`·`v` 문맥이면 제외(버전 문자열) | `<IP#n>` |
| MAC 주소 | 6옥텟 `:`·`-` 형식(`-` 형식은 숫자만이면 제외), 키 문맥(`mac`·`mac_address`·`bssid`·`hwaddr`·`ether`·`bd_addr`, 낱말이 앞에 붙은 `…MacAddress`)의 12 hex | `<MAC#n>` |
| GPS 좌표 | `lat`·`latitude`·`lon`·`longitude`·`lng`·`altitude`(앞에 `m` 허용) 키 문맥의 소수 3자리 이상, `gps`·`fused`·`network`·`passive` 뒤의 `위도,경도` 쌍(소수 4자리 이상) | `<GEO#n>` |
| 장치 serial | `ro.serialno`·`ro.boot.serialno`·`serialno`·`serial_number` 키(6자 이상, getprop `[ro.serialno]: [값]` 포함). `sn`(6자 이상)·`serial`·`mSerial`(8자 이상)은 영문+숫자 혼합만(시퀀스 번호·숫자뿐인 RIL serial 제외) | `<SERIAL#n>` |
| 이메일 | 이메일 형식 | `<EMAIL#n>` |
| 자격증명 성격 값 | SIP `Authorization`/`WWW-Authenticate` 헤더의 `response=`, `nonce=`, `cnonce=`; AKA `RES`/`AUTN`/`AUTS`/`Ki`/`Kc`/`CK`/`IK`/`OPc`/`OP`/`K`(16 hex 이상, 대소문자 구분 — `KI`·`KC`·`OPC` 대문자 변형은 받고 소문자 `ki`·`ck`는 받지 않음); 키 이름 문맥 `password`, `passwd`, `pwd`, `secret`, `token`, `key`의 값; `pin`·`puk`(앞에 `m` 허용)은 숫자 4~8자리만; `pass`·`passcode`는 상태 낱말(`enabled`·`ready`·`ok`·`passed`·`true` 등)·대문자 열거형·3자리 이하 숫자 제외; `Bearer <토큰>`(대소문자 무관)·JWT(`eyJ…`) (IMS REGISTER 로그가 fixture에 들어가므로 필요) | `<CRED#n>` |

- **번호 토큰(가명화)**: 같은 파일(분석 1회) 안에서 **같은 원래 값은 같은 번호**, 다른 값은 다른 번호로 바꾼다(`<CELL#1>`, `<CELL#2>`). 번호는 파일 안에서 처음 나온 순서로 매긴다. 그래서 "셀이 바뀌었다", "같은 번호로 재시도했다" 같은 **값 비교 관계가 마스킹 뒤에도 보존**되고, 기존 파서의 판별 로직이 마스킹된 fixture에서도 같게 동작한다 (`16-existing-assets.md §16.3`). 원래 값과 번호의 대응표는 메모리에만 두고 저장하지 않는다.
- 시그니처와 extractor는 특정 번호(`#1`)가 아니라 토큰 종류(`<CELL#\d+>`)나 "같은 토큰/다른 토큰" 관계로만 쓴다 (`db_lint`가 특정 번호 고정을 경고).
- **문맥 기반 탐지를 우선**하고, 숫자 길이만으로 판정하는 규칙은 보수적으로 쓴다 (빌드 번호, 타임스탬프 오탐 방지).
- 알려진 한계: 문맥 없는 15자리에 `_`·영문이 바로 붙은 값(`…518_slot1`)은 잡지 않는다(빌드 번호 오탐 방지, 키 문맥이 있으면 잡는다). 사람 이름·자유 텍스트, 소수 2자리 좌표, 키 없는 serial, 16진 IMEI 변형도 잡지 않는다 — 사내 로그 표본으로 다시 본다(TODO(SITE:S13)).
- 키 이름은 따로 적지 않으면 대소문자를 가리지 않고(AKA 키만 구분), `key=v`·`key: v`·JSON `"key":"v"` 형식을 모두 받는다.
- 성능: 마스킹은 줄마다 도는 hot path다. 키 이름 문맥 규칙은 소문자 줄에 그 키 부분문자열이 있을 때만 돈다(`Rule.gate`, 결과 불변 — `test_gate_does_not_change_result`). ASCII가 아닌 줄은 게이트를 끈다(`(?i)`가 `ſ`·`İ`도 맞추기 때문).
- 오탐 예외는 `issue-db.config.yaml`의 `mask.allow_patterns`로 관리한다 (메인테이너 리뷰). `db_lint`가 정규식 오류(`schema`)·안전성(`regex-unsafe`)과 대표 PII 표본 전체에 맞는 넓은 패턴(`mask-allow-too-broad`, 예: `.*`)을 오류로 낸다. 정규식이 틀리면 `mask_pii`는 종료 코드 2다.
- Android 자체 마스킹(`***`, `xxxxxx`)은 그대로 둔다.
- extractor와 매처는 항상 마스킹된 텍스트에 대해 돈다. 그래서 시그니처와 extractor 패턴은 마스킹 이후 텍스트 기준으로 작성하고, 그 안의 원본 식별자 패턴은 `db_lint`가 금지한다 (`04-parser-matching.md §5.11 (1)`).
- 마스킹은 같은 입력이면 항상 같은 출력을 내고, 이미 마스킹된 입력(`<…#n>` 토큰)에 다시 적용해도 결과가 같다(멱등, 기존 토큰은 그대로 둔다). 분석과 회귀(마스킹된 fixture를 다시 파싱)의 일치를 위해서다.
- **이미 토큰이 있는 입력**(부분 마스킹된 외부 로그, 사람이 원본 값을 끼워 넣은 fixture): 먼저 입력 전체에서 종류별 기존 최대 번호를 구하고, 새 원본 값에는 그 다음 번호부터 준다. 예: `<CELL#1>`이 이미 있는 파일에 새 셀 ID가 나오면 `<CELL#2>`. 서로 다른 값이 같은 토큰이 되어 값 비교 관계가 거짓으로 바뀌는 것을 막기 위해서다.
- 파서 백엔드·외부 파서가 낸 이벤트의 `msg`와 `fields`도 extractor 전에 같은 함수(같은 번호 대응)로 마스킹한다 (`parse_logcat.py parse --mask`).
- `--check` 모드는 검출 시 종료 코드 1이다. NUL이 든 파일도 건너뛰지 않는다(`--staged`·`--changed`: NUL을 지운 줄과 공백으로 바꾼 줄을 함께 검사 — UTF-16·잘린 logcat). `db_precommit`(`--staged`), `db_pr stage`(`--changed`), Claude hook이 쓴다.
- 항목별 누락/과잉 마스킹 테스트를 둔다.

### 8.1 Jira 텍스트

마스킹 표는 logcat 형식 기준이지만, Jira에서 읽은 텍스트도 리포트·계획·PR 본문에 들어가므로 같은 규칙을 적용한다. Jira 설명에는 테스터 이름, 고객 전화번호, IMEI가 자유 텍스트로 자주 적히고 **사람 이름은 위 표로 잡히지 않는다.** 그래서 마스킹에만 기대지 않고 **저장하는 정보 자체를 줄인다.**

- 이슈 DB(`issues/<KEY>.yaml`, 원인 본문, 피드백)와 PR 본문에는 Jira의 **구조화 필드**(`model`, `sw`, `platform_version`, `carrier`, `occurred_on`)와 **사용자가 확인한 한 줄 요약**(`note`), 그리고 있으면 마스킹된 **실패 스텝 한 줄**(`failed_step`, ≤200자)만 넣는다. Jira 요약·설명·코멘트 **원문은 저장하지 않는다** (`03-issue-db.md §5.4 (2)`).
- **MCP 응답 원문은 모델 컨텍스트에 넣지 않는다.** Jira `get_issue`·`get_comments` 결과는 PostToolUse hook(`jira_bridge.py`, §9 9번)이 `<work_dir>/<KEY>/issue_raw.json`에 쓰고, 모델에는 마스킹된 요약만 보인다. `triage.py run`이 그 파일을 `jira_fields.py extract --consume`으로 읽고 지운다. 후처리 마스킹은 이미 컨텍스트에 들어간 원문을 되돌릴 수 없기 때문이다. hook 출력 대체가 안 되는 Claude Code 버전이면(S1에서 확인) 스킬이 응답을 그 파일에 저장하는 예전 경로로 돌아간다. 그때 스킬은 격리 hook이 동작하지 않았다(원문이 대화에 들어왔다)고 사용자에게 알린다.
- `field_map`으로 뽑은 텍스트 필드(요약, 설명, 재현 절차, 코멘트)는 Step 2에서 읽은 직후 `mask_pii`를 거치고, 이후 단계(리포트, 키워드 보너스, `note` 초안)는 마스킹된 텍스트만 쓴다. 계획 `issue`에는 원문 필드를 두지 않는다 (`contracts.md §작업 계획`).
- **실패 스텝**(`--failed-step` 원문·`--steps-file` 내용)의 원문은 `trace.jsonl`·`triage-state.json` 같은 상태·추적 파일에 쓰지 않는다. `triage.py`가 같은 프로세스 안에서 마스킹한 뒤에만 `issue.json`·`issue_meta.json`·계획에 남기고, 하위 스크립트 인자에도 원문을 넘기지 않는다.
  `--steps-file`이 zip이면 **메모리에서만 읽는다**(풀지 않는다 — 항목 선택·크기 상한·절대/`..`/암호화 항목 거부는 `07-workflow.md §Step 2`). 개발자가 붙여넣은 스텝 목록은 `WD/<KEY>/steps-pasted.txt`(work_dir는 700 권한 디렉터리)에 쓰고 `--steps-file`로 넘기며, **커밋하지 않고** 도구가 읽을 때 마스킹한다. 원문이므로 작업이 끝나면 지운다: `db_pr discard`, `--force` 없는 `lock release <작업 키>`(`triage.py release` 포함, `triage.py run --analysis-only`가 ok로 끝나며 lock을 풀 때도), `cleanup`. 스텝 이름·표 내용은 `parse_logcat markers --step-events`의 인자에 없고(규칙은 이슈 DB 설정에서 읽는다) 출력에는 이름·시각만 있다. 리포트의 zip 멤버 경로는 마스킹해서 쓴다.
- **재사용 캐시**(`<work_dir>/<KEY>/analysis-cache.json`)에는 마스킹된 분석 결과(후보·근거·코드 경로·마스킹된 스텝 이름)와 입력의 해시만 둔다. `triage-state.json`의 `job`에는 입력 로그의 경로·이름·sha·크기와 실행 이력만 있고, 실패 스텝·steps-file 원문은 어느 쪽에도 없다. needs_input으로 멈추면 `pending`에 질문 종류와 시각(`{kind, asked_at}`)만 남긴다(질문 문구·선택지는 다른 작업 키·경로를 담을 수 있어 쓰지 않는다) (`07-workflow.md §입력 재사용`).
- **`runs/<n>/`**(`--more-logs`·재분석 때 덮어쓰기 전에 복사한 이전 `analysis.json`·`report.md`, 최근 5개)에는 이미 마스킹된 결과만 있다. `events.json`·`match.json`·로그 원문은 보관하지 않는다 (`07-workflow.md §추가 로그 재분석`).
- **Jira 코멘트 본문**(`issue_post.py`, `07-workflow.md §Step 9`): 이미 마스킹된 `analysis.json`·`issue.json`·계획 값으로 결정적 칸을 채우고, LLM 칸(`post.fill.json`)은 그 본문을 기준으로 만든 마스커(기존 토큰 다음 번호)로 마스킹한 뒤 렌더한 전체 본문에 한 번 더 적용한다. 마스커 검출이 남거나, LLM 칸에 로그 원문 줄 모양이 있거나, Jira 요약·설명·코멘트와 40자 이상 같은 연속 부분이 있으면 종료 1이다. 그래도 사람 이름은 잡지 못하므로 스킬 규칙과 확인 화면(본문 그대로 표시)으로 막는다. 게시 응답 원문은 컨텍스트에 넣지 않는다(§9 9번).
- `note` 초안은 스킬이 마스킹된 요약에서 한 문장으로 만들고 사용자가 확인한다. 사람 이름·고객명은 초안에 넣지 않는다.
- `db_lint`는 `issues/*.yaml`의 `note`, 원인 본문, `cp_evidence`에 대해서도 원본 식별자 패턴(표의 항목)을 검사한다.

## 9. Hooks (`hooks/hooks.json`)

**적용 범위**: 플러그인 hook은 플러그인이 켜진 모든 세션에 적용된다. `record`도 같은 hook(Jira 읽기·승인 코멘트, 커밋·push 검사)을 거친다. `record` 전용 hook은 없다(표시 보조 hook `show_guard.py`도 모든 흐름에 같다, §9.1). 그래서 git 관련 hook은 모두 먼저 **대상 레포를 판별**한다. `guard.py`가 명령의 작업 디렉토리(cwd, `git -C <dir>`)에서 `git rev-parse --git-common-dir`을 구해, config의 `issue_db.path` 레포(그 worktree와 읽기 스냅샷 포함)일 때만 규칙을 적용하고, 아니면 아무것도 하지 않는다. **플랫폼 프로필이 여럿이면**(`17-platforms.md`, 최상위 android 프로필 + `platforms.<이름>`) 사용자 config에 있는 **모든 프로필**의 clone·`work_dir`·원격·base 브랜치를 보호한다(`platform.enabled`·선택 플랫폼과 무관 — 플러그인을 두 벌 설치해도 서로 보호된다). 규칙 2(승인 기록 파일)·8·11과 git 규칙(3~7)이 그렇고, git 규칙은 cwd가 속한 프로필의 base 브랜치를 쓴다. 이름이 잘못된 프로필의 clone도 보호한다. 프로필이 하나면 판정은 이전과 같다. `gh`·MCP 쓰기(11번)는 대상 레포를 따로 판정하고, Bash의 clone 변경 차단(8번)은 clone **본체**(git dir이 `<clone>/.git`)에만 적용한다(작업 worktree·`_snapshot` 제외).

**매처 원칙**: `hooks.json`의 matcher는 도구 이름까지만 거른다. 명령 내용과 서버 판정은 `guard.py`가 한다.
- Bash 규칙: matcher `Bash`.
- Jira 규칙: matcher **`mcp__.*`** (모든 MCP 도구). `guard.py`가 도구 이름 `mcp__<server>__<tool>`의 서버 접두사를 config `tracker.mcp_server`와 `tracker.tools` 도구 이름의 서버 접두사(합집합, 플러그인 번들 서버 `mcp__plugin_…`도 덮는다)와 비교해서, **그 서버의 도구만** 판정한다. 서버 이름은 `[^A-Za-z0-9_-]`→`_`로 정규화해 비교한다(관측 기반 추정, S1 확인). 다른 서버 도구는 그대로 통과시킨다. 서버 이름을 matcher에 직접 넣지 않는 이유는 서버 이름이 사용자 config에 있고 플러그인 hooks.json은 고정 파일이기 때문이다.
- `tracker.read_tools`는 **전체 도구 이름**(`mcp__<server>__<tool>`)으로 저장하고, guard는 전체 이름(서버 부분 정규화)으로 비교한다. 플러그인 hook에 전달되는 MCP 도구 이름 형식은 S1·S3에서 확인한다 (`14-site.md §14.2`).

**명령 판정의 한계**: `guard.py`의 명령 파싱은 **최선 노력**이다. `git -C <dir>`, `cd <dir> && git …`, `;`/`&&`/`||`로 이어진 명령, `sh -c "…"`/`bash -c "…"`·`eval "…"` (중첩 한도 안), 앞 래퍼(`env`(`-u`·`-C`·`-S` 포함)·`timeout`·`nice`·`ionice`·`stdbuf`·`sudo`·`setsid`·`time -p`·`exec -a`·`nohup`·`command`·`xargs`(정적 인자만))를 풀어서 판정한다. 레포 판별은 `git --git-dir`·`--work-tree`(공백형·`=`형)와 앞의 `GIT_DIR=`·`GIT_COMMON_DIR=`·`GIT_WORK_TREE=` 대입도 반영한다. `VAR=값` 대입 값 안의 `$( )`·백틱 본문과 `-c` 없는 셸이 읽는 heredoc 본문(`bash <<EOF`·`cat <<EOF | sh`)은 명령으로 풀어 본다. 그 밖의 heredoc 본문은 명령으로 읽지 않는다. 주석(인용 밖 단어 첫머리 `#`부터 줄 끝)은 빼되 줄바꿈은 남겨 다음 줄을 따로 본다(`echo x # 메모` 다음 줄의 `git push`가 앞 argv에 붙어 규칙을 피하지 않게, K 3차). 변수 치환, 별칭, 스크립트 파일 안의 git 호출, 인자 안의 백틱·`$( )`, `xargs -I{} git -C {} …`처럼 입력 항목이 인자가 되는 경우, 표 밖 래퍼(`watch`·`flock` 등), 앞선 명령이나 셸 설정에서 `export`한 `GH_REPO`·`GIT_DIR`·`GIT_WORK_TREE`·`GIT_CONFIG_*`(guard는 그 명령 앞의 대입만 본다)는 판정하지 못한다. 공백 없이 붙은 리디렉션(`x>file`, `>|`)은 따옴표 밖에서 나눠 본다. 그래서 커밋 검사의 **진짜 강제는 git pre-commit hook**이고, Claude hook은 빠른 차단과 우회 방지 역할이다. 워크플로우는 커밋을 `db_pr publish --commit`이 하게 해서(셸 거치지 않는 `git commit -F`, 승인 해시·`core.hooksPath`·guard와 같은 검사 프로필·pre-commit을 같은 프로세스에서 확인) 스킬이 `git commit`을 직접 부르지 않는다. `publish` 토큰은 옵션과 무관하게 규칙 7로 `ask`다 (`07-workflow.md §Step 8-6`). **규칙 7 publish는 위 한계의 예외**로 넓게 본다(낱말 그물 하나, L M-2 — 상세는 §9 규칙 7 문단): 명령 글 전체(heredoc 본문 밖 줄 이음을 bash처럼 잇고 heredoc 본문 포함)에 이름 `db_pr`와 낱말 `publish`가 함께 있으면 `ask`다. 검색·출력·파일 받기(grep·echo·cat·tee 등)만인 줄과 그 줄이 연 heredoc 본문은 글로 보고 뺀다. 남는 한계는 낱말을 변수로 만들어 쓴 호출(`${P}lish`·`X=db; …/${X}_pr.py publish`)·인코딩한 호출, 인용 안 `<<EOF`(`echo "<<EOF"`)와 맨 `EOF` 줄로 만든 가짜 heredoc(그 사이 줄을 본문으로 뺀다), 스크립트 파일 안 호출(`bash push.sh` — eval 채점기는 결과의 `"published": true`로도 센다), 사용자 셸 프로필의 별칭·함수. 인용·`\`·`$'…'`·줄 이음으로 쪼갠 낱말(`pub"lish"`·`"$S"d""b_pr.py`·`pub\⏎lish`)은 붙여 본다. 반대로 db_pr 소스·문서를 sed·python으로 다루는 명령에 두 낱말이 함께 들면 `ask` 오판이다(싸다).

- Hook은 **11종**이다: 위 표의 안전 관문 **10종**(SessionStart 1 + Jira 1 + Bash 6 + 파일 도구 1 + Jira 응답 격리 1)과 **표시 보조 1종**(§9.1 `show_guard.py`). 판정은 1~8번·10번·11번 `guard.py`, 9번 `jira_bridge.py`. 10번·11번은 새 matcher 없이 기존 Bash·`mcp__.*` matcher에서 판정한다(새 hook이 아니다). 표시 보조는 표의 행이 아니다: 표의 행은 막거나(`deny`) 사람에게 묻는(`ask`) 안전 관문이고 내부 오류에 닫혀(fail-closed) 있지만, 표시 보조는 내부 오류에 열려(fail-open) 있고 안전을 맡지 않는다.
- **10번의 한계**: 최선 노력이다. `python -c`·`cut`·`paste`·`while read`처럼 파일을 통째로 내보내는 다른 명령, 위 목록에 없는 match-all 패턴(`grep -E '^|x'` 등), 변수·스크립트 파일 안의 읽기, 8KB 안에 로그 줄이 없는 파일, 31번째 줄부터 로그인 파일은 보지 못한다. **Read 도구**의 limit 없는 통독은 이 장치가 막지 못한다(`99-deferred.md §E`, 사내 S1 뒤). 그때까지는 스킬 지침(`reference/rules.md`의 `limit`·`offset`)에 기댄다.
- **로컬 장치는 모두 우회 가능하다.** Claude hook은 최선 노력 파싱이고, git hook은 `core.hooksPath`를 바꾸면 꺼진다. main 직접 push 금지와 CODEOWNERS 필수 리뷰는 **GHE 브랜치 보호로 서버에서 강제**되어야 한다 (`06-collaboration.md §6.1`). 이 전제가 없으면 `.githooks/`(main에 커밋된 스크립트가 모든 기여자 PC에서 실행됨)가 코드 실행 경로가 된다.
- git hook은 두 개다: `pre-commit`(`db_precommit.py`)과 **`pre-push`**. `pre-push`는 (a) 대상 ref가 `refs/heads/<base_branch>`면 거부하고, (b) 환경변수 `TT_PUBLISH_TOKEN`이 없거나 `<work_dir>/<작업 키>/state.json`의 `approved_hash`와 다르면 거부한다. pre-push는 작업 키를 모르므로 `<work_dir>/*/state.json`에서 `approved_hash`가 토큰과 같은 것을 찾는다. 토큰이 `manual`이 아니면 추가로 (c) push하는 커밋의 트리가 토큰과 같고, (d) 대상 브랜치가 그 `state.json`의 `branch`이며, (e) 원격 ref 삭제가 아니어야 한다(모두 `db_pr publish`가 이미 지키는 조건이라 정상 흐름은 거부되지 않는다). `base_branch`·`work_dir`는 사용자 config에서 읽고, 없으면 `main`·`<home>/work`로 본다. 플랫폼 분기(`17-platforms.md`): push하는 커밋의 `issue-db.config.yaml` `platform`(없으면 android, 읽지 못하면 거부)이 android가 아니면 `platforms.<p>.issue_db.base_branch`·`platforms.<p>.work_dir`(기본 `<home>/work-<p>`)을 쓴다. 샘플 DB(`tests/fixtures/issue-db-sample/.githooks/pre-push`)에 들어 있고, 운영 이슈 DB hook은 배포 때 같은 분기를 넣었는지 확인한다. pre-push는 플러그인 스크립트에 기대지 않는 이슈 DB 안의 자기완결 스크립트다(`plugin.scripts_path`가 무효해도 동작). 토큰은 `db_pr publish`가 자기 `git push` 호출에만 넣는다 (`contracts.md §3.2`). 직접 편집 기여자는 `validate` 통과 후 `TT_PUBLISH_TOKEN=manual`로 push한다(`CONTRIBUTING.md`). 목적은 도구 경로 밖의 실수 방지이지 권한 통제가 아니다.
- 3·4번은 git pre-commit hook(`db_precommit.py`)과 검사 내용이 겹친다. Claude 세션 안에서 더 빨리, 명확한 메시지로 막기 위한 이중 장치다.
- 7번은 `db_pr publish`가 내부에서 실행하는 `git push`에도 적용된다. `db_pr.py`는 Bash로 실행되므로 guard는 `python …/db_pr.py publish` 명령도 push로 보고 `ask`를 반환한다(위 "명령 판정의 한계"의 예외로 넓게 본다 — ask 오판은 싸다 — 낱말 그물 `word_net`, L M-2: heredoc 본문 밖 줄 이음을 bash처럼 빈 글로 잇고 heredoc 본문을 붙인 명령 글 전체에(끝 표시는 원래 줄에서 찾는다 — 본문 끝 줄의 `\`가 끝 표시를 삼키지 않게, 끝 표시가 없으면 그 줄을 빼지 않는다) 이름 `db_pr`(앞이 글자·`.`·`-`가 아니고 뒤가 글자·`-`가 아님 — `test_db_pr.py`·`dbpr/` 아님)와 낱말 `publish`(앞이 글자·`.`가 아니고 뒤가 글자·`.`·`-`가 아님 — `publish.json`·`publish-preview`·`dbpr/publish.py`·`published` 아님, `${P:-publish}`는 맞음)가 함께 있다. 인터프리터·`python3 -m`·`SUB=publish; … $SUB`·`C="…"; $C`·별칭 정의·`$( )`·`python3 -c`·heredoc 안 subprocess와 무관하게 ask다. `$( )`·백틱 없이 grep·rg·echo·printf·cat·tee만인 줄과 그 줄이 연 heredoc 본문은 뺀다 — `grep -n "db_pr.py publish"`·`cat > notes.md <<EOF`는 묻지 않는다. git·gh 줄은 빼지 않는다(`git -c alias.p='!…'`·`core.pager`·`GIT_SSH_COMMAND`·`gh alias set`으로 글을 실행할 수 있다 — 그래서 커밋 메시지·PR 본문에 두 낱말이 들면 ask 오판). 글 명령만인 줄도 셸로 넘기면(`echo "…db_pr.py publish…" | bash`) ask다. 남는 한계: 낱말을 변수로 만들어 쓴 호출(`${P}lish`·`X=db; …/${X}_pr.py publish`)·인코딩한 호출, 인용 안 `<<EOF`(`echo "<<EOF"`)와 맨 `EOF` 줄로 만든 가짜 heredoc(그 사이 줄을 본문으로 뺀다), 스크립트 파일 안 호출(`bash push.sh` — eval 채점기는 결과의 `"published": true`로도 센다), 사용자 셸 프로필의 별칭·함수. 인용·`\`·`$'…'`·줄 이음으로 쪼갠 낱말(`pub"lish"`·`"$S"d""b_pr.py`·`pub\⏎lish`)은 붙여 본다. 반대로 db_pr 소스·문서를 sed·python으로 다루는 명령에 두 낱말이 함께 들면 ask 오판이다). 이슈 DB `git push` 자체는 git 규칙(6·7)으로 본다.
- **`site-defaults.yaml` 없음**: guard는 멈추지 않고(종료 코드 2를 내면 모든 도구 호출이 막힌다) 경고만 낸 뒤 사용자 config로 판정한다. 이때 커밋 검사(3·4번)가 부르는 스크립트는 종료 코드 2를 내므로 이슈 DB 커밋은 거부된다 (`contracts.md §3.2` 설정 읽기).
- **설정 없음 처리**: config가 없거나 `issue_db.path`로 레포를 판별할 수 없으면 git 규칙은 적용하지 않는다(통과). `tracker.mcp_server`와 `tracker.tools`가 모두 비어 있으면 설정 서버 규칙은 적용하지 않고 경고만 한다(setup 전 상태, 이름에 트래커 서버 단어(`jira`·`atlassian`)가 든 서버의 쓰기형 도구 거부는 적용). config가 있는데 `tracker.read_tools`가 비어 있으면 그 서버의 도구는 모두 거부한다. `tracker.write_tools`가 없으면 코멘트 예외가 없다(모든 Jira 쓰기 거부, 게시 기능 꺼짐). 사용자 config가 없으면 승인 기록을 찾을 수 없으므로 코멘트 도구도 거부한다.
- **의존성 없음·내부 오류 처리**: PyYAML 등 import가 실패하면 hook은 종료 1(Claude Code에서 비차단 오류)로 끝나 아무것도 막지 못한다. 그래서 `guard.py`·`jira_bridge.py`는 import 실패를 받아 종료 0으로 아래처럼 판정한다(guard 판정 중 예외도 guard는 같은 표를 쓴다, 입력이 JSON이 아니면 판정하지 않는다). 종료 2는 쓰지 않는다: Bash 전체(의존성 설치 명령까지)를 막아 모든 도구 호출을 막는 사고가 된다. 종료 1·2의 실제 동작은 사내 S1에서 확인한다(`tests/mocks/plugin-probe/README.md` 9번).

### 9.1 표시 보조 hook (`show_guard.py`)

**왜**: Bash·Read 출력은 사용자에게 보이지 않는다. 그런데 모델은 스크립트 출력을 요약해 답하는 경향이 있다(스킬 eval 48회 중 22회: 확인 화면의 `생성 파일|README.md|수정` 행·diff 줄, 리포트의 근거 로그 줄, 초안 검증표 행이 빠졌다). 사용자가 승인하는 것은 **자기가 본 것**이므로, 확인 화면·리포트가 요약되면 승인의 근거가 무너진다. 스킬 지침만으로는 지켜지지 않아 hook이 기계적으로 되돌린다. 판정은 eval 채점기와 같은 `common/shown.py`다(`tests/skill_evals/README.md` "사용자에게 보였다").

**대상**(의무): push 확인 화면(`## push 전 확인:` ~ `approved_hash:`), 트래커 게시 확인 화면(`## … 게시 전 확인:` ~ `post_sha256:`), Step 6 분석 리포트(결정적 줄 — 분류 후보·근거 로그와 하위 줄·로그 범위 등 — 과 `must_show`, `triage.py run`이 status ok일 때), 초안 검증표(`db_verify.py rules --draft`, 규칙마다 상태와 통과가 아니면 사유가 든 한 행 — "R1~R4 통과"처럼 묶은 줄은 인정하지 않는다). 단 전부 통과한 초안 표(모든 행이 pass이거나 사유가 정확히 `해당 없음`인 skipped, `review_required`·needs-approval·allow-cause 없음 — `shown.draft_all_clear`)는 의무가 아니다: 승인 전에 보여야 하는 push 확인 화면의 "검증 결과"로 갈음한다(10/14 사용자). fail·`fixture 없음`·pending 등 다른 사유의 건너뜀이 하나라도 있으면 그대로 의무다. 줄마다 정규화(표 칸 공백·인용 `>`·코드 울타리·글머리)한 뒤 출력 뒤에 보인 글(assistant 텍스트·질문 도구 문구)의 어디에든 있으면 보인 것이다.

| 이벤트 / 매처 | 모드 | 동작 |
|---|---|---|

| PreToolUse `AskUserQuestion\|mcp__.*__ask_user` | `pre-ask` | 질문 문구까지 더해 빠지면 질문을 `deny`. 리포트는 Step 7 분류 질문(선택지 2개 이상)일 때만 본다 |
| PreToolUse Bash(guard와 같은 그룹의 두 번째 hook — 한 그룹의 hook은 병렬로 실행되고 `deny`가 하나라도 있으면 거부) | `pre-bash` | `db_pr.py publish --approved H`·`issue_post.py approve`: 해시가 같은 화면을 찾아 화면 뒤 ~ 마지막 질문(또는 사용자 입력) 사이에 화면 전체가 보였는지 본다(해시가 변수 — `--approved "$H"`·`$(…)` — 면 마지막 stage 호출 뒤의 마지막 화면: 다시 stage한 화면을 숨겼으면 앞 화면으로 갈음하지 않고 화면 없음으로 본다. summary는 화면·해시를 바꾸지 않으므로 기준이 아니다(같은 해시 화면을 summary로 다시 보이거나 `--format json`으로 해시를 읽어도 그대로). post의 변수 `--sha`와 같다). 빠지면 `deny` "승인 질문 전에 확인 화면 전체를 보이지 않았다 — 화면을 다시 보이고 다시 승인받는다". 그 해시의 화면이 어느 도구 출력에도 없는데(리디렉션·`head`·`grep`·state.json에서 해시) 화면을 낸 호출(stage·summary / render)이 기록에 있으면 push는 **키마다 4번**(`UNSEEN_BLOCKS` — 보지 않은 화면의 push가 한 번의 재시도로 통과하지 않게, K P1-2. 키는 해시, 해시가 변수면 `push:var:<branch>`. 한도 없이 막지 않는 것은 fail-open: 큰 출력을 Claude Code가 파일로 돌리면 화면이 끝내 도구 출력에 안 나올 수 있다 — 그 뒤는 `systemMessage`만, 최종 관문은 규칙 7 `ask`), post는 **한 번**(sha 또는 `--sha`가 변수면 게시 대상 키마다) `deny`하고 `db_pr.py summary <wt> --format markdown`(post는 `issue_post.py render <KEY> --fill …`)을 파이프 없이 실행해 전문을 보이게 한다. 그런 호출이 없거나 transcript를 끝부분만 읽었으면 판정하지 않는다. `db_pr.py stage`(`--dry-run`도 — dry-run 흐름의 stage도 확인 화면을 낸다): 열린 초안 검증표(전부 통과한 표 제외 — push 확인 화면으로 갈음)가 보이지 않았으면 `deny`(그 창은 stage로 닫힌다) |
| PostToolUse Bash | `post` | 결과에 화면·리포트·초안 검증 결과가 있으면 `additionalContext`로 "이 출력은 사용자에게 안 보인다. 다음 메시지에 전문(N줄)을 글자 그대로, 같은 메시지 끝에 질문" 안내만 |

- **의무가 생기는 곳**: 화면은 그것을 낸 스크립트 호출(Bash의 `db_pr.py stage`·`summary`, `issue_post.py render`) 결과와 그 호출이 리디렉션(`>`·`>>`·`&>`, `/dev/*` 제외)으로 쓴 파일을 다시 읽은 결과만(절대 경로는 경로 전체, 상대·`$VAR` 경로는 파일 이름으로 비교), 리포트는 `triage.py run`이 있을 때 마지막 run의 리포트(`JOB/report.md`)만 본다. 문서·fixture를 `cat`·Read한 결과의 화면 모양 글은 의무가 아니다(채점기는 Read로 다시 연 화면도 센다).
- **창 닫힘**: 화면 = publish·discard(push)·approve(post)·해시가 다른 다음 화면, 리포트 = Step 7 분류 질문·stage, 초안 표 = 다음 초안 검증·stage(`--dry-run` 포함 — dry-run 흐름의 stage도 worktree를 만들고 확인 화면을 낸다). 단 전부 통과가 아닌 결과(`draft_all_clear` 아님)는 **다른 계획**(`--plan` 끝 두 마디가 다르다 — `plan-narrow.json`)의 초안 검증으로 닫히지 않고, 같은 계획의 재실행·작업 경계(`triage.py run`, `db_pr.py discard`·`lock acquire|release`)·stage까지 열려 있다: 좁힌 안을 다른 파일로 돌려 통과해도 처음 실패 표(걸린 fixture·시그니처 전역 키)를 보이고 사용자가 좁힐지·허용할지 고른다(h3-d eval 18). 같은 계획을 고쳐 다시 돌린 읽을 수 있는 결과는 앞 결과를 대신한다(`shown.draft_end`, 채점기와 같다). 단 고치지 않고 다시 돌려 같은 결과를 덜 보이게 찍은 것(같은 규칙은 상태가 같고 사유가 앞 사유의 앞부분, 더한 행은 통과뿐 — `[:150]`으로 자른 사유, `shown.weaker_copy`)은 앞 결과를 대신하지도 따로 의무가 되지도 않는다(h5-18b eval 18). 결과를 표(`| R1 | pass | … |`)로 찍은 출력도 읽는다. hook이 거부해 실행되지 않은 호출(결과가 `PreToolUse:… hook error`)은 창을 닫지 않는다 — 거부된 뒤 다시 시도해도 다시 본다. 이 제외는 eval 채점기에도 같다(실행되지 않은 명령은 실행한 것이 아니다; 기록된 48 run 재채점 차이 0). Stop·질문은 열린 창만 본다.
- **PreToolUse의 transcript 기다림**: transcript는 비동기로 쓰여 PreToolUse 때 같은 응답의 앞 텍스트 블록이 아직 없을 수 있다(10/14 sm4: 화면 전문을 쓴 직후의 질문 8건이 거짓 거부). pre-ask·pre-bash는 지금 호출(`tool_use_id`)이 transcript에 기록될 때까지 최대 2초(새로 붙은 바이트만 확인) 기다린 뒤 판정하고, 끝내 기록되지 않으면 거부하지 않는다(stderr 경고). 입력에 `tool_use_id`가 없으면 기다리지 않고 바로 판정한다. **전제**: 한 응답(같은 `message.id`)의 텍스트 블록은 그 tool_use보다 먼저 transcript에 붙는다(sm4 transcript 300개 응답에서 예외 없음, `tests/mocks/plugin-probe/README.md` 13번 — 사내 버전에서 다시 확인).
- **되돌림·거부 문구**: 첫 줄 맨 앞은 표식과 키다. Stop은 `[telephony-triage] show-guard <key> — 되돌림(오류 아님): <종류>을/를 요약했다(빠진 줄 k/m). Bash 출력은 사용자에게 보이지 않는다.` + 할 일 한 줄, 거부(pre-ask·pre-bash)는 `… <key> — 거부됨(오류·일시 장애 아님). 이 호출은 실행되지 않았다. 기다리거나 같은 호출을 그대로 다시 하면 또 거부된다.` + `까닭: …(Bash 출력과 이 거부 문구는 사용자에게 안 보인다)` + `할 일: …`(질문은 보일 줄을 질문 본문 앞이나 바로 앞 글에 넣고 다시 부른다, stage는 먼저 글로 표를 쓰고 같은 응답에서 같은 stage를 다시 — 새 질문을 만들지 않는다) — 10/14 모델이 거부를 일시 오류로 읽고 기다렸다 같은 호출을 되풀이하거나(`sleep 3`) 거부 문구가 사용자에게 보인다고 믿은 일 때문이다. 그 뒤 빠진 줄 예(8줄까지) + 붙일 화면 전문(12KB 이하일 때). `<key>`는 `push:<approved_hash>`·`post:<sha 앞 16자>`(`--sha`가 변수라 화면을 못 고르면 `post:render:<KEY>` — 게시 대상 키별로 한 번)·`report:<run 호출 id>`·`draft:<초안 결과 해시>`(`--plan` 인자(`--plan`은 끝 두 마디)·규칙·상태·사유 — 같은 작업에서 같은 결과로 다시 돌려도 같은 키라 한도를 함께 쓴다). 막은 횟수는 그 의무가 생긴 뒤의 표식만 세고, 초안 표는 같은 작업(마지막 `triage.py run` 뒤)에서 같은 결과가 처음 나온 곳부터 센다 — 다른 작업의 같은 키는 세지 않는다. triage를 다시 돌리면 새 작업으로 센다(재분석은 표를 다시 보일 이유).
- **한도**: 같은 키로 막은 횟수(transcript의 표식이 든 Stop 피드백·거부된 도구 결과)가 **2회**(`MAX_BLOCKS`)에 이르면 더 막지 않고 `systemMessage` "[telephony-triage] 확인 화면 일부를 답에 보이지 못했다(재시도 한도) — <경로>를 직접 확인"만 낸다(안전 관문은 그대로이므로 사람이 직접 확인한다). 단 거부된 호출을 똑같이(도구 이름과 `description`을 뺀 입력이 같다) 그 사이 보인 글·질문·사용자 입력 없이 다시 한 거부(다른 도구 호출 — `sleep 3` — 만 있었다)는 키마다 1번(`BLIND_FREE`)까지 세지 않는다: 거부를 일시 오류로 읽고 되풀이한 것은 표를 보일 기회를 쓴 것이 아니기 때문이다(10/14). 그래서 같은 키 거부는 많아야 3번이고, 그때 거부 문구에 "방금 거부된 것과 똑같은 호출이다 … 글을 먼저 쓴다"를 더한다. Stop 피드백은 덜 세지 않는다. Stop이 연이어 막혔는데(`stop_hook_active`) 이번 턴 transcript에 표식이 없으면(다른 hook이 막았거나 피드백이 기록되지 않는 버전) 횟수를 셀 수 없으므로 아무것도 내지 않는다. transcript 끝 16MB 안에 실제 사용자 입력이 없으면(이번 턴의 시작을 모른다) Stop·질문은 판정하지 않는다. Claude Code 자체의 연속 계속 한도(8회)도 있다. 화면이 어느 도구 출력에도 없던 publish의 거부(위 pre-bash 행)는 이 한도를 쓰지 않는다 — 키마다 4번(`UNSEEN_BLOCKS`)까지 거부하고 두 번째부터 거부 문구에 "다시 불러도 거부된다(키마다 4번)"을 더한다(post는 한 번). 그 뒤는 `systemMessage`만 낸다. 화면이 나온 뒤의 보통 판정은 그 화면부터 다시 센다.
- **내부 오류(fail-open)**: 입력·transcript를 못 읽거나, import(`common/shown.py`) 실패·판정 중 예외면 판정하지 않고 stderr에 경고한다(Stop은 이번 턴 transcript에 화면·리포트 흔적이 있을 때만 `systemMessage` "show_guard 판정 못 함"도 — 매 턴 되풀이하지 않게). 입출력은 UTF-8로 읽고 ASCII(JSON 이스케이프)로 쓴다(Windows 콘솔 인코딩과 무관). 이유: 표시 보조일 뿐 안전을 맡지 않는다 — 실제 관문(규칙 7 publish `ask`, `approved_hash`·pre-push 토큰, 규칙 2 게시 승인 기록·`ask`)은 그대로라 hook이 열려도 승인 없는 쓰기는 생기지 않는다. 반대로 닫히면(모든 질문·Stop을 막으면) 세션이 멈춘다. pre-bash(G3)도 같다.
- 파일을 쓰지 않는다. 종료 코드는 항상 0. transcript는 끝 16MB만 읽고, 그 안에 화면·리포트·초안 표의 흔적(`## push 전 확인:`·`게시 전 확인:`·`triage.py`·`--draft`·`db_pr.py`·`issue_post.py`)이 없으면 바로 끝낸다.
- **전제**: hook 입력의 `transcript_path` 파일이 있어야 한다. 세션을 저장하지 않는 실행(`claude -p --no-session-persistence`)에서는 파일이 생기지 않아 아무것도 판정하지 않는다(stderr 경고만, fail-open). 스킬 eval 실행기는 plugin 모드에서 세션을 저장하고 transcript를 run 디렉토리로 옮긴다(`tests/skill_evals/README.md`).
- **한계**: 최선 노력이다. Read로 연 화면은 `post` 안내가 없다(matcher Bash). 화면을 낸 호출 없이 손으로 쓴 해시로 publish하면(기록에 stage·summary가 없음) 보지 않는다 — 그 publish는 규칙 7 `ask`와 승인 해시·pre-push 토큰이 막는다. `$PY $S/db_pr.py publish`처럼 변수 인터프리터 뒤 호출은 `shown.PUSH_END`가 놓쳐 show_guard가 보지 않는다 — guard 규칙 7은 낱말 그물로 보고 `ask`한다(K P0-1, L M-2). 같은 계획 파일을 고쳐 초안 검증을 다시 돌리면 앞 결과의 창은 닫히므로 그 첫 실패 결과를 보였는지는 보지 않는다(다른 계획 파일로 돌린 것은 본다). 좁힌 계획을 다른 작업 디렉토리 이름이 아닌 곳에 써도 같은 작업으로 본다(작업 경계는 lock·discard·triage run). 같은 응답의 앞 텍스트가 PreToolUse 때 transcript에 있다는 것, Stop 피드백이 `isMeta`로 남는 것, 여러 그룹·hook이 걸리면 모두 실행되고 `deny`가 이기는 것(거부 결과 `PreToolUse:<tool> hook error: <reason>`, `is_error: true`)은 사외 실험(2026-10-14)으로 확인했고 사내 버전은 S1에서 다시 확인한다(`tests/mocks/plugin-probe/README.md` 10~12번).
