## 8. 개인정보 마스킹 (`mask_pii.py`)

이슈 DB에 들어가는 모든 로그 예시, fixture, 본문, 리포트에 적용한다. **extractor와 매칭 전 로그 줄에도 적용한다** (`parse_logcat.py parse --mask`, `07-workflow.md §Step 3`). 마스킹 함수는 `common/`에 있고 `mask_pii.py`와 `parse_logcat.py`가 공유한다.

| 항목 | 탐지 방법 (참고) | 치환 |

| IP 주소 | IPv4/IPv6. IPv4 값 바로 앞이 `version`·`build`·`release`·`rev`·`fw`·`sw`·`baseband`·`kernel`·`v` 문맥이면 제외(버전 문자열). IPv6는 형식 규칙 외에 주소 키(`addr`·`address`·`ip`·`ipv6`·`gw`·`gateway`·`dns<n>`) 바로 뒤(`addr:<v6>`, `/64` 허용)·끝이 `:`인 잘린 표기, 문맥 없는 6묶음 이상 조각(`::` 없음, 3~4자리 묶음 2개 이상, MAC 모양 제외 — 줄 경계에서 쪼개진 주소) | `<IP#n>` |

| 이메일 | 이메일 형식 | `<EMAIL#n>` |
| 자격증명 성격 값 | SIP `Authorization`/`WWW-Authenticate` 헤더의 `response=`, `nonce=`, `cnonce=`; AKA `RES`/`AUTN`/`AUTS`/`Ki`/`Kc`/`CK`/`IK`/`OPc`/`OP`/`K`(16 hex 이상, 대소문자 구분 — `KI`·`KC`·`OPC` 대문자 변형은 받고 소문자 `ki`·`ck`는 받지 않음); 키 이름 문맥 `password`, `passwd`, `pwd`, `secret`, `token`, `key`의 값(`token`은 짧은 숫자 — 10진 10자리 이하·`0x`+16진 8자리 이하, RIL 요청 token — 제외, 값은 ASCII까지라 `token=612로`도 짧은 숫자; `key` 밖 다섯은 앞에 낱말이 붙은 키 `mPassword`·`apn_password`·`userPwd`·`clientSecret`·`authToken`도 — 값은 `=` 앞까지, 영문+숫자 혼합이고 상태 낱말·대문자 열거형이 아닐 때만, 접두 token은 `@`가 든 자바 객체 표기 값도 제외); `pin`·`puk`(앞에 `m` 허용)은 숫자 4~8자리만; `pass`·`passcode`는 상태 낱말(`enabled`·`ready`·`ok`·`passed`·`true` 등)·대문자 열거형·3자리 이하 숫자 제외; `Bearer <토큰>`(대소문자 무관)·JWT(`eyJ…`) (IMS REGISTER 로그가 fixture에 들어가므로 필요) | `<CRED#n>` |

- **번호 토큰(가명화)**: 같은 파일(분석 1회) 안에서 **같은 원래 값은 같은 번호**, 다른 값은 다른 번호로 바꾼다(`<CELL#1>`, `<CELL#2>`). 번호는 파일 안에서 처음 나온 순서로 매긴다. 그래서 "셀이 바뀌었다", "같은 번호로 재시도했다" 같은 **값 비교 관계가 마스킹 뒤에도 보존**되고, 기존 파서의 판별 로직이 마스킹된 fixture에서도 같게 동작한다 (`16-existing-assets.md §16.3`). 원래 값과 번호의 대응표는 메모리에만 두고 저장하지 않는다.
- 시그니처와 extractor는 특정 번호(`#1`)가 아니라 토큰 종류(`<CELL#\d+>`)나 "같은 토큰/다른 토큰" 관계로만 쓴다 (`db_lint`가 특정 번호 고정을 경고).
- **문맥 기반 탐지를 우선**하고, 숫자 길이만으로 판정하는 규칙은 보수적으로 쓴다 (빌드 번호, 타임스탬프 오탐 방지).
- 알려진 한계: 문맥 없는 15자리에 `_`·영문이 바로 붙은 값(`…518_slot1`)은 잡지 않는다(빌드 번호 오탐 방지, 키 문맥이 있으면 잡는다). 사람 이름·자유 텍스트, 소수 2자리 좌표, 키 없는 serial, 16진 IMEI 변형, 접두 비밀 키의 글자뿐·숫자뿐인 값(`mPassword=letmein`)도 잡지 않는다. 줄 경계에서 쪼개진 IPv6의 5묶음 이하 조각, `key:` 바로 뒤 MAC(`macaddr:aa:bb:…`, MAC 형식 규칙의 앞 경계 `:`에 막힘)도 잡지 않는다. 반대로 1묶음 압축 IPv6 모양(C++ `std::string`의 `d::s`)은 IP로 가린다(과잉) — 사내 로그 표본으로 다시 본다(TODO(SITE:S13)).
- 로그 줄 전용 제품 코드 규칙의 문맥에는 벤더 태그·드라이버 이름을 두지 않는다(설정 키도 없다): 모뎀 모델 코드 `m<4자리>`는 줄 어디든 ` <소문자 낱말>:`(커널/벤더 태그 꼴, 태그 칸에 고정하지 않음)이 있으면 가린다 — 특정 태그 문맥보다 넓다(과잉 허용). 문맥이 넓어 이 규칙은 값 규칙(`ro.*`·fingerprint·variant·APN 사용자 이름 등) 뒤에 돈다: 값 안에 `m<4자리>`가 있으면 값 전체가 값 규칙 토큰 하나로 가려진다(앞에 돌면 값이 쪼개져 일부가 평문으로 남는다).
- 키 이름은 따로 적지 않으면 대소문자를 가리지 않고(AKA 키만 구분), `key=v`·`key: v`·JSON `"key":"v"` 형식을 모두 받는다.
- 경계·낱말·숫자는 ASCII다(규칙을 `re.ASCII`로 컴파일): 값 앞뒤에 공백 없이 붙은 한글(`010-1234-5678로`·`주소192.0.2.10은`)도 경계라 제 종류로 가린다. 키·값 사이 공백과 값 끝은 유니코드 공백(NBSP·U+3000)도 받는다. 규칙은 글을 접어서 본다(`fold_ascii`: 전각·아라비아-인도 숫자 → ASCII 숫자, 유니코드 공백 → 공백, 글자 수 같음) — 전각 IMSI·NBSP 뒤 값도 가리고, 출력에는 원문 글자가 남는다. `(?i)`도 ASCII만 접어 `paſs=`·`PİN=`은 키가 아니다.
- 성능: 마스킹은 줄마다 도는 hot path다. 키 이름 문맥 규칙은 소문자 줄에 그 키 부분문자열이 있을 때만 돈다(`Rule.gate`, 결과 불변 — `test_gate_does_not_change_result`, 한글 줄 포함).
- 오탐 예외는 `issue-db.config.yaml`의 `mask.allow_patterns`로 관리한다 (메인테이너 리뷰). `db_lint`가 정규식 오류(`schema`)·안전성(`regex-unsafe`)과 대표 PII 표본 전체에 맞는 넓은 패턴(`mask-allow-too-broad`, 예: `.*`)을 오류로 낸다. 정규식이 틀리면 `mask_pii`는 종료 코드 2다.
- Android 자체 마스킹(`***`, `xxxxxx`)은 그대로 둔다.
- extractor와 매처는 항상 마스킹된 텍스트에 대해 돈다. 그래서 시그니처와 extractor 패턴은 마스킹 이후 텍스트 기준으로 작성하고, 그 안의 원본 식별자 패턴은 `db_lint`가 금지한다 (`04-parser-matching.md §5.11 (1)`).
- 마스킹은 같은 입력이면 항상 같은 출력을 내고, 이미 마스킹된 입력(`<…#n>` 토큰)에 다시 적용해도 결과가 같다(멱등, 기존 토큰은 그대로 둔다). 분석과 회귀(마스킹된 fixture를 다시 파싱)의 일치를 위해서다.
- **이미 토큰이 있는 입력**(부분 마스킹된 외부 로그, 사람이 원본 값을 끼워 넣은 fixture): 먼저 입력 전체에서 종류별 기존 최대 번호를 구하고, 새 원본 값에는 그 다음 번호부터 준다. 예: `<CELL#1>`이 이미 있는 파일에 새 셀 ID가 나오면 `<CELL#2>`. 서로 다른 값이 같은 토큰이 되어 값 비교 관계가 거짓으로 바뀌는 것을 막기 위해서다.
- 파서 백엔드·외부 파서가 낸 이벤트의 `msg`와 `fields`도 extractor 전에 같은 함수(같은 번호 대응)로 마스킹한다 (`parse_logcat.py parse --mask`).
- **갈린 덤프 조각**: 마스커는 줄 단위지만 oFono 덤프 함수가 IMSI·ICCID 값을 두 줄에 가르면(덤프 함수 `<이름>() ` 뒤가 조각 — 이름은 site-defaults oFono 블록 `dump_func`, 기본 placeholder, 시각 뺀 앞머리 같고 1초 안, `common/dumpjoin.py`) 키 있는 IMSI·ICCID 규칙(`imsi=`·NAI·`iccid=`·`ICCID(`)만 이은 글에 돌려 경계를 넘는 값을 조각마다 전체 값의 토큰 하나로 가린다(개수 1회, 조각 글자도 같은 번호 — `fields`). 키 없는 숫자 규칙은 이은 글에 쓰지 않는다. `mask_pii`(파일·이벤트·`--check`)·`parse --mask`(시간 창 밖 조각까지 묶음)·`markers`·`cut`(전체 줄로 묶은 뒤 고른 줄에 적용)·`residual`·`redact`가 같다.
- **짝 주석 값**(oFono 설정 짝 규칙·내장 gril의 `proto` 주석, `17-platforms.md §9-3`): site 정규식이 뽑을 수 있는 값이라 `--mask`면 한 번 더 본다. `request`·`error`는 같은 줄에서 가린 값이면 그 토큰, 아니면 텍스트 규칙으로 마스킹한다. `serial`은 짝 규칙이 10진 1~10자리만 주석에 싣고(11자리 이상 IMSI·ICCID·전화번호 모양은 주석 없음), `--mask` 출력에는 같은 수(앞 0 무시)가 마스킹된 같은 줄의 토큰 밖에 숫자로 따로 보일 때만 남긴다(숫자 경계 — 더 긴 숫자의 조각은 안 된다) — 아니면 `null`(파생 이벤트 필드에도 없다). 다른 줄에서 복사한 serial(`kind: hop` 아래 줄)은 같은 줄 대조를 할 수 없어 `null`이다. 번호 표 전체가 아니라 같은 줄만 본다(앞 줄의 같은 글자와 우연히 겹치지 않게). 한계: 가린 값에서 뽑은 serial과 같은 수가 그 줄의 가리지 않은 곳에 숫자로 따로 보이면 남는다(숫자 자체는 이미 출력에 보이고, "serial = 가린 값" 연결만 남는다). Android 주석은 `proto`가 없어 그대로다.
- `--check` 모드는 검출 시 종료 코드 1이다. NUL이 든 파일도 건너뛰지 않는다(`--staged`·`--changed`: NUL을 지운 줄과 공백으로 바꾼 줄을 함께 검사 — UTF-16·잘린 logcat). `db_precommit`(`--staged`), `db_pr stage`(`--changed`), Claude hook이 쓴다.
- 항목별 누락/과잉 마스킹 테스트를 둔다.

### 8.1 Jira 텍스트

마스킹 표는 logcat 형식 기준이지만, Jira에서 읽은 텍스트도 리포트·계획·PR 본문에 들어가므로 같은 규칙을 적용한다. Jira 설명에는 테스터 이름, 고객 전화번호, IMEI가 자유 텍스트로 자주 적히고 **사람 이름은 위 표로 잡히지 않는다.** 그래서 마스킹에만 기대지 않고 **저장하는 정보 자체를 줄인다.**

- 이슈 DB(`issues/<KEY>.yaml`, 원인 본문, 피드백)와 PR 본문에는 Jira의 **구조화 필드**(`model`, `sw`, `platform_version`, `carrier`, `occurred_on`)와 **사용자가 확인한 한 줄 요약**(`note`), 그리고 있으면 마스킹된 **실패 스텝 한 줄**(`failed_step`, ≤200자)만 넣는다. Jira 요약·설명·코멘트 **원문은 저장하지 않는다** (`03-issue-db.md §5.4 (2)`).
- **MCP 응답 원문은 모델 컨텍스트에 넣지 않는다.** Jira `get_issue`·`get_comments` 결과는 PostToolUse hook(`jira_bridge.py`, §9 9번)이 `<work_dir>/<KEY>/issue_raw.json`에 쓰고, 모델에는 마스킹된 요약만 보인다. `triage.py run`이 그 파일을 `jira_fields.py extract --consume`으로 읽고 지운다. 후처리 마스킹은 이미 컨텍스트에 들어간 원문을 되돌릴 수 없기 때문이다. hook 출력 대체가 안 되는 Claude Code 버전이면(S1에서 확인) 스킬이 응답을 그 파일에 저장하는 예전 경로로 돌아간다. 그때 스킬은 격리 hook이 동작하지 않았다(원문이 대화에 들어왔다)고 사용자에게 알린다. 그 알림은 노출 **뒤**라 노출 자체를 막지 못하므로, S1 확인 전(site-defaults `tracker.isolation_confirmed`가 참이 아님)에는 guard(규칙 2)가 읽기 도구 호출마다 `ask`로 그 위험을 보이고 사람이 허용할 때만 읽는다(`-p` 비대화형에서는 거부). OpenCode는 어댑터 `after`가 결과를 직접 바꾸고 자체 관문이 있어 해당하지 않는다.
- `field_map`으로 뽑은 텍스트 필드(요약, 설명, 재현 절차, 코멘트)는 Step 2에서 읽은 직후 `mask_pii`를 거치고, 이후 단계(리포트, 키워드 보너스, `note` 초안)는 마스킹된 텍스트만 쓴다. 계획 `issue`에는 원문 필드를 두지 않는다 (`contracts.md §작업 계획`).
- **실패 스텝**(`--failed-step` 원문·`--steps-file` 내용)의 원문은 `trace.jsonl`·`triage-state.json` 같은 상태·추적 파일에 쓰지 않는다. `triage.py`가 같은 프로세스 안에서 마스킹한 뒤에만 `issue.json`·`issue_meta.json`·계획에 남기고, 하위 스크립트 인자에도 원문을 넘기지 않는다.
  `--steps-file`이 zip이면 **메모리에서만 읽는다**(풀지 않는다 — 항목 선택·크기 상한·절대/`..`/암호화 항목 거부는 `07-workflow.md §Step 2`). 개발자가 붙여넣은 스텝 목록은 `WD/<KEY>/steps-pasted.txt`(work_dir는 700 권한 디렉터리)에 쓰고 `--steps-file`로 넘기며, **커밋하지 않고** 도구가 읽을 때 마스킹한다. 원문이므로 작업이 끝나면 지운다: `db_pr discard`, `--force` 없는 `lock release <작업 키>`(`triage.py release` 포함, `triage.py run --analysis-only`가 ok로 끝나며 lock을 풀 때도), `cleanup`. 스텝 이름·표 내용은 `parse_logcat markers --step-events`의 인자에 없고(규칙은 이슈 DB 설정에서 읽는다) 출력에는 이름·시각만 있다. 리포트의 zip 멤버 경로는 마스킹해서 쓴다.
- **재사용 캐시**(`<work_dir>/<KEY>/analysis-cache.json`)에는 마스킹된 분석 결과(후보·근거·코드 경로·마스킹된 스텝 이름)와 입력의 해시만 둔다. `triage-state.json`의 `job`에는 입력 로그의 경로·이름·sha·크기와 실행 이력만 있고, 실패 스텝·steps-file 원문은 어느 쪽에도 없다. needs_input으로 멈추면 `pending`에 질문 종류와 시각(`{kind, asked_at}`)만 남긴다(질문 문구·선택지는 다른 작업 키·경로를 담을 수 있어 쓰지 않는다) (`07-workflow.md §입력 재사용`).
- **`runs/<n>/`**(`--more-logs`·재분석 때 덮어쓰기 전에 복사한 이전 `analysis.json`·`report.md`, 최근 5개)에는 이미 마스킹된 결과만 있다. `events.json`·`match.json`·로그 원문은 보관하지 않는다 (`07-workflow.md §추가 로그 재분석`).
- **Jira 코멘트 본문**(`issue_post.py`, `07-workflow.md §Step 9`): 이미 마스킹된 `analysis.json`·`issue.json`·계획 값으로 결정적 칸을 채우고, LLM 칸(`post.fill.json`)은 그 본문을 기준으로 만든 마스커(기존 토큰 다음 번호)로 마스킹한 뒤 렌더한 전체 본문에 한 번 더 적용한다. 마스커 검출이 남거나, LLM 칸에 로그 원문 줄 모양이 있거나, Jira 요약·설명·코멘트와 40자 이상 같은 연속 부분이 있으면 종료 1이다. 그래도 사람 이름은 잡지 못하므로 스킬 규칙과 확인 화면(본문 그대로 표시)으로 막는다. 게시 응답 원문은 컨텍스트에 넣지 않는다(§9 9번).
- **작업 기록**(`JOB/trace.jsonl`, `contracts.md` "작업 기록"): db_pr의 `stage`·`publish`·`discard` 행에는 결과 코드·PR 번호·사유(`after-publish`·`dry-run`·`cancel`)만, 정보 행(`explore`·`module`·`checked`)에는 종료 코드·`purpose`·불리언·모듈 이름 `<p>/<dir>`만(로그 글·PII 없음) 쓰고, `stage` 오류 메시지는 마스킹·URL 자격증명을 가려 120자까지만 둔다. `job_status --doctor`·`last-run-error`도 같은 가림을 거친 뒤 보인다.
- `note` 초안은 스킬이 마스킹된 요약에서 한 문장으로 만들고 사용자가 확인한다. 사람 이름·고객명은 초안에 넣지 않는다.
- `db_lint`는 `issues/*.yaml`의 `note`, 원인 본문, `cp_evidence`에 대해서도 원본 식별자 패턴(표의 항목)을 검사한다.

## 9. Hooks (`hooks/hooks.json`)

**적용 범위**: 플러그인 hook은 플러그인이 켜진 모든 세션에 적용된다. `record`도 같은 hook(Jira 읽기·승인 코멘트, 커밋·push 검사)을 거친다. `record` 전용 hook은 없다(표시 보조 hook `show_guard.py`도 모든 흐름에 같다, §9.1). 그래서 git 관련 hook은 모두 먼저 **대상 레포를 판별**한다. `guard.py`가 명령의 작업 디렉토리(cwd, `git -C <dir>`)에서 `git rev-parse --git-common-dir`을 구해, config의 `issue_db.path` 레포(그 worktree와 읽기 스냅샷 포함)일 때만 규칙을 적용하고, 아니면 아무것도 하지 않는다. **플랫폼 프로필이 여럿이면**(`17-platforms.md`, 최상위 android 프로필 + `platforms.<이름>`) 사용자 config에 있는 **모든 프로필**의 clone·`work_dir`·원격·base 브랜치를 보호한다(`platform.enabled`·선택 플랫폼과 무관 — 플러그인을 두 벌 설치해도 서로 보호된다). 규칙 2(승인 기록 파일)·8·11과 git 규칙(3~7)이 그렇고, git 규칙은 cwd가 속한 프로필의 base 브랜치를 쓴다. 이름이 잘못된 프로필의 clone도 보호한다. 프로필이 하나면 판정은 이전과 같다. `gh`·MCP 쓰기(11번)는 대상 레포를 따로 판정하고, Bash의 clone 변경 차단(8번)은 clone **본체**(git dir이 `<clone>/.git`)에만 적용한다(작업 worktree·`_snapshot` 제외).

**매처 원칙**: `hooks.json`의 matcher는 도구 이름까지만 거른다. 명령 내용과 서버 판정은 `guard.py`가 한다.
- Bash 규칙: matcher `Bash`.
- Jira 규칙: matcher **`mcp__.*`** (모든 MCP 도구). `guard.py`가 도구 이름 `mcp__<server>__<tool>`의 서버 접두사를 config `tracker.mcp_server`와 `tracker.tools` 도구 이름의 서버 접두사(합집합, 플러그인 번들 서버 `mcp__plugin_…`도 덮는다)와 비교해서, **그 서버의 도구만** 판정한다. 서버 이름은 `[^A-Za-z0-9_-]`→`_`로 정규화해 비교한다(관측 기반 추정, S1 확인). 다른 서버 도구는 그대로 통과시킨다. 서버 이름을 matcher에 직접 넣지 않는 이유는 서버 이름이 사용자 config에 있고 플러그인 hooks.json은 고정 파일이기 때문이다.
- `tracker.read_tools`는 **전체 도구 이름**(`mcp__<server>__<tool>`)으로 저장하고, guard는 전체 이름(서버 부분 정규화)으로 비교한다. 플러그인 hook에 전달되는 MCP 도구 이름 형식은 S1·S3에서 확인한다 (`14-site.md §14.2`).

**명령 판정의 한계**: `guard.py`의 명령 파싱은 **최선 노력**이다. `git -C <dir>`, `cd <dir> && git …`, `;`/`&&`/`||`로 이어진 명령, `sh -c "…"`/`bash -c "…"`·`eval "…"` (중첩 한도 안), 앞 래퍼(`env`(`-u`·`-C`·`-S` 포함)·`timeout`·`nice`·`ionice`·`stdbuf`·`sudo`·`setsid`·`time -p`·`exec -a`·`nohup`·`command`·`xargs`(정적 인자만))를 풀어서 판정한다. 값 받는 래퍼 옵션(`env -C`·`sudo -D`·`timeout -s/-k`·`nice -n`·`ionice -c` 등)의 값이 다음 낱말이면 그 사이 리디렉션(대상째)은 bash처럼 먼저 뗀다(`env -C </dev/null <dir> …`·붙은 `env -C</dev/null <dir>`도 값은 `<dir>` — 11/04 P2). 따옴표 밖 연산자만 리디렉션이다: 인용한 값(`sudo -p '<pw>'`·`time -f '<%e>'`·`xargs -E '<<'`·`time -f \<%e`)은 옵션 값이다(11/04 재리뷰 P0 — 값으로 먹지 않으면 뒤 명령 낱말이 리디렉션 대상으로 사라졌다). 명령 앞의 셸 예약어(`if`·`then`·`do`·`while`·`{`·`!`·`function NAME`·`coproc`)와 리디렉션(`>/dev/null`·`2>&1`·`</dev/null` — 대상째)은 떼고 명령 낱말을 찾는다(모르는 머리가 명령을 가리지 않게, H-A1 r5). 작은따옴표 밖 줄 이음(`\`+줄바꿈)은 bash처럼 지우고(`gh api \⏎ --method PUT …`), `$'…'`은 풀어 읽는다(닫는 `'`는 bash 어휘 분석처럼 먼저 찾고 — `\` 뒤 한 글자는 건너뛴다 — 그 안에서만 푼다. 인용 끝의 `\c`는 글자 그대로다: `$'\c'; git push …`의 뒤 명령도 판정한다, 재리뷰 P0. NUL — `\0`·`\x00`·`\u0000`·`\c@` 등 — 이 나오면 bash처럼 그 인용의 나머지를 버린다: `$'a\0b'c`는 `ac`. 서로게이트 코드 포인트는 U+FFFD. 명령 글의 날 NUL은 빼고(bash는 입력의 NUL을 버린다) 짝 없는 서로게이트는 U+FFFD로 본다 — 회귀 수정 R2). `cd -`·`pushd`·`popd`는 같은 명령 글 안에서 bash 의미대로 따라가고(`pushd -n`·`popd -n`·`popd +N`(N≥1)은 cwd를 바꾸지 않고 스택만, `popd`·`popd +0`은 맨 위 칸으로, 인자 없는 `pushd`는 맨 위 두 칸을 바꾼다), 따라갈 수 없으면 모르는 디렉토리다. **실패할 수 있거나 대상을 모르는 이동은 이전 cwd 후보를 버리지 않는다**(회귀 수정 R1): 빈 스택이나 이 명령 글 밖 스택의 `popd`·인자 없는 `pushd`(Claude Code는 Bash 호출마다 새 셸이라 앞 호출의 스택은 없다 — bash는 실패하고 cwd는 그대로다), `pushd ±N`·`popd -N`, 이전 디렉토리를 모르는 `cd -`, `cd ±N`, 분기를 합쳐 스택이 달라진 뒤의 `popd`(쌓은 칸 모두로 본다), 없는 경로·셸이 풀 경로(`cd "$D"`)·들어갈 수 없는 경로(stat 오류 — 255바이트를 넘는 경로 칸(ENAMETOOLONG)·남의 홈 아래(EACCES) 등 —, x 권한 없음)로의 cd·pushd, bash가 거절하거나 다른 셸에선 뜻이 다른 꼴(cd의 `-L`·`-P`·`-e`·`-@` 밖 옵션, pushd·popd의 `-n` 밖 옵션 — zsh `popd -q`, 남는 인자 — zsh `cd a b`는 경로 바꾸기: 이전 후보·옵션을 무시한 대상·남는 인자면 모르는 디렉토리를 모두 보고 스택을 모른다고 본다, 재리뷰). `dirs`에 인자가 있거나(`dirs -c`는 스택을 비운다 — 뒤 popd는 실패한다) `DIRSTACK`이 나오면 스택 칸을 모른다. cd 대상의 stat 오류는 판정 예외가 아니라 실패할 수 있는 이동이다(재리뷰 P0 — 예전에는 그 예외가 판정 전체를 내부 오류 판정으로 무너뜨려 같은 명령의 병합·main push가 ask로 약해졌다). 모르는 디렉토리 후보는 git 규칙(3~8·12)에서 판정하지 못하는 후보다(규칙 11은 4-c부터 cwd를 보지 않는다) — 그래서 이전 후보를 버리지 않는다. 바로 뒤가 `&&`면 이동이 실패할 때 뒤 명령은 돌지 않으므로 이전 후보는 그 and-or 목록의 `||` 뒤와 목록 끝(다음 명령)에만 남는다. `!`로 부정한 cd(`! cd X && …`)는 반대로 `&&` 뒤가 cd가 실패했을 때 돌므로 미루지 않고 이전 후보와 곧바로 합친다(재리뷰). 조건부·분기 뒤 cwd 후보가 상한(8)을 넘으면 처음 후보, 보호 뿌리(사용자 설정의 모든 프로필 clone·`work_dir`(작업 worktree·스냅샷)·스킬 소스) 안의 가장 최근 후보 8개(그보다 많으면 나머지는 그 후보가 든 레포 꼭대기 — `.git`이 있는 곳 — 나 작업 폴더 `<work_dir>/<KEY>`로. 뿌리 자체로 접으면 worktree·작업 폴더가 work_dir이 돼 git 규칙·기록 검사를 건너뛰었다, 재리뷰), 그 밖의 가장 최근 후보들을 남기고 나머지를 모르는 디렉토리 하나로 접는다(회귀 수정 R4 — 마지막 cd 대상을 버리지 않는다, 재리뷰 — 처음에 들어간 clone이 뒤의 조건부 cd·실패할 수 있는 이동에 밀려 접히지 않는다. 접힌 후보는 모르는 디렉토리다). 1024자보다 긴 후보(상대 cd가 길게 이어진 것)는 실제 경로(심볼릭 링크를 푼 것 — 짧은 후보를 git이 푸는 것과 같다, bash `cd -P`·글자 경로가 없을 때의 기본 cd)와 `..`·`.`을 글자로 접은 경로(bash 논리 cd `-L`)로 바꾸고 다르면 둘 다 본다. 깊이는 그대로라 뒤 상대 `..`도 실제 디렉토리에서 올라간다. 4096자(PATH_MAX)보다 길고 실제로 있는 디렉토리가 아닐 때만 그 안의 조상으로 자르고 모르는 디렉토리도 둔다(실제로 있는 깊은 디렉토리는 bash가 상대 cd로 들어갈 수 있어 자르지 않는다 — 65536자 상한. 후보 경로가 cd마다 길어져 판정 시간이 cd 수의 제곱으로 늘지 않게. 재리뷰 P1: 보호 뿌리로 접으면 worktree·작업 폴더 후보가 `work_dir` 자체가 됐고, 글자로만 접거나 1024자 안 조상으로 자르면 링크를 지나 clone으로 드는 사슬·깊은 디렉토리 뒤의 `..`를 놓쳤다). 셸이 풀 글자가 든 긴 후보는 그 보호 뿌리나 모르는 디렉토리다. 스택 칸을 모르게 되거나 sticky가 되면(위) 칸을 하나로 합쳐 상한 안에 둔다 — 뒤 popd 등은 스택 칸 전체로 보므로 판정은 같다. 합칠 때는 bash처럼 마지막에 넣은 칸이 이긴다(다시 넣은 칸은 최근 자리)(재리뷰 P1 성능: 없는 경로 pushd 1000개 + popd 1000개가 hook 시간 한도를 넘겼다, P0: 다시 넣은 칸을 첫 자리로 두면 넘침 때 최근 칸을 접었다). cd·pushd 대상의 디렉토리 스택 tilde(`~-` = OLDPWD, `~+` = PWD, `~N`·`~+N` = dirs 왼쪽에서 N번째(0 = cwd), `~-N` = 오른쪽에서 N번째, 뒤 `/…` 포함 — `~-//x`는 bash처럼 `$OLDPWD//x` = `$OLDPWD/x`, N은 ASCII 숫자만)는 `cd -`·`pushd +N`·`popd`와 같은 상태로 bash처럼 푼다(H 계획 A2 뒤 — 예전에는 글자 경로로 보아 이슈 DB clone에서 `cd /tmp && cd ~- && git push origin main`이 규칙 6을 피했다): `~-`는 이전 디렉토리(모르면 — 셸이 물려받은 OLDPWD — 모르는 디렉토리), `~N`은 이 글이 쌓은 스택 맨 위에서 N번째 칸(칸을 정확히 알 때. 더 깊으면 이 글 밖 칸 — 모르는 디렉토리), `~-N`(아래에서 세므로 이 글 밖 칸 수에 달렸다)과 칸을 모르는 스택의 `~N`은 `popd -N`처럼 스택 칸 어디든·모르는 디렉토리·cwd다. 풀 수 없으면(새 셸에는 OLDPWD가 없다, 스택이 짧다) bash는 글자 그대로 두어 cd가 실패할 수 있으므로 이전 후보를 버리지 않는다. 따옴표·`\`로 막은 tilde(`"~-"`·`\~-`·`~"-"`)는 글자다. 명령 글에서 `OLDPWD`·`PWD`를 바꿀 수 있으면(대입·`export`·`read`·`unset`·`${OLDPWD:=…}` — `$PWD` 읽기는 아니다. 이름은 푼 낱말로 본다: `export $'OLDP\x57D'=…`·`export OLDPW''D=…`·`export "OLDPW"D=…`도) `cd -`·`~-`·`~+`는 모르는 디렉토리를 후보로 두고(대입이 돌지 않았거나 서브셸·함수 안일 수 있다), 정적(따옴표만·절대 경로) 대입 값을 후보로 더한다(cd가 `$PWD`를 OLDPWD로 복사하므로 가짜 `PWD=<C>` 뒤 `cd Y; cd -`도 — 11/04 P2 E). 대입 자리는 앞 대입(`OLDPWD=…`)과 대입 빌트인(`export`·`declare`·`typeset`·`readonly`·`local` — `builtin`·`command` 뒤 포함, 옵션 뒤 모든 `NAME=값`: `export FOO=1 OLDPWD=…`)이고(`: ${OLDPWD:=/abs}`의 정적 값도), `eval` 안의 대입도 밖에 남는다. `env OLDPWD=…`은 부모 셸 변수가 아니라 그 자식 환경이다(11/04 재리뷰). cd·pushd 대상 밖의 디렉토리 스택 tilde(`git -C ~-`·`git -C ~1`·`env -C ~-`·`sudo -D ~-`·리디렉션 대상 `> ~-/f`)와 대입꼴 낱말 값의 tilde(bash는 인자에서도 푼다 — 앞 대입 `GIT_DIR=~-/.git`·`env GIT_DIR=~-/.git`·값 안 따옴표 밖 `:` 뒤 `X=a:~-`)도 같은 상태로 풀어 argv 변형마다 본다(11/04 P2 F, 재리뷰). 한 단순 명령의 같은 접두(`~-`끼리·`~N`끼리)는 같은 값이라 접두 값마다 변형 하나다(접두가 여럿이라 16개를 넘으면 접두 하나씩만 푼 변형 — 후보를 자르지 않는다). bash가 풀지 않는 꼴(`"~-"`·`--opt=~-`·`a=x=~-`·`"a"=~-`·`a\=~-`)은 글자 그대로다. 1024자 이하 후보는 실제 경로로만 본다 — 링크를 지난 뒤의 `..`을 bash 논리 cd처럼 글자로 접은 곳(예: `cd 링크/..`)은 보지 않는다. cd는 bash 범위대로 본다(H-A1 r6): 서브셸(`( … )`·`$( … )`·`<( … )`)·파이프 요소·`&` 백그라운드 목록의 cd는 밖에 남지 않고(`{ …; } | cat`·`… | while …; done`도), `&&`·`||` 뒤·`if`·`case`·루프 안 cd는 돌지 않았을 수 있어 전후 cwd를 모두 본다. and-or 목록에서 건너뛴 명령의 상태도 뒤 명령의 후보다: `A || B && C`의 C는 A가 성공해 B를 건너뛴 상태에서도, `A && B || C`의 C는 A가 실패해 B를 건너뛴 상태에서도 돈다(재리뷰 — `cd <clone> || cd /tmp && git push`·`false && cd /tmp || git push`). `if` 조건의 cd도 돌았으므로 `else`·`elif`·`fi` 뒤는 `if`에 들어갈 때 상태와 조건들의 끝 상태를 합쳐 본다(`if ! cd <clone>; then …; else …`의 else는 clone에서 돈다). 함수 본문 안 cd, 짝 없는 `)`·닫는 말, `source`·`.`, 셸 값이 든 `eval`은 그 뒤 명령에 모르는 디렉토리를 더하고, 명령 글에 `CDPATH`가 있으면 상대 cd도 그렇다. `eval`·`{ …; }`의 cd는 남는다. 레포 판별은 `git --git-dir`·`--work-tree`(공백형·`=`형)와 앞의 `GIT_DIR=`·`GIT_COMMON_DIR=`·`GIT_WORK_TREE=` 대입도 반영한다. `VAR=값` 대입 값 안의 `$( )`·백틱 본문과 `-c` 없는 셸이 읽는 heredoc 본문(`bash <<EOF`·공백 없는 `bash<<EOF`·`env bash<<-EOF`·`cat <<EOF | sh`·`source /dev/stdin <<EOF`(이 셸) — 그 연산자가 든 명령의 cwd 후보·OLDPWD로 한 번, 그 글에서 거친 나머지 cwd 후보(상한 안)와 넓은 OLDPWD(거친 cwd 모두·모르는 디렉토리)로 한 번 걷는다. 거친 cwd마다 다시 걷지 않는다 — 재리뷰, 실패하는 cd마다 후보가 늘고 중첩 heredoc에서 곱으로 커져 1KB 미만 명령이 hook 시간 한도를 넘기던(Claude Code는 시간 초과를 막지 않는다) 부류)은 명령으로 풀어 본다. `-c` 없는 셸의 here-string(`bash <<<"…"`·`sh<<<'…'`)도 그 명령의 cwd로 스크립트로 걷는다(H 계획 A2 뒤). 그 밖의 heredoc 본문과 셸이 아닌 명령의 here-string(`cat <<<"…"`)은 그 자체로는 명령으로 읽지 않지만, 파이프·stdin으로 셸에 넘겨 실행되는 정적 글은 서브셸 스크립트로 걷는다(11/04 P2 D): `echo "…" | bash`·`printf … | sh`·`cat <<<"…" | bash`·`echo … | cat | bash`·`(echo …) | bash`·`echo … |& bash`·`source /dev/stdin <<<"…"`·`bash -s <<<"…"`. 파이프 요소는 서브셸이라 그 글의 cd는 밖으로 새지 않는다. 글은 그 파이프 묶음이 시작할 때의 cwd 후보·OLDPWD로 한 번 걷는다(뒤 cd가 숨기지 않고, 거친 cwd마다 다시 걷지 않는다 — 재리뷰 P1 성능). `printf`는 bash처럼 서식을 인자마다 되풀이한 출력(`%s`·`%b`·`%d`·`%q`, `\n` 등)을 걷고(못 만들면 인자 하나씩·인자를 줄로 이은 글·변환을 지운 서식의 합), `echo`는 이스케이프를 푼 글도 걷는다. 셸 값이 든 글(`echo "gh pr merge $N" | bash`)은 `bash -c "…$N"`처럼 셸 값으로 판정한다. stdin을 읽는 셸은 묶음 어디에 있든(`… | bash 2>&1 | cat`) 보고, 값 받는 셸 옵션(`-o`·`+o`·`-O`·`--rcfile`)의 값과 `+x` 묶음은 스크립트 파일이 아니다. `source`·`.`이 stdin 경로(`/dev/stdin`·`/dev/fd/0`·`/proc/self/fd/0`)를 읽으면 here-string·heredoc을 이 셸에서 걷는다(cd가 남는다). 브레이스 그룹(`{ …; } | bash`)·셸이 만드는 글(`bash -c 'eval "$(cat)"'`·`xargs bash -c`)은 보지 않는다(남는 한계). 중첩 셸(`bash -c '…'`·here-string·셸이 읽는 heredoc·파이프 글)은 bash가 내보낸 `$OLDPWD`·`$PWD`를 물려받아 자식의 `cd -`·`~-`·`~+`를 푼다(11/04 P2 B — 예전에는 old=None으로 시작해 `cd <C>; cd /tmp; bash -c 'cd ~-; git push'`가 None이었다): 자식의 OLDPWD 후보는 그 자리(`-c`·here-string은 그 명령, heredoc은 연산자가 든 명령, 파이프 글은 묶음 시작)의 부모 후보 — 따라간 이전 디렉토리·정적 대입 값·앞 `env OLDPWD=`, 모르면(처음 OLDPWD·실패할 수 있는 이동·`cd -` 뒤) 모르는 디렉토리도 — 다(재리뷰 P0: 모르는 후보를 빼면 자식 `cd -; gh pr merge 3`이 None이었다). dash(이 머신의 `sh`)는 dir-stack tilde를 풀지 않으므로(`sh -c 'cd ~-'`는 실패하고 cwd 그대로) `sh`·`dash` 자식에서는 글자 그대로도 보고, 이 머신에 없어 확인하지 못한 zsh·ksh 자식은 그에 더해 OLDPWD를 물려받지 않을 수 있다고 본다(자식 cwd·모르는 디렉토리도 후보). 인용 안 줄바꿈은 낱말 글자다(`bash -c 'cd ~-\⏎/'`의 줄 이음은 자식이 푼다). heredoc은 bash처럼 찾는다(H-A1 r6, `_heredoc_scan` — 모든 Bash 규칙과 규칙 7 낱말 그물이 같이 쓴다): 인용(줄을 넘어 이어진다)·주석·산술(`$(( ))`·`(( ))`) 밖의 `<<`·`<<-`만 연산자이고 `<<<`는 아니다. 끝 표시는 줄 전체가 낱말과 같을 때만이다(`<<-`는 앞 탭만 뗀다). 끝 표시를 못 찾으면 본문으로 빼지 않는다(뒤 줄을 명령으로 본다). 주석(인용 밖 단어 첫머리 `#`부터 줄 끝)은 빼되 줄바꿈은 남겨 다음 줄을 따로 본다(`echo x # 메모` 다음 줄의 `git push`가 앞 argv에 붙어 규칙을 피하지 않게, K 3차). 변수 치환, 별칭, 스크립트 파일 안의 git 호출, 인자 안의 백틱·`$( )`, `xargs -I{} git -C {} …`처럼 입력 항목이 인자가 되는 경우, 표 밖 래퍼(`watch`·`flock` 등), 앞선 명령이나 셸 설정에서 `export`한 `GIT_DIR`·`GIT_WORK_TREE`·`GIT_CONFIG_*`(guard는 그 명령 앞의 대입만 본다)는 판정하지 못한다. 공백 없이 붙은 리디렉션(`x>file`, `>|`, `git</dev/null push`·`gh<x pr merge 3`·`git<>f`·`git<<<x`)은 따옴표 밖에서 나눠 본다(`<`도 `>`처럼 연산자 글자 — H 계획 A2 뒤, 예전에는 `git</dev/null`을 한 낱말로 보아 git을 몰랐다). 리디렉션 앞 숫자·`{이름}`은 공백 없이 붙었을 때만 fd다(`2>`·`0<`·`{fd}<` — `timeout 5 >/dev/null git …`의 `5`는 timeout 인자다). 줄 이음은 bash처럼 먼저 지우고 본다(`2\⏎>`는 `2>`, `cd ~\⏎-`는 `cd ~-`). `>&`·`<&` 바로 뒤 숫자는 복제 대상이라 뒤 `<`의 fd가 아니다(`2>&1</dev/null`은 `2>&1`과 `</dev/null` — 재리뷰 P0: 예전에는 `1<`로 붙여 `/dev/null`이 인자로 남았다). `>&-`·`<&-`(앞 fd·`{이름}` 포함)는 fd를 닫는 연산자이고 바로 뒤(또는 공백 뒤) 낱말은 복제 대상이 아니라 별도 인자다(bash — `git 0<&-push origin main`은 `git push …`, `gh 2>&-pr merge 3`은 `gh pr merge 3`; 닫기 뒤 `N>f`는 새 fd 리디렉션, 따옴표 친 `-`는 파일 — 11/04 P2 A). 예전에는 `-낱말`을 복제 대상으로 떼어 clone에서 `git 0<&-push`가 None이었다. `<<-`는 한 연산자다(`<<-cmds`를 `<<`와 `-cmds`로 나누면 끝 표시가 `-c` 옵션처럼 보였다). 셸의 `-c`는 리디렉션과 그 대상을 뺀 argv에서도 찾는다(`bash << -c`의 끝 표시는 옵션이 아니고, `bash -c </dev/null '…'`의 스크립트는 `'…'`다). `[n]<>f`는 읽고 쓰기로 여므로(파일을 만들고 앞부분을 덮어쓴다) 쓰기 대상이다(규칙 8). 따옴표 안 `<`·`>`는 글자이고 `<( )`·`>( )`는 서브셸이다. 산술(`$(( ))`·`(( ))`)·`[[ ]]` 비교 안의 `<`도 리디렉션으로 나뉘지만 명령 낱말이 아니라 판정에 영향이 없다. 매개변수 확장 안의 `<`·`>`(`${x/</y}`)도 나누는 것은 `>`와 같은 남는 한계다. 그래서 커밋 검사의 **진짜 강제는 git pre-commit hook**이고, Claude hook은 빠른 차단과 우회 방지 역할이다. 워크플로우는 커밋을 `db_pr publish --commit`이 하게 해서(셸 거치지 않는 `git commit -F`, 승인 해시·`core.hooksPath`·guard와 같은 검사 프로필·pre-commit을 같은 프로세스에서 확인) 스킬이 `git commit`을 직접 부르지 않는다. `publish` 토큰은 옵션과 무관하게 규칙 7로 `ask`다 (`07-workflow.md §Step 8-6`). **규칙 7 publish는 위 한계의 예외**로 넓게 본다(낱말 그물 하나, L M-2 — 상세는 §9 규칙 7 문단): 명령 글 전체(heredoc 본문 밖 줄 이음을 bash처럼 잇고 heredoc 본문 포함)에 이름 `db_pr`와 낱말 `publish`가 함께 있으면 `ask`다. 검색·출력·파일 받기(grep·echo·cat·tee 등)만인 줄과 그 줄이 연 heredoc 본문은 글로 보고 뺀다. 남는 한계는 낱말을 변수로 만들어 쓴 호출(`${P}lish`·`X=db; …/${X}_pr.py publish`)·인코딩한 호출, 스크립트 파일 안 호출(`bash push.sh` — eval 채점기는 결과의 `"published": true`로도 센다), 사용자 셸 프로필의 별칭·함수. 인용·`\`·`$'…'`·줄 이음으로 쪼갠 낱말(`pub"lish"`·`"$S"d""b_pr.py`·`pub\⏎lish`)은 붙여 본다. 반대로 db_pr 소스·문서를 sed·python으로 다루는 명령에 두 낱말이 함께 들면 `ask` 오판이다(싸다).

- **로컬 장치는 모두 우회 가능하다.** Claude hook은 최선 노력 파싱이고, git hook은 `core.hooksPath`를 바꾸면 꺼진다. main 직접 push 금지(PR 필수)와 메인테이너 경로(`/.githooks/` 등)의 CODEOWNERS 필수 리뷰는 **GHE 브랜치 보호로 서버에서 강제**되어야 한다 (`06-collaboration.md §6.1`). 규칙 6·11 완화(병합 계열 ask)는 `site_checks` `s4a.protection_guard` 통과가 전제다. 거친 판정은 대상 레포를 보지 않으므로 이슈 DB가 아닌 레포의 `gh` 병합·쓰기도 ask이고, 트래커가 아닌 모든 MCP 서버의 쓰기형 도구도 ask다(예: `mcp__gdrive__create_file`). 병합에는 서버도 승인 1을 강제한다(필수 승인 1·Dismiss stale approvals, `06-collaboration.md §6.1`) — GHE 웹 병합은 Claude hook·`db_pr merge`를 거치지 않으므로 서버 설정이 유일한 장치다. 이 전제가 없으면 `.githooks/`(main에 커밋된 스크립트가 모든 기여자 PC에서 실행됨)가 코드 실행 경로가 된다.
- git hook은 두 개다: `pre-commit`(`db_precommit.py`)과 **`pre-push`**. `pre-push`는 (a) 대상 ref가 `refs/heads/<base_branch>`면 거부하고, (b) 환경변수 `TT_PUBLISH_TOKEN`이 없거나 `<work_dir>/<작업 키>/state.json`의 `approved_hash`와 다르면 거부한다. pre-push는 작업 키를 모르므로 `<work_dir>/*/state.json`에서 `approved_hash`가 토큰과 같은 것을 찾는다. 토큰이 `manual`이 아니면 추가로 (c) push하는 커밋의 트리가 토큰과 같고, (d) 대상 브랜치가 그 `state.json`의 `branch`이며, (e) 원격 ref 삭제가 아니어야 한다(모두 `db_pr publish`가 이미 지키는 조건이라 정상 흐름은 거부되지 않는다). `base_branch`·`work_dir`는 사용자 config에서 읽고, 없으면 `main`·`<home>/work`로 본다. 플랫폼 분기(`17-platforms.md`): push하는 커밋의 `issue-db.config.yaml` `platform`(없으면 android, 읽지 못하면 거부)이 android가 아니면 `platforms.<p>.issue_db.base_branch`·`platforms.<p>.work_dir`(기본 `<home>/work-<p>`)을 쓴다. 샘플 DB(`tests/fixtures/issue-db-sample/.githooks/pre-push`)에 들어 있고, 운영 이슈 DB hook은 배포 때 같은 분기를 넣었는지 확인한다. pre-push는 플러그인 스크립트에 기대지 않는 이슈 DB 안의 자기완결 스크립트다(`plugin.scripts_path`가 무효해도 동작). 토큰은 `db_pr publish`가 자기 `git push` 호출에만 넣는다 (`contracts.md §3.2`). 직접 편집 기여자는 `validate` 통과 후 `TT_PUBLISH_TOKEN=manual`로 push한다(`CONTRIBUTING.md`). 목적은 도구 경로 밖의 실수 방지이지 권한 통제가 아니다.
- 3·4번은 git pre-commit hook(`db_precommit.py`)과 검사 내용이 겹친다. Claude 세션 안에서 더 빨리, 명확한 메시지로 막기 위한 이중 장치다.
- 7번은 `db_pr publish`가 내부에서 실행하는 `git push`에도 적용된다. `db_pr.py`는 Bash로 실행되므로 guard는 `python …/db_pr.py publish` 명령도 push로 보고 `ask`를 반환한다(위 "명령 판정의 한계"의 예외로 넓게 본다 — ask 오판은 싸다 — 낱말 그물 `word_net`, L M-2: heredoc 본문 밖 줄 이음을 bash처럼 빈 글로 잇고 heredoc 본문을 붙인 명령 글 전체에(끝 표시는 원래 줄에서 찾는다 — 본문 끝 줄의 `\`가 끝 표시를 삼키지 않게, 끝 표시가 없으면 그 줄을 빼지 않는다) 이름 `db_pr`(앞이 글자·`.`·`-`가 아니고 뒤가 글자·`-`가 아님 — `test_db_pr.py`·`dbpr/` 아님)와 낱말 `publish`(앞이 글자·`.`가 아니고 뒤가 글자·`.`·`-`가 아님 — `publish.json`·`publish-preview`·`dbpr/publish.py`·`published` 아님, `${P:-publish}`는 맞음)가 함께 있다. 인터프리터·`python3 -m`·`SUB=publish; … $SUB`·`C="…"; $C`·별칭 정의·`$( )`·`python3 -c`·heredoc 안 subprocess와 무관하게 ask다. `$( )`·백틱 없이 grep·rg·echo·printf·cat·tee만인 줄과 그 줄이 연 heredoc 본문은 뺀다 — `grep -n "db_pr.py publish"`·`cat > notes.md <<EOF`는 묻지 않는다. git·gh 줄은 빼지 않는다(`git -c alias.p='!…'`·`core.pager`·`GIT_SSH_COMMAND`·`gh alias set`으로 글을 실행할 수 있다 — 그래서 커밋 메시지·PR 본문에 두 낱말이 들면 ask 오판). 글 명령만인 줄도 셸로 넘기면(`echo "…db_pr.py publish…" | bash`) ask다. 남는 한계: 낱말을 변수로 만들어 쓴 호출(`${P}lish`·`X=db; …/${X}_pr.py publish`)·인코딩한 호출, 스크립트 파일 안 호출(`bash push.sh` — eval 채점기는 결과의 `"published": true`로도 센다), 사용자 셸 프로필의 별칭·함수. 인용·`\`·`$'…'`·줄 이음으로 쪼갠 낱말(`pub"lish"`·`"$S"d""b_pr.py`·`pub\⏎lish`)은 붙여 본다. 반대로 db_pr 소스·문서를 sed·python으로 다루는 명령에 두 낱말이 함께 들면 ask 오판이다). 이슈 DB `git push` 자체는 git 규칙(6·7)으로 본다.
- **`site-defaults.yaml` 없음**: guard는 멈추지 않고(종료 코드 2를 내면 모든 도구 호출이 막힌다) 경고만 낸 뒤 사용자 config로 판정한다. 이때 커밋 검사(3·4번)가 부르는 스크립트는 종료 코드 2를 내므로 이슈 DB 커밋은 거부된다 (`contracts.md §3.2` 설정 읽기).

### 9.1 표시 보조 hook (`show_guard.py`)

**왜**: Bash·Read 출력은 사용자에게 보이지 않는다. 그런데 모델은 스크립트 출력을 요약해 답하는 경향이 있다(스킬 eval 48회 중 22회: 확인 화면의 `생성 파일|README.md|수정` 행·diff 줄, 리포트의 근거 로그 줄, 초안 검증표 행이 빠졌다). 사용자가 승인하는 것은 **자기가 본 것**이므로, 확인 화면·리포트가 요약되면 승인의 근거가 무너진다. 스킬 지침만으로는 지켜지지 않아 hook이 기계적으로 되돌린다. **무엇이 의무인가**는 그 출력을 낸 스크립트가 남긴 표시 기록으로 정하고(L R, 아래 "표시 기록" — 도구 출력·명령 모양으로 추론하지 않는다), **보였는가**는 transcript의 보인 글로 본다(`common/shown.py`). eval 채점기는 같은 "보였다" 비교를 쓰되 의무를 transcript에서 추론한다(`tests/skill_evals/shown_infer.py`) — hook과 채점기는 독립된 두 판정이다(`tests/skill_evals/README.md` "사용자에게 보였다").

**대상**(의무 — 그 출력을 낸 스크립트가 기록한다): push 확인 화면(`db_pr.py stage --then-summary`·`summary`, 출력 형식·리디렉션과 무관, `## push 전 확인:` ~ `approved_hash:`), 트래커 게시 확인 화면(`issue_post.py render`, `## … 게시 전 확인:` ~ `post_sha256:`), Step 6 분석 리포트(`triage.py run`이 status ok일 때, 결정적 줄 — 분류 후보·근거 로그와 하위 줄·로그 범위 등 — 과 `must_show`), 초안 검증표(`db_verify.py rules --draft`, 규칙마다 상태와 통과가 아니면 사유가 든 한 행 — "R1~R4 통과"처럼 묶은 줄은 인정하지 않는다), 스킬 제안 patch 안내(`skill_patch.py`, analyze Step 7 `[스킬]` 규칙 제안: 고정 안내 줄과 파일별 `+N −M`, 실패면 메모 한 줄 — 글머리·굵게·백틱만 무시하고 글자 그대로, Step 7 질문이 아니어도 다음 질문·턴 끝 전에). 단 전부 통과한 초안 표(모든 행이 pass이거나 사유가 정확히 `해당 없음`인 skipped, `review_required`·needs-approval·allow-cause 없음 — `shown.draft_all_clear`)는 의무가 아니다: 승인 전에 보여야 하는 push 확인 화면의 "검증 결과"로 갈음한다(10/14 사용자). fail·`fixture 없음`·pending 등 다른 사유의 건너뜀이 하나라도 있으면 그대로 의무다. 줄마다 정규화(표 칸 공백·인용 `>`·코드 울타리·글머리)한 뒤 출력 뒤에 보인 글(assistant 텍스트·질문 도구 문구)의 어디에든 있으면 보인 것이다.

- **의무가 생기는 곳**: 스크립트 기록을 transcript의 Bash 호출에 시각으로 고정한 곳(`shown.anchor`: 명령에 기록의 스크립트 이름(또는 in-process로 부른 진입 스크립트 `via` — `triage.py run`이 부르는 `db_pr lock`)이 있고 tool_use 시각 − 2초(`ANCHOR_SLACK`) ≤ 기록 시각 ≤ tool_result 시각인 호출 중 가장 먼저 끝난 것). 고정되지 않은 기록(다른 세션·하위 에이전트·아직 끝나지 않은 호출·백그라운드 실행)은 버린다. 문서·fixture를 `cat`·Read한 화면 모양 글은 기록이 없으므로 의무가 아니고, 리디렉션으로 숨긴 화면도 기록이 있으므로 의무다(되읽기 규칙이 필요 없다). 채점기는 transcript에서 추론한다(Read로 다시 연 화면도 센다).
- **창 닫힘**(`shown.record_obligations`, 기록을 고정한 순서로만 — 작업 키와 무관): push 화면 = key가 다른 push 기록(다시 stage·summary)·publish·discard 기록, post 화면 = key가 다른 post 기록·approve 기록, 리포트 = 다른 리포트 기록·stage 기록·고정 뒤의 거부되지 않은 Step 7 분류 질문, 초안 표 = 같은 작업·같은 계획의 key가 다른 초안 기록·stage(`--dry-run` 포함)·discard·`lock` 기록·리포트 기록(작업 경계), patch 안내 = 닫히지 않는다(같은 key — 작업·스킬 이름 — 의 내용이 다른 기록이 오면 새 의무로 바뀌고, 다른 분석 스킬의 patch는 따로 의무다. 화면처럼 그 턴 안에서만 본다). **같은 key는 하나의 의무**다: 같은 key의 뒤 기록은 새 창을 만들지 않고 첫 창을 그대로 쓴다(열려 있으면 열린 채, 닫혔으면 닫힌 채). 단 push key는 트리 해시라 커밋 메시지·PR 제목·리뷰어만 바꿔 다시 stage해도 같으므로, 내용(화면 전문, 리포트는 결정적 줄·`must_show`)이 바뀌면 열린 창은 버리고 새 의무를 연다(새 화면을 그 기록 뒤에 다 보여야 한다). 다른 화면·초안에 밀려 닫혔던 key가 다시 오면(A→B→A — 사용자가 마지막에 본 것은 B) 내용이 같아도 새 의무다. publish·discard·stage 등으로 닫힌 창에 내용이 다른 같은 key가 오면(publish 실패·discard 뒤 같은 트리를 다른 메시지로 다시 stage) 창은 닫힌 채(Stop은 보지 않는다)지만 내용·시작을 새 기록으로 바꿔 publish 승인 판정(pre-bash)은 새 화면으로 한다. 그래서 같은 계획을 고치지 않고 다시 돌려 같은 결과를 덜 보이게 찍어도(사유를 자른 출력) 기록에는 전체 규칙이 있어 첫 의무가 그대로다(h5-18b eval 18). 전부 통과가 아닌 결과는 **다른 계획**(`plan-narrow.json`)의 초안 기록으로 닫히지 않는다: 좁힌 안을 다른 파일로 돌려 통과해도 처음 실패 표(걸린 fixture·시그니처 전역 키)를 보이고 사용자가 좁힐지·허용할지 고른다(h3-d eval 18). hook이 거부했거나 사용자가 권한 확인에서 거절해 실행되지 않은 호출은 스크립트가 돌지 않았으므로 기록이 없고 창을 닫지 않는다 — 다시 시도해도 다시 본다. Stop·질문은 열린 창만 본다.
- **PreToolUse의 transcript 기다림**: transcript는 비동기로 쓰여 PreToolUse 때 같은 응답의 앞 텍스트 블록이 아직 없을 수 있다(10/14 sm4: 화면 전문을 쓴 직후의 질문 8건이 거짓 거부). pre-ask·pre-bash는 지금 호출(`tool_use_id`)이 transcript에 기록될 때까지 최대 2초(새로 붙은 바이트만 확인) 기다린 뒤 판정하고, 끝내 기록되지 않으면 거부하지 않는다(stderr 경고). 입력에 `tool_use_id`가 없으면 기다리지 않고 바로 판정한다. **전제**: 한 응답(같은 `message.id`)의 텍스트 블록은 그 tool_use보다 먼저 transcript에 붙는다(sm4 transcript 300개 응답에서 예외 없음, `tests/mocks/plugin-probe/README.md` 13번 — 사내 버전에서 다시 확인).
- **되돌림·거부 문구**: 첫 줄 맨 앞은 표식과 키다. Stop은 `[telephony-triage] show-guard <key> — 되돌림(오류 아님): <종류>을/를 요약했다(빠진 줄 k/m). Bash 출력은 사용자에게 보이지 않는다.` + 할 일 한 줄, 거부(pre-ask·pre-bash)는 `… <key> — 거부됨(오류·일시 장애 아님). 이 호출은 실행되지 않았다. 기다리거나 같은 호출을 그대로 다시 하면 또 거부된다.` + `까닭: …(Bash 출력과 이 거부 문구는 사용자에게 안 보인다)` + `할 일: …`(질문은 보일 줄을 질문 본문 앞이나 바로 앞 글에 넣고 다시 부른다, stage는 먼저 글로 표를 쓰고 같은 응답에서 같은 stage를 다시 — 새 질문을 만들지 않는다) — 10/14 모델이 거부를 일시 오류로 읽고 기다렸다 같은 호출을 되풀이하거나(`sleep 3`) 거부 문구가 사용자에게 보인다고 믿은 일 때문이다. 그 뒤 빠진 줄 예(8줄까지) + 붙일 화면 전문(12KB 이하일 때). `<key>`는 스크립트가 기록한 key다: `push:<approved_hash>`·`post:<sha 앞 16자>`·`report:<KEY>#<run>`·`patch:<KEY>/<스킬 이름>`·`draft:<sha1 12자>`(`<KEY>/<plan 파일>`과 규칙·상태·사유 — 같은 작업·같은 계획에서 같은 결과로 다시 돌려도 같은 key라 한도를 함께 쓰고, 작업이 다르면 다른 key다). 막은 횟수는 그 의무(첫 기록)가 생긴 뒤의 표식만 센다 — 다른 작업·지난 의무의 같은 키는 세지 않는다.
- **한도**: 같은 키로 막은 횟수(transcript의 표식이 든 Stop 피드백·거부된 도구 결과)가 **2회**(`MAX_BLOCKS`)에 이르면 더 막지 않고 `systemMessage` "[telephony-triage] 확인 화면 일부를 답에 보이지 못했다(재시도 한도) — <경로>를 직접 확인"만 낸다(안전 관문은 그대로이므로 사람이 직접 확인한다). 단 거부된 호출을 똑같이(도구 이름과 `description`을 뺀 입력이 같다) 그 사이 보인 글·질문·사용자 입력 없이 다시 한 거부(다른 도구 호출 — `sleep 3` — 만 있었다)는 키마다 1번(`BLIND_FREE`)까지 세지 않는다: 거부를 일시 오류로 읽고 되풀이한 것은 표를 보일 기회를 쓴 것이 아니기 때문이다(10/14). 그래서 같은 키 거부는 많아야 3번이고, 그때 거부 문구에 "방금 거부된 것과 똑같은 호출이다 … 글을 먼저 쓴다"를 더한다. Stop 피드백은 덜 세지 않는다. Stop이 연이어 막혔는데(`stop_hook_active`) 이번 턴 transcript에 표식이 없으면(다른 hook이 막았거나 피드백이 기록되지 않는 버전) 횟수를 셀 수 없으므로 아무것도 내지 않는다. transcript 끝 16MB 안에 실제 사용자 입력이 없으면(이번 턴의 시작을 모른다) Stop·질문은 판정하지 않는다. Claude Code 자체의 연속 계속 한도(8회)도 있다. 화면이 도구 출력에 없던(숨긴) publish·approve도 같은 한도다(J2, 10/16 사용자 — 예전 "화면 없음" 갈래의 키마다 4번은 없앴다): 기록이 있으므로 보통 판정이고 거부 문구에 붙일 화면이 실린다.
- **내부 오류(fail-open)**: 입력·transcript·사용자 config·표시 기록을 못 읽거나, import(`common/shown.py`·`common/userconfig`) 실패·판정 중 예외면 판정하지 않고 stderr에 경고한다(Stop은 이번 턴 transcript에 화면·리포트 흔적이 있을 때만 `systemMessage` "show_guard 판정 못 함"도 — 매 턴 되풀이하지 않게). 입출력은 UTF-8로 읽고 ASCII(JSON 이스케이프)로 쓴다(Windows 콘솔 인코딩과 무관). 이유: 표시 보조일 뿐 안전을 맡지 않는다 — 실제 관문(규칙 7 publish `ask`, `approved_hash`·pre-push 토큰, 규칙 2 게시 승인 기록·`ask`)은 그대로라 hook이 열려도 승인 없는 쓰기는 생기지 않는다. 반대로 닫히면(모든 질문·Stop을 막으면) 세션이 멈춘다. pre-bash(G3)도 같다.
- **표시 기록**: hook은 파일을 쓰지 않는다(종료 코드는 항상 0). 기록은 스크립트가 `<work_dir>/.shown/log.jsonl`에 쓴다(형식 `contracts.md` "표시 기록" — 줄마다 JSON 하나, 배타 잠금 아래 한 번에 append, 4MB를 넘으면 `log.jsonl.1`로 한 세대 회전, 쓰기 실패는 stderr 경고만이고 본 작업 결과는 그대로). hook은 사용자 config의 모든 프로필 `work_dir`(TT_PLATFORM과 무관)에서 끝 2MB(지금 파일이 작으면 `.1`의 끝까지)를 읽고, 세션 첫 시각보다 이른 기록은 버린다. 이 세션의 기록이 없으면 transcript를 읽지 않고 끝낸다. transcript는 끝 16MB만 읽는다. **`.shown` 기록은 마스킹된 화면과 같은 민감도다**: 확인 화면·리포트 결정적 줄·초안 표 사유를 그대로 담는다(작업 디렉토리의 `report.md`·`state.json`과 같은 내용, work_dir 권한 700). 사내 반입 때 `.shown/`은 work_dir(사용자 PC) 안이라 레포·반입 묶음에 들어가지 않는다 — 사외 PC의 기록을 사내로 옮기지 않고, 사내 기록을 사외 보고·이슈에 붙이지 않는다(hook_replay는 숫자만 낸다). 작업 폴더가 아니므로 `cleanup`·`discard` 대상이 아니다.
- **전제**: hook 입력의 `transcript_path` 파일이 있고 줄마다 `timestamp`가 있어야 한다 — tool_use·tool_result 줄의 시각이 스크립트 실행을 감싼다(기록 시각이 그 사이, 2초 여유: `tests/mocks/plugin-probe/README.md` 15번, 확인 방법 `tools/hook_replay.py`의 `records.unanchored` = 0). 시각이 없거나 고정에 실패하면 판정하지 않는다(fail-open). 세션을 저장하지 않는 실행(`claude -p --no-session-persistence`)에서는 파일이 생기지 않아 아무것도 판정하지 않는다(stderr 경고만, fail-open). 스킬 eval 실행기는 plugin 모드에서 세션을 저장하고 transcript를 run 디렉토리로 옮긴다(`tests/skill_evals/README.md`).
- **한계**: 최선 노력이다. Read로 연 화면은 `post` 안내가 없다(matcher Bash). 기록 파일을 모델이 직접 고치거나 지워도 guard로 막지 않는다(J8 — 표시 보조라 안전 관문(규칙 7 `ask`·승인 해시·pre-push 토큰)은 그대로). 고정 실패(시계가 다른 실행 환경 — 호스트 Claude Code와 컨테이너·원격 Bash, 백그라운드 실행)·같은 work_dir를 쓰는 동시 세션(세션 lock으로 드물다)·회전으로 밀려난 기록(4MB 한 세대)은 판정하지 않거나 다른 세션의 기록을 볼 수 있다. publish·approve·stage 판정은 guard의 낱말 그물이라 넓다 — 오판이어도 맞는 의무(열린 화면·표)가 있을 때만 거부한다. 같은 응답의 앞 텍스트가 PreToolUse 때 transcript에 있다는 것, Stop 피드백이 `isMeta`로 남는 것, 여러 그룹·hook이 걸리면 모두 실행되고 `deny`가 이기는 것(거부 결과 `PreToolUse:<tool> hook error: <reason>`, `is_error: true`)은 사외 실험(2026-10-14)으로 확인했고 사내 버전은 S1에서 다시 확인한다(`tests/mocks/plugin-probe/README.md` 10~12번), 시각 고정은 15번. 자동 백그라운드 전환: 120초를 넘긴 Bash 호출은 Claude Code가 백그라운드로 돌려 tool_result가 먼저 기록되므로, 그 뒤에 쓴 기록(긴 `stage`)은 `at > rts`라 고정되지 않아 판정하지 않는다(옛 transcript 판정은 화면 없음으로 거부했다). 사용자 config의 모든 프로필 work_dir를 읽으므로 다른 프로필로 동시에 도는 세션의 기록이 이 세션의 같은 스크립트 호출 시각 안에 들면 이 세션에 고정될 수 있다. Windows Claude Code의 PowerShell 도구는 `hooks.json`의 `Bash` matcher에 걸리지 않는다 — guard 규칙 3~8·10·11과 show_guard가 PowerShell 호출을 보지 못한다(사내 S-1/S-2에서 노출 여부를 확인하고, 있으면 matcher를 더하거나 그 도구를 deny한다 — `tests/mocks/plugin-probe/README.md` 16번).
- **transcript 집계**(`usage_stats.py --transcripts`, S-7 운영 지표): hook이 아니라 사후에 transcript를 읽어 usage 숫자·표식 일치 개수만 낸다(내용·명령·경로·세션 ID·작업 키 없음). transcript는 평문이므로 팀원 PC에서 읽을지는 S-7에서 사내 보안 기준으로 정한다.
