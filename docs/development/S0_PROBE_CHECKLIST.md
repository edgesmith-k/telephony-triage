# S-0 선행 확인 체크리스트 (사내 로그가 모의 로그와 다를 때 가장 먼저)

- 대상: 사내에 사외 초안을 반입하기 **전**(또는 직후 S-1 전에), 사내 로그 형식이 사외 파서가 가정한 것과 얼마나 다른지 **30분 안에** 확인하려는 사람.
- 설계 근거: `docs/design/15-local-draft.md §15.5` S-0. 이 문서는 그 절차를 실행 가능한 순서로 풀어 쓴 것이다.
- **Claude를 쓰지 않는다.** 파이썬만 돌리므로 토큰이 거의 들지 않는다.
- 결과 숫자·로그는 **사내 `SITE_PROFILE.md`에만** 적는다. 사외로는 사용자가 직접 타이핑하는 정성 결론 한두 문장만(마지막 절).

## 왜 하나

사외 파서는 AOSP 기준 형식(threadtime, `RILJ`)을 가정한다. 사내 로그가 다르면 S-4(`parser-rules` 보정)까지 가서야 발견되고, 그때는 되돌리는 비용이 크다. S-0는 "시그니처 매칭이 실제 logcat에서 통하는가"를 그 전에 확인한다.

## 준비 (한 번)

1. 사외 초안에서 `plugin/`, `tools/s0_stats.py`, `tests/helpers/make_plugin_root.py`, 그리고 이슈 DB 뼈대의 `parser-rules/` 3개(`tags.yaml`, `ril.yaml`, `extractors.yaml`)를 사내로 가져간다. 로그와 숫자는 사내에 남는다.
2. **`site-defaults.yaml`이 없으면 파서가 멈춘다** (`종료 코드 2: 사내 기본값 없음`). S-0는 그 파일을 만드는 S-3보다 앞이므로, 임시 플러그인 루트를 쓴다:
   ```
   python3 tests/helpers/make_plugin_root.py        # 마지막 줄이 임시 루트 경로
   ```
   (개발 레포의 `plugin/` 안에는 `site-defaults.yaml`을 만들지 않는다. 반입 체크리스트 §15.4.)
3. 실제 로그 **3~5개**를 고른다: 카테고리를 섞고(data, call, sim 등), **듀얼 SIM 로그 1개 이상**, 가능하면 시계가 바뀐 로그 1개.
4. 로그에 개인정보가 있어도 된다: 도구는 `--mask`로 마스킹한 뒤 개수만 센다.

## 실행

```
python3 tools/s0_stats.py <logcat 1> <logcat 2> ... \
    --rules <parser-rules 디렉토리> --tz Asia/Seoul --year 2026 \
    --plugin-root <위 임시 루트>
```

- `--tz`: 로그 시각의 타임존(연도 없는 logcat의 해석 기준). 모르면 단말 로컬 시각인지부터 확인(S7).
- `--year`: 로그 첫 줄의 연도. 연도가 로그에 있으면 생략 가능.
- 출력에는 로그 문구가 없다. 태그 이름과 개수·비율만 나온다.

## 결과 읽는 법

| 지표 | 정상일 때 | 이렇게 나오면 | 의미와 다음 행동 |
|---|---|---|---|
| **시각 파싱** `읽은 줄/전체 줄`(형식만 본다, 태그와 무관) | 100% 근처 | 90% 미만 | 읽지 못한 줄이 있다 = 줄 형식이 다르다(타임스탬프 형식, 버퍼 접두어, 인코딩). 어느 줄이 실패하는지 `parse_logcat parse --full`의 `warnings`를 본다 (S7) |
| **시각 범위 / 시계 이상** | 범위가 로그 기간과 같고 이상 0 | 이상 1건 이상 | 단말 시각이 되감기거나 점프한다. 도구는 이를 `coverage`로 **알려 준다**(조용히 틀리지 않음). 이슈 분석 때 "증상 스캔" 경로를 쓴다 |
| **수집 태그 비율** `수집 줄/읽은 줄` | 대부분 | 낮음 | `tags.yaml`에 없는 태그가 많다 = 매핑 부족(S-4). 줄 형식 문제가 아니다 |
| **RIL 짝 맞춤** | 요청이 있으면 대부분 짝이 맞음 | **요청 0건** | 먼저 `tags.yaml`에 RIL 태그가 있는지 본다. 형식이 `RILJ`와 같으면 `platform.ril.tags`, 다르면 `ril.py` 정규식 포팅(S-4a) = 벤더 RIL (S9·S10) |
| | | 짝 맞춤 낮음 | 로그가 여러 파일로 나뉘었거나(회전), 요청·응답 문구가 다르다. 사외 알려진 한계(`docs/history/improvement-handoff-2026-10.md` R4) |
| **phone_id 추출** | 듀얼 SIM 로그에서 대부분 추출 | 낮음 / 0% | 슬롯 표기가 `[PHONE<n>]`·`DNC-<n>`이 아니다(`[SUB<n>]` 등). `site-defaults.yaml`의 `platform.log.phone_id` 설정 대상 (S20) |
| **태그 상위(전체)·미수집 태그 상위** | 데이터 스택은 `DNC-`, `DN-`, `DPM-`… | 모르는 태그가 대부분 | 카테고리 태그 매핑(`tags.yaml`)이 비어 있다. S-4에서 채울 목록이 이것 (S8) |
| **warnings / errors** | 0 | 있음 | 문구를 읽고 원인 분류 |

## 판정 기준 (어떤 단계가 커지나)

| 보이는 것 | 결론 | 커지는 단계 |
|---|---|---|
| 시각 파싱 ≥ 95%, RIL 짝 있음, 슬롯 추출됨, 태그만 낯섦 | **값 교체 수준** | S-4 (`parser-rules` 문구 교체) |
| 시각 파싱 낮음 | 줄 형식이 다름 | 파서 코드 수정 (S7) |
| RIL 요청 0건 | 벤더 RIL | S-4a 파서 포팅(`ril.py` 정규식) |
| phone_id 낮음 | 슬롯 표기 다름 | `platform.log.phone_id` 설정 (S20) |
| 위가 여럿 | 사외 파서 모델이 안 맞음 | **S-1 전에 사용자와 방향 재검토** (기존 파서를 백엔드로 포팅하는 쪽으로) |

## 사외로 가져가도 되는 것 (사용자가 직접 타이핑하는 정성 결론만 — 파일·숫자·로그 반출 없음)

- 가능: "슬롯 표기가 문서와 다름", "RIL 페어링 방식 재검토 필요", "시각 형식이 `YYYY-MM-DD HH:MM:SS.mmm`임", "로그가 2개 파일로 회전됨".
- 금지: 로그 원문, 태그 이름 목록, 구체 숫자(`SITE_PROFILE.md`에만).
