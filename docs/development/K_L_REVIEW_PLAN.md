## L — 종합 개선 검토 (Opus, 노력 max, 관점별 에이전트 4개 병렬 + 오케스트레이터 종합 — 목록만, 구현은 사용자가 고른 것만)

- 실행 방식(사용자 10/15): 메인 세션이 오케스트레이터. 아래 네 관점마다 **Opus·노력 max 에이전트를 하나씩 병렬로** 띄우고(읽기 전용, eval 실행 금지), 각 결과를 받아 오케스트레이터가 겹침 정리·충돌 조정·우선순위를 **종합 판단**한다.
- 네 관점 중 "매니저"는 사용자의 관리자 위에서 이 도구를 종합 보고받고 **도입을 검토·결정하는 사람**이다.

근거: eval 실행 기록(`tests/skill_evals/workspace/` h1·h3·h7·o1 등 — 질문 수·순서, hook 거부 왕복, 리포트 길이, 비용), 커맨드·스킬 흐름, 설계 문서, 기존 아이디어 목록(`docs/history/TEAM_PLUGIN_EXPANSION_IDEAS_2026-10-07.md`, `docs/history/TEAM_PLUGIN_WEB_PORTAL_2026-10-07.md`, `docs/design/99-deferred.md`, RF-4~9, `docs/history/draft-notes-2026-10.md` "10/13 이동" R-36~47).

1. **사용자(기여자·카테고리 오너)**: 편의성·보완 — 입력 번거로움, 중복 질문, 막혔을 때 안내, 리포트 가독성, 처리 시간·비용, 자주 쓰는 흐름 단축.
2. **관리자(메인테이너) 장기 유지보수**: 플랫폼 확장(oFono 등, `17-platforms.md`), Android 버전 업(새 소스 트리·태그·문구 변경, RF-4), 트래커 추가(`18-trackers.md`), 스키마 마이그레이션, 사내 재반입, 테스트·eval 유지 비용, 코드 구조(예: `shown.py` 정규식 경계 사례 → 표시 판정 단순화 R).

4. **응용·확장**: 다른 용도·도메인(배치 사전 triage, 회귀 감시, 릴리스 게이트, 대량 스크리닝, CP 로그, 다른 로그 도메인 — 안내서 "활용 방안"), 자동화(RF-8), 웹 포털.

- 에이전트별 결과물: 관점별 항목 표(근거 file:line·eval 기록 경로 포함)
- 오케스트레이터 종합 결과물: 관점 간 겹침·충돌 정리, 전체 우선순위, 관점별 항목 표(누가·무엇·효과·규모 S/M/L·**eval 영향**·시점: 사외 지금 / 사내 파일럿 뒤 / 장기). 매니저용 한 장 요약 포함. 공유 가능한 문서(artifact 또는 Docs)로 만들고 링크를 남긴다.
- 사외에서 지금 할 것은 eval에서 반복 관찰된 불편 등 확실한 것만 사용자에게 제안한다. 나머지는 파일럿 피드백 뒤.
- **eval 영향** 칸(사용자 10/15): 항목마다 `없음`(문서·자료만) / `관련 eval`(사용자에게 보이는 흐름·질문·화면·리포트 줄·새 커맨드 — 해당 eval 단언 수정·eval 추가·채점기 판정 추가, 재측정 eval당 ≈$0.4) / `전체`(스킬 공통 지침·hook·`common/shown.py` 등 공통 판정 변경 — 결정 (i)로 전체 재측정 ≈$22·1.5~2시간)를 적는다. 동작이 바뀌면 `offsite_results.json` 재생성·전체 테스트·반입 묶음 재생성이 뒤따른다.
- 구현하기로 고른 항목은 **모두 구현한 뒤 eval 재측정을 한 번만** 한다(재측정을 나눠 반복하지 않는다). 흐름을 크게 바꾸는 항목은 사내 파일럿 피드백 뒤로 미루는 것을 기본으로 제안한다.
