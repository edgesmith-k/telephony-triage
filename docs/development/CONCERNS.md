# 사용자 고민과 보완 (계획 H·I, 11/03~)

> 사용자가 짚은 고민마다 **무엇이 걱정이었나 → 어떻게 판단했나 → 무엇으로 보완했나 → 지금 상태**를 남긴다. 결정의 정본은
> `MODULE_SKILLS_DECISIONS.md`이고, 이 파일은 사람이 읽는 요약이다. G에서 HTML(`docs/materials/`)로도 만든다.

## 모듈 스킬

| 고민 | 판단 | 보완 | 상태 |
|---|---|---|---|
| 사내에 이미 있는 분석 스킬을 계속 쓰고 싶다 | 모듈 문서로 강제하면 기존 자산을 버린다 | 카테고리별 `prefer: module|skill`, `skill_dir` — 설치 스킬을 파일로 읽는다(모든 런타임) | B1 ☑ |
| 모듈 스킬 레포도 승인 뒤 업데이트 가능해야 한다(이슈 DB처럼) | 맞다 | 모듈 레포 PR + +1 병합(E에서 자동 제안 흐름) | 안내 그림 반영, E 다음 묶음 |
| 공개 형식을 따른 합성 로그로 모듈별 필터·가설을 잘 하게 | 합성 줄이 실제 줄 모양을 못 따라갈 수 있다(사내에서 확인) | 공개 형식(oFono syslog·AOSP logcat)을 따른 합성 로그를 사례·fixture로(남은 식별자 0 확인), 모듈 필터를 합성 로그로 측정(필수 줄 recall 37→64% 등) | B2 ☑, C1+D 사례 14개 합성 |
| 모듈 스킬로 어떻게 결과를 판단하나 | 정답을 아는 사례로 스크립트 채점 | 사례마다 정답 층·데몬·근거 regex, 문서 있음/없음 비교, 안전 행, 토큰 차이. 정답 표는 사용자 확인 | C0 ☑, C1+D 진행 |
| 모듈별로 실제 이슈 유형이 다양하다(sim 인식·느림·eSIM, data 연결·끊김·재시도·APN·ping·쓰루풋·원치 않는 패킷, CSFB·eCall·VoLTE·NR, 타이밍·크래시 …) | 사례 2~3개로는 다 못 덮는다 | 모듈 문서에 "증상별 첫 점검" 표, 텔레포니 로그로 못 보는 증상은 받을 로그 안내, 빈 증상 합성 사례 약 11개 추가, 나머지는 사내 실제 이슈(MS-2) | C1+D 보정(금) |
| 문서 보정을 1회로 줄인 것 | 순서대로 하면 회차가 반나절 | 모듈별 에이전트 병렬 — 회차 1시간 남짓, 최대 2회 | C1+D 보정(금) |
| 모듈 eval 정답을 결론 하나로 못 박으면 정답 표가 틀릴 때 측정이 흔들리고 확인 부담도 크다 | 실제 탐색(5-2)도 가설 1~3개(추정)라 eval이 어긋나 있었다 | 탐색 사례는 후보 1~3개 + 가장 유력, 인정 후보가 목록에 있고 함정이 가장 유력이 아니면 통과, 1순위 적중은 따로 기록, 정답 표는 "인정 후보 / 함정"(스크립트 생성) | ☑ 11/06 |

## 로그가 바뀔 때

| 고민 | 판단 | 보완 | 상태 |
|---|---|---|---|
| 같은 버전(예: Android 17)인데 버그로 판단 근거 줄이 사라지면 | 보통은 시그니처가 안 맞아 "후보 없음"으로 가고 아무도 모른다. 줄이 **없음**에 기대는 시그니처(`must_not_match`)는 그 줄이 사라지면 **잘못 분류**될 수도 있다(B 리뷰에서 확인). 회귀 검증은 저장된 예전 로그와 비교해서 못 잡는다. verify-fix는 흔적이 필수라 거짓 "고쳐짐"은 막는다 | **A** 모듈 문서에 대체 근거 **B** 이슈 DB 작성 지침(다른 층 줄로 시그니처 하나 더(OR) — 증상 시그니처도 같은 줄에 기대면 둘 다, 대체 줄은 같은 슬롯·창 안; 없음에 기대는 근거는 "일어났음" 줄을 `must_not_match`에 하나 더) + `db_lint --advice` 참고 알림(관문에 안 듦) **C′** 분석 때 부분 일치·없는 줄 표시와 시그니처 추가 제안 **C** 정기 점검에서 "자주 맞던 시그니처 0건" 감지 — DB 업데이트는 `update-signature`(사용자 확인·PR·+1) | B ☑ c73550f, A ☑ C1+D 보정, C·C′ ☑ (11/06) |
| 스크립트가 후보를 걸렀는데 완벽히 일치하지 않을 때, 코드를 한번 확인해 대조하면 과한가 | 과하지 않다 — 부분 일치일 때만, 스크립트로 먼저 하면 토큰이 거의 안 든다. 로그만으로는 "줄이 사라짐 / 그 경로를 안 탐 / 로그 미수집"을 못 가른다 | **C′ 코드 대조**: 코드 경로가 있으면 없는 줄의 출력 문구를 grep → 못 찾음·문구 다름(path:line)·같음 한 줄을 리포트에, 문구가 다르면 새 문구로 시그니처 추가 제안(사용자 확인). 모델은 애매할 때만 해당 구간을 읽음 | ☑ 11/06 (출력은 path:line만, 제안은 마스킹 로그 줄로만) |
| 리팩토링으로 로그가 확 바뀌거나, oFono는 개발 중이라 데몬이 생기고·사라지고·합쳐지고·대체된다 | 이름·규칙은 데이터여야 한다. 이번 코드에 데몬 이름이 박힌 곳 3개 발견 | 판별 대상 이름(레벨 보정·벤더 IPC 대상)을 이슈 DB `tags.yaml` 속성으로(기본값 유지), 모듈 문서 데몬 이름을 공통 표 한 곳(역할 → 지금 이름·구 이름)에, 과도기에는 옛·새 이름을 같이, `modules coverage`(토큰 0)로 새·사라진 데몬 발견 → `modules.yaml` PR | ☑ 11/06 C1+D 보정 |
